## 任务一 · Docker 镜像构建实测

实测命令与输出（在 `skeleton/` 下执行）：

```
$ docker info
  Client:  (Docker Desktop 29.7.2 已安装，仅打印 Client 段；Server 段缺失)
$ docker version --format '{{.Server.Version}}'
  failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine;
  check if the path is correct and if the daemon is running:
  open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.
  退出码 1
```

**结论：本机 Docker daemon 未运行**（不是没装客户端，是守护进程没起来）。

**处理**：按项目规则，未尝试安装或启动系统服务。Docker 镜像的本地构建 = **未验证，列为待办**。

**替代证据（非本地，仅作代理）**：商用就绪报告 §10.3 记载 CI 的 docker job「5 步全 ✓」（head `9ef9c70`），即镜像在 CI 内可构建成功。但 CI 产出的是流水线内的临时构建，**尚未产出打 tag 的生产镜像制品**；且 CI 跑在境外 runner，与《部署手册》假设的目标 Linux 服务器不是同一台。

**静态核对（不依赖 daemon，已做）**：
- Dockerfile 的 9 个 COPY 目标（根 `pom.xml` + 8 个 `dy-*/pom.xml`）全部存在（`find . -maxdepth 2 -name pom.xml` 确认 9 个）。
- `.dockerignore` 已排除 `target` / `node_modules` / `_work` / `_work_*` / `*.log` / `frontends` / `.github`，构建上下文干净（根目录散落的 `_audit_*.log`、`_work_final_mvn.log` 等会被 `**/*.log` 命中排除）。
- 根因已显式处理：`-Dexec.skip=true` 跳过 4 个 validate 门禁（冻结契约在 `skeleton/` 上级、maven 基础镜像无 python），本 RUN 定位是「打包」而非「验证」（与 Dockerfile 注释、原报告 §2.2④ 一致）。
- 构建期依赖已具备：已存在 `skeleton/requirements.txt`（CI 侧 Python 依赖归一，见原报告 §2.2）。

**静态观察（未实测、仅供参考，不列为阻断）**：
- Dockerfile HEALTHCHECK 用 `wget`（第 58 行）；而 `docker-compose.prod.yml` 的 app healthcheck 改用 `curl`（第 56 行）。运行期基础镜像 `eclipse-temurin:17-jre` 是否自带 `wget`/`curl` 需在容器构建/运行后核实，否则 healthcheck 会误判 unhealthy。
- `docker build` 阶段**不会**执行 HEALTHCHECK，故该点不影响构建成败，只影响容器运行时健康判定；建议上线前确认工具存在，或改为容器内 Java 探针。

## C. 一键部署核对（首次生产部署前必须人工确认）

参考《商用就绪报告》§五 与 `skeleton/deploy/DEPLOY.md` §0–§4。下列任一项未过，不得视为「部署完成」：

1. **服务器**：Linux x86_64 ≥2C4G，Docker Engine ≥24 + compose 插件（DEPLOY §0）。
2. **网络**：域名解析到公网 IP；80/443 开放，5432/6379/8080 不对公网开放（DEPLOY §0）。
3. **TLS**：证书就位（Let's Encrypt 或商业证书 → `certs/fullchain.pem` + `privkey.pem`）。
4. **密钥填充**：`.env` 由 example 复制、逐项替换 `CHANGE_ME`；`DY_JWT_SECRET` 用 `openssl rand -base64 48`；`.env` `chmod 600`（DEPLOY §1②）。
5. **仓库转私有**：public 状态商用代码禁止（DEPLOY §4①；当前 public，报告 §10.1）。
6. **required check 配置**：4 个 workflow 设为 required status check（DEPLOY §4④；CI-ENABLEMENT 仍写 3 个，需更新为 4）。
7. **主密钥走 KMS**：`DY_MASTER_KEY` 上线前必须走 KMS 注入，不得长期明文（`docker-compose.prod.yml` 注释 + `.env.example`）；当前为 `CHANGE_ME_via_kms` 占位。
8. **首次部署验收门**（DEPLOY §1⑤，非建议）：四容器 healthy + `/actuator/health` 200 + 真实登录 200 + `/audit/log-chain` 自检通过。
9. **备份 cron 挂上**（DEPLOY §3）+ 首月内至少一次 `restore.sh` 全流程演练。
10. **防火墙**：只放 80/443 + SSH；SSH 建议密钥登录（DEPLOY §4③）。
11. **轮换预案**：JWT/主密钥轮换预案就位（DEPLOY §4⑤；`DY_MASTER_KEY` 轮换前先读 dy-crypto KEK 文档，不得直接换）。
