## 1. 缺口是什么（含两次自我纠错的探针口径）

RLS 策略形如：

```sql
tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
```

它保护的是**本行的归属**（你写/读的每一行，`tenant_id` 必须等于你的上下文）。
它**完全不保护本行引用的对象归谁** —— 因为外键检查在 PG 内部是以**表所有者**身份执行的，
而 `FORCE ROW LEVEL SECURITY` 对表所有者也生效……**除了**外键/唯一性检查这类由系统内部
发起的操作。实测（真库、应用角色 `diaoyuanyun`、非超级用户）：

```
BEGIN;
  SET LOCAL app.tenant_id = <A>;
  INSERT INTO band (band_id, tenant_id, customer_id, ...) VALUES (<BAND_A>, <A>, <CUST_A>, ...);
  SET LOCAL app.tenant_id = <B>;
  SELECT count(*) FROM customer WHERE id = <CUST_A>;   -- 0  ← RLS 生效，看不见
  INSERT INTO band (band_id, tenant_id, customer_id, vendor, bound_at, status)
  VALUES (<BAND_B>, <B>, <CUST_A>, 'GTL1', CURRENT_DATE, 'active');   -- INSERT 0 1 ← 插进去了
ROLLBACK;
```

**实测规模**：源表与目标表**都** `FORCE RLS`、且外键只引用单列（不含 `tenant_id`）的外键 = **47 处**，
涉及 **12 张**被引用表、覆盖全部 **30 张** `FORCE RLS` 源表。

### 🛑 探针口径的两次自我纠错（值得单独记）

第一次结论是"**跨租户引用不可行**" —— 错的。根因：探针用**应用角色**跑"现存数据里的跨租户引用"检查，
无上下文时 JOIN 两侧都读 0 行 ⇒ **假阴性**。
第二次改用 `postgres` 超管重跑 —— 结论也不可用，因为**超级用户绕过 FORCE RLS**。
第三次同时换两样（**应用角色** + **显式写一行再做 JOIN**），才拿到上面那份真结论。

> 教训：**"用了什么角色 + 有没有设上下文"会翻转同一个查询的结论。**
> 只报告结论而不报告这两项，等于没报告。

## 2. 修法：把 47 处单列外键升级为**租户耦合的复合外键**

```
源表 (tenant_id, customer_id)  →  目标表 (tenant_id, id)
```

前置动作：给 12 张被引用表补 `UNIQUE (tenant_id, <pk>)`（复合外键的**载体**）。

**为什么只增不减、可以放心**：30 张源表的 `tenant_id` 全部 `NOT NULL`
⇒ `MATCH SIMPLE` 下 `tenant_id` 永远参与检查，不会因为"引用列为 NULL 就整体跳过"；
可空引用列（如 `store.region_id`）的 NULL 语义不变。

**三向验证**（缺一条就不足）：
| 方向 | 断言 | 结果 |
|---|---|---|
| 跨租户 | B 上下文里引用 A 的行 ⇒ 必须**被拒** | ✅ 23503 |
| 同租户 | B 上下文里引用 B 的行 ⇒ 必须**成功** | ✅ 通过 |
| 拒绝理由 | 不得是 42501（权限错） | ✅ 是 23503 |

> 第三条是**分水岭**：`42501` 说明是被权限挡住的，不是被约束挡住的 ——
> 那只是"换了个地方失败"，缺口还在。

## 3. 判据缺陷：同一个坑连踩两次

### 3.1 第一次 —— 字符串 LIKE 认**列序**

载体唯一约束若写成 `UNIQUE (id, tenant_id)`（列序不同），外键**依然有效**：
实测跨租户引用**被拒 = t**。但判据 `LIKE '%(tenant_id, %'` **认不出它**（判"无载体" = f）。
⇒ **假阳性**：把一个正确的实现判成错的。

### 3.2 第二次 —— `conkey[1]` 认**位置**

修完第一次后，反向验证的 C3（列序交换的等价形态）报 `(b) = 46（期望 47）`。
根因：我把判据写成了 `conkey[1] = 'tenant_id'` —— **仍是位置判定**。
语义完全等价的 `FOREIGN KEY (customer_id, tenant_id) REFERENCES customer (id, tenant_id)`
做的事和迁移产物一模一样（都要求目标行 `tenant_id` 与源行相同，跨租户**都**被拒），
却被数漏一个。

**修法**：一律改用 `pg_constraint.conkey` / `confkey` 的**列集合**判定 —— 位置无关。
（`unnest(conkey) JOIN pg_attribute WHERE attname = 'tenant_id'`）

> 🛑 **判据可改，期望值不可改。** 两次的正确反应都是修判据 —— 因为缺陷在**仪器**，不在**规格**。

## 4. `(d)` 的次序缺陷：根因断言成了死代码

自证块最初把 `(d)`（"缺载体唯一约束"）排在 `(a)`（"余量 ≠ 0"）与 `(b)`（"复合数 ≠ 47"）之后。
**缺载体 ⇒ 复合外键根本建不起来 ⇒ 必然先触发 (a) 或 (b) ⇒ (d) 永远轮不到报错。**

修法：把 `(d)` **移到本块第一条**，并新增反向验证用例 I4 锁住它：
用 `DROP CONSTRAINT uq_tenant_customer_id CASCADE`（连带摘掉依赖它的外键）
⇒ 若 `(d)` 已前置，第一报错必须是 `自证失败(d)`；若没前置，会报 `(a)` 而用例失败。

## 5. 反向验证（`verification/116_*.py`，9/9）

**核心设计**：注入必须**插在 `$v16_guard$` 自证块之前**。
第一版把注入追加在文件末尾 —— 那时自证块已跑完并成功了 ⇒ I1~I4 全部**假失败**。
这等价于"**考完试再改答案**"。本版用正则把迁移切两半再拼（`inject_before_guard`）。

| 用例 | 注入 | 必须被抓住 | 结果 |
|---|---|---|---|
| C1 | 无 | 原样全绿 | ✅ 9/9 |
| I1 | 一处复合改回单列 | `(a)` 余量 ≠ 0 | ✅ |
| I2 | 删掉一处复合外键 | `(b)` = 46 | ✅ |
| I3 | 抹掉迁移登记 | `(c)` = 0 | ✅ |
| I4 | 摘掉载体（CASCADE） | **(d)**，且必须是 (d) 而非 (a) | ✅ |
| I5 | 迁移后注入跨租户引用 | 数据库拒绝 | ✅ 23503 |
| C2 | 注入同租户引用 | **必须成功**（防一拒了之） | ✅ |
| C3 | 列序交换的等价形态 | 必须仍全绿（防判据误伤） | ✅ |
| C5 | 5 条自证失败分支字面量都在 | 元门禁（防"删了自证也算通过"） | ✅ |

## 7. 🛑 全量回归抓出的真缺陷：迁移探针**越界**了

全量回归 **768 例 / 1 例失败**：

```
ProvisioningBoundaryGateTest.tables_declared_as_not_provisioned_have_no_writer_in_production
```

根因：**V16 自证块 (e) 里有 `INSERT INTO band`**，而 `band` 登记在
"未开通账"里（生产代码零写入方）。

> **门禁是对的，迁移越了界。** 一条"完整性修复"的迁移，不应成为 `band` 这张业务表的
> **第一个写入方** —— 那会把"设备/手环台账无写入方"这条**如实登记的边界**，
> 静默地移动成"有了"。
>
> 🛑 **被放弃的选项**是"把 `band` 加进 `PROVISIONED` 账"：那等于为了让迁移通过
> 而把**账本改成迎合实现** —— 正是本仓反复要防的形态。而且账本改了也没用：
> `band` 的写入方仍只有一个迁移探针，第②例会立刻指出"账本在骗人"。

**修法**：探针换成两端都在**已开通账**里的表对 ——
`store(tenant_id, region_id) → region(tenant_id, region_id)`（`store`/`region`
都已有真实写入方 B-7 组织开通通路）。清场块同步改为"先 `store` 后 `region`"
（外键依赖倒序，写反了会报"在 `region` 上的删除违反了 `store` 上的外键约束"）。

## 8. 🛑 由此得到的第二条硬约束：迁移文本一改，已应用库必须显式处置

改完 V16 文本（自证块 + 注释）后，应用启动立刻炸：

```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 16
```

**这不是新缺陷，而是"改动迁移文本"的必然后果** —— 但此前没有任何东西看着它。
处置纪律（新增）：

> **迁移文本一改，已应用库必须显式处置** ——
> ① 证明"新旧文本的 **DDL 净效果相同**" ⇒ 对齐 checksum（= Flyway `repair` 的语义）；
> ② 承认"效果变了" ⇒ 重建该库 / 补一条**新**迁移（forward-only）。
> 🛑 最坏的反应是"把 checksum 改成新值就完事" ——
> 那等于用一行 `UPDATE` 掩盖一个**未经验证的断言**（"我只改了注释"是**人的记忆**，
> 不是**机器的证据**）。

这项工作被固化成 `verification/117_migration_chain_schema_reconciliation.py`（6/6）：
**已应用库**与**用当前迁移链从零重建的库**逐项对账。

## 9. 🛑 最强的一份证据：一个在 V16 之前写下的门禁**主动叫醒了自己**

全量回归（第三次）里，**既有**测试类 `RlsV7IntakeProfileRevisionIsolationTest`
有两条用例报红。**这不是缺陷，而是本仓最漂亮的一处设计在起作用**：

```java
@DisplayName("V7 修订账本: FK 完整性检查绕过 RLS ⇒ 跨租户 customer 挂载是个【登记缺口】（绿≠安全）")
void foreign_key_checks_bypass_rls_so_cross_tenant_link_is_a_registered_gap() {
    // ...
    // 🛑 若上游决定在库层堵：可选方案是给本表加一条复合 FK
    //    （(tenant_id, customer_id) → customer(tenant_id, id)，需 customer 上有对应唯一约束），
    //    或加触发器。那是一次**契约/字典级**的改动，属待裁定项，故本类只登记、不代拍。
    assertAcceptedInRollbackTxAs(TENANT_B,
        "登记缺口（非缺陷断言）: 库层目前【不】拒绝『本租户的行指向他租户客户』…
        若它变红，说明上游已在库层堵上该缺口（复合 FK / 触发器），
        请同步更新此处登记并收敛应用层防线", …);
}
```

**三重巧合，逐一都对上了**：

1. 它**预告了失败形态**（"若它变红…"）；
2. 它**预告了修法**（"复合 FK `(tenant_id, customer_id) → customer(tenant_id, id)`，需 customer 上有对应唯一约束"）—— 这正是 V16 做的；
3. 它**留下了处置指引**（"请同步更新此处登记并收敛应用层防线"）。

⇒ 一条**缺口登记**用例的正确生命周期：**它必须能被上游的修复叫醒**。
若它永远绿，那它就不是登记，而是一个把缺口伪装成常态的**装饰**。

**按指引做的两件事**：

- **翻转**：`assertAccepted…`（必须成功）→ 三向缺陷断言（必须被 `23503` 拒 +
  拒绝理由**不得**是 `42501` + 反向自证该行未落库）。
  第三条尤其要紧：反向自证必须**切回 B 的上下文**再查 ——
  在 A 的上下文下查 `tenant_id=B` 的行，RLS 会静默过滤成 0 行，
  于是"没落库"与"我看不见"给出同一个 0，反向自证就成了装饰。
- **修一个借用**：另一条用例用 `SEED_B_ID`（**租户 B** 的客户）表达"同租户里的另一个客户" ——
  V16 之后它变成**跨租户引用**而被正当地拒。按其原意改为**自建的同租户第二客户**。
  > 顺手得到一条口径：**"另一个客户"从来就该是同租户的另一个客户，不是另一个租户的客户。**

## 10. 教训清单

1. **角色 + 上下文会翻转结论。** 探针必须同时声明这两项；超管会绕过 FORCE RLS ⇒ 结论不可用。
2. **判据要按"参与"判定，不要按"列序/位置"判定。** 同一个坑本迁移踩了两次（字符串 LIKE → `conkey[1]`）。
3. **判据可改，期望值不可改。** 两次的正确反应都是修仪器。
4. **根因断言必须排在后果断言之前**，否则成死代码（`(d)` vs `(a)(b)`）。
5. **注入必须插在自证块之前**，否则是"考完试改答案"。
6. **门禁自己也要被证明会变红**（116 C5/C6、117 ⑥、门禁第 7 例）。
7. **对账脚本的比较器必须对称。** 117 第一版在计数时没排除 `flyway_schema_history`、
   在 pg_dump 时排除了 ⇒ 凭空多出 1 约束 / 2 索引，**是仪器 bug 不是库的差异**。
8. **迁移不应成为某张业务表的第一个写入方。** 越界写"未开通"表会被门禁正确拦下 —— 此时该改迁移，不该改账本。
9. **缺判据的环节最危险。** "校验和失配"此前无人盯 ⇒ 现在由 117 ⑤ 常驻断言。
10. **注释里写对的原则，必须在【每一处】落实；只写在一处等于没写。**
    门禁用例①的注释完整论证了"为什么必须自建客户而不是复用种子客户"，
    但第一版只把第②步（跨租户）改了，第①步（同租户基线）仍复用种子客户 ⇒
    撞 `uq_band_active_customer`。
    🛑 **而且这个坑只有全量回归能看见** —— 单独跑该门禁类是绿的
    （没有别的测试类先留下 active 手环）。这就是"单类绿"不能当交付证据的原因。
11. **"登记缺口"型用例必须能被修复叫醒**，否则它只是把缺口伪装成常态的装饰（见 §9）。
