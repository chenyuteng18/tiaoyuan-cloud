# 117 · 迁移链模式对账 —— 证据

> 一句话：**已应用库**与**用当前迁移链从零重建出的库**，模式必须逐项相同。
> 这是"对齐 Flyway checksum 是否安全"所需的**全部前提**。
> 日期：2026-09-27 ｜ 脚本：`verification/117_migration_chain_schema_reconciliation.py`（**6/6**）

---

## 1. 它为什么存在（真实事件，不是假想）

V16 迁移在真库应用成功之后，因为一次**门禁驱动的修正**（全量回归抓出
`ProvisioningBoundaryGateTest` 报红：迁移内的行为探针 `INSERT INTO band` 越界写了一张
登记为"未开通"的表），我改了 V16 的文本 —— 改的是**自证块与注释**。

于是应用启动时立刻炸：

```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 16
```

由此得到本仓一条**新的硬约束**：

> **迁移文本一改，已应用的库就必须做一次显式处置** ——
> ① 要么证明"新旧文本的 **DDL 净效果相同**"⇒ 对齐 checksum（Flyway `repair` 的语义）；
> ② 要么承认"效果变了"⇒ 重建该库 / 补一条**新**迁移（forward-only）。
>
> 🛑 最坏的反应是"把 checksum 改成新值就完事"——
> 那等于用一行 `UPDATE` 掩盖一个**未经验证的断言**。
> **"我只改了注释"是人的记忆，不是机器的证据。**

本脚本就是把那句"证明"变成可执行的门禁。

## 2. 六条断言

| # | 断言 | 说明 |
|---|---|---|
| ① | 结构清单逐项相等 | 表 / 列 / 约束 / 索引 / 策略 / **FORCE RLS 表数** / 触发器 / 函数 / 序列 / `schema_migration` 行数 |
| ② | **约束结构指纹**完全一致 | 按 `(表, 类型, 列集, 目标表, 目标列集)` 排序比较 —— 🛑 **不用 `pg_get_constraintdef` 的文本**（文本形态随列序/写法变化，116 已连踩两次） |
| ③ | `schema_migration` 登记逐行一致 | version + description |
| ④ | `pg_dump --schema-only` 归一化后**逐字节**一致 | 兜底：①②③ 没覆盖的东西也逃不掉 |
| ⑤ | **已应用库的 Flyway checksum 与当前迁移文本逐条一致** | 把"有没有忘记处置"变成**常驻断言** |
| ⑥ | **判别力自证** | 往重建库注入一个约束差异 ⇒ 对账必须**变红**；撤销后必须恢复 |

## 3. 🛑 比较器的对称性（第一版就踩了）

第一版报：

```
constraints  已应用=   252  重建=   251
indexes      已应用=   181  重建=   179
```

**看起来像"已应用库多了 1 约束 / 2 索引"** —— 但那是**仪器 bug**：
- 计数那步**没有**排除 `flyway_schema_history`（Flyway 的簿记表）；
- `pg_dump` 那步**排除**了它；
- 而 dev 是 Flyway 建的（有簿记表），recon 是 psql 直建（没有簿记表）。

⇒ **比较器不对称**，凭空造出 1 约束 / 2 索引的差异。
修法：把排除规则集中到一处（`c.relname <> 'flyway_schema_history'`），计数 / 指纹 / dump 全部引用它。

> 教训（本仓第三次同类）：**报差异之前，先怀疑比较器。**
> 一个"两库结构不同"的结论，若无法指认**具体哪个对象**不同，多半是仪器的问题。

## 4. checksum 口径的可信度来自**反验**，不是"看起来对"

Flyway 的 checksum 算法：`CRC32`，**逐行**（不含行终止符）喂入，`UTF-8` 编码，返回**有符号 int**。

本脚本自己复算（`flyway_checksum()`），而不是读 Flyway API —— 因为本仓用**嵌入式 Flyway**
（Spring 启动时执行），对账脚本是独立进程，拿不到那个实例。

**口径怎么确认的**：拿 **V1~V15**（这 15 条自应用后再未改动过）复算，
逐条**命中库中已存值** ⇒ 口径正确。随后 ⑤ 对**全部 16 条**通过，
等于再反验一次 —— 包括刚改过文本的 V16（`checksum = 626314169`）。

> 🛑 若哪天 Flyway 换了算法，⑤ 会整体报错 —— 这本身就是它该做的事。

## 5. 本次处置过程（留档）

1. `117` 跑出 **5/5**（当时还没有 ⑤）⇒ 证明模式相同；
2. `pg_dump --schema-only` 留档到 `_work_backups/dev_schema_before_v16_repair_20260927.sql`（141 KB）；
3. 单事务内 `UPDATE flyway_schema_history SET checksum = 626314169 WHERE version = '16';`（**只动这一列**）；
4. 不重建 dev 库 —— 因为已证明无需重建，而且重建会丢掉 `audit_log` 421 行等测试数据；
5. **最终验收交给全量回归**：仓内 17 个 `@SpringBootTest` 都会真实启动，
   Flyway 会在启动时校验整条链 —— 全部启动成功即证明修复生效（这比任何单元断言更硬）。

🛑 为什么不用 Flyway 官方 `repair`：① 它会清掉**所有**失败记录，而此处只有一个
checksum 失配，范围越小越好；② 本仓没有配置 maven flyway 插件（嵌入式），不存在现成命令可调。
