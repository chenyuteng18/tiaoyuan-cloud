## 2. 🛑 本脚本抓出的四处真实缺陷（全部实测）

### 缺陷 ①（核心）：(b6) 判据可被函数体内 RAISE 消息的【字面量】满足 ⇒ 静默假绿 + 假红 双面失效

**成因**：函数体里那条"跨租户撞号"的 RAISE，其给运维看的解释文本里**逐字**写着
`INSERT ... ON CONFLICT (archive_id) DO NOTHING`。而 (b6) 的初版判据是**裸的**：

```sql
IF v_reg_code !~ 'ON\s+CONFLICT\s*\(\s*archive_id\s*\)' THEN   -- 无锚点
```

**既无锚点、也没剥注释** ⇒ **那条 RAISE 消息的字面量就能满足它**。

**实测**（本脚本 `I(b6-a)` / `I(b6-b)`）：

| 注入 | 修复前 | 修复后 |
|---|---|---|
| 把真 INSERT 改成 `ON CONFLICT (tenant_id, archive_id)`（**错误的**改法，跨租户 RAISE 成死代码） | 判据被 RAISE 字面量满足 ⇒ 自证打印**"通过"**（静默假绿） | 自证报 **(b6)** |
| 把真 INSERT 改成 `ON CONFLICT ON CONSTRAINT case_archive_pkey`（**语义等价的正确**改法） | 判据不匹配 ⇒ **假红** | **全绿** |

⇒ 处置（① + ② + ③）：
① 判据**带锚点**（从 `INSERT INTO case_archive` 起锚、以 `;` 为界）；
② 接受两种语义等价形态（列推断 / 约束名推断）—— 断言的对象是"**推断目标不含 tenant_id**
   这个语义"，不是"某一种语法写法"；
③ 补一条 **(b6-负向)**：锚点段内不得出现含 `tenant_id` 的推断目标
   （正向判据兜不住 `ON CONFLICT (archive_id, tenant_id)` 这种"含主键但也含租户"的写法）。

```sql
IF v_reg_code !~ 'INSERT\s+INTO\s+case_archive\M[^;]*'
               '(ON\s+CONFLICT\s+ON\s+CONSTRAINT\s+case_archive_pkey\M'
               '|ON\s+CONFLICT\s*\(\s*archive_id\s*\))' THEN   -- (b6) 正向（带锚点、双形态）
IF v_reg_code ~  'INSERT\s+INTO\s+case_archive\M[^;]*ON\s+CONFLICT\s*\([^)]*tenant_id' THEN
    RAISE EXCEPTION 'V20 自证失败(b6-负向): ...'               -- (b6) 负向
```

### 缺陷 ②：(e3) 只断言"抛了异常" ⇒ 被库层复合外键（V16 的成果）掩盖 ⇒ 静默假绿

**实测**（本脚本 `I(e3-a)`）：把函数里 (4) 的客户存在性检查改成 `IF false THEN`
⇒ INSERT 落到库层外键 `case_archive_customer_id_fkey` 上 ⇒ 收到 **23503**
⇒ 内层 EXCEPTION 捕获 ⇒ **自证照常"通过"**。

这是本仓最典型的一族形态：**防御纵深把一条函数层判据的失效掩盖了** ——
拒绝仍然发生，只是理由完全不同（**23503 vs P0001**）。后果天差地别：
函数层给的是**可归因**消息（"客户 X 在租户 Y 内不存在" + 实际上下文值），
外键只给一条 23503；且**函数可以被人绕过（直接写 SQL）**，归因质量只能来自函数层。

⇒ 处置：断言 `SQLSTATE = P0001` **且**消息含"客户"。同款补强一并加在
**(e4)/(e6)/(e10)/(e11)**（它们原先也只断言"抛了"）。

```sql
IF v_state IS DISTINCT FROM 'P0001' THEN
    RAISE EXCEPTION 'V20 自证失败(e3): 跨租户客户引用虽然被拒绝了，但 SQLSTATE = %'
                    '（期望 P0001）—— 这说明【函数层的客户存在性检查 (4) 没有生效】...', v_state;
END IF;
IF v_msg IS NULL OR v_msg !~ '客户' THEN ... END IF;
```

🛑 `(e3)` 与 `(e8)` 互补：`(e8)` 断言库层外键必须给 **23503**（V16 的成果），
`(e3)` 断言函数层必须给 **P0001**（本层的成果）。两者**缺一不可**。

### 缺陷 ③：(e2) 幂等重放传入与首次**完全相同**的内容 ⇒ 对 `DO UPDATE SET ...` 毫无反应

**实测**（本脚本 `I(e2-a)` / `I(e2-b)` / `I(e2-c)`）：把
`ON CONFLICT (archive_id) DO NOTHING` 改成

⇒ 处置：第二次调用传入**另一份内容**（6 键清单保持与首次**逐字相同**以隔离变量；
改的是签名人 / 日期 / 结论 / 趋势 / 脱敏授权 / `created_by`），

+ 脱敏开关 + `created_by` + `metrics_trend`）。

🛑 三个变体刻意覆盖"改明显列"到"改最隐蔽列"：
`final_conclusion/staff_signs`（明显）· `metrics_trend`（像"补充说明"）·

### 缺陷 ④：(b8) 判据把"语义等价的谓词书写"判成错（假红）

**实测**（本脚本 `C5`）：`WHERE p_archive_id = archive_id` 在初版判据下报 **(b8)**。

⇒ 处置：判据接受两种等价的谓词书写（断言"**按 archive_id 做等值匹配**"这个语义）：

### C6 判据的精确口径（本轮的修正）

C6 要防的是「整块自证只会在**第一行**报错」—— 即某条注入改错了地方，却因为另一条
**先执行**的判据顺手报了红而被误认为"这条判据有牙齿"。故判据是**双重**的：

1. 每一条注入的**首报错标签**必须**等于它自己的判据标签**（脚本内 `EXPECT` 表）；
2. 除已声明的等价对外，各标签两两互异。

**`b6` / `b6neg` 两条注入同报 `(b6)` 是设计使然**：`ON CONFLICT (archive_id, tenant_id)`
同时违反正向后缀判据与负向判据，而正向判据执行顺序在前 ⇒ 首报错是 (b6)。
（反向"全网互不相同"的朴素判据会误报 —— 这是本轮 C6 首跑的失败项之一，
已改为 `expect_dup_ok = {("b6", "b6neg")}` + `EXPECT` 表。）

## 5. C8：DDL 净效果等价性（本仓"改迁移文本"的处置依据）

本仓纪律（`verification/117` 文件头）：**迁移文本一改，已应用的库就必须做一次显式处置**
—— 要么证明 DDL 净效果相同（⇒ 对齐 checksum），要么承认变了（⇒ 重建库 / 补新迁移）。
**最坏的反应是"把 checksum 改成新值就完事"。**

本轮为修 (b6)/(b8)/(e2)/(e3) 的缺陷改了 V20 文本（**只落在第 4 节自证**，不含 DDL）
⇒ 必须给出"净效果相同"的机械证据。

**净效果口径**（与 118/119/120 一致）= V20 实际产生/改变的四类东西：

1. 函数签名（`proname` + 参数 + 返回类型）
2. **函数体原文**（`prosrc`）—— V20 唯一有内容的产出（两个函数）

## 8. V20 第 5 节已记录、本轮识别但**未修**的边界（诚实）

本脚本**不判**"这些自证是否覆盖了全部业务语义"。以下三条是**已知缺口**，
登记在 V20 第 5 节 / README，须由后续迁移或应用层承担（**不在本脚本的覆盖面内**）：

1. **跨租户撞号在库层无法表达** —— `case_archive_pkey = PRIMARY KEY (archive_id)`
   是**单列全局主键**（不含 `tenant_id`）⇒ 跨租户撞号**必然发生**，
   当前由函数层的 `RAISE EXCEPTION` 兜住（这正是 (b6)/(b7)/(e6) 三条判据守护的语义）。
   🛑 若有人把推断目标改成含 `tenant_id` 的复合形式，该 RAISE 即成**死代码**
   —— 这正是 (b6) 要防的事。
2. **`case_archive` 无 CHECK 约束**（只能靠 RLS 的 `WITH CHECK`）——
   `RlsV5EntityIsolationTest` 用 `archive_checklist='{}'` 探针断言 **42501**，
   ⇒ 库层**不能**加 CHECK 约束（会先于 RLS 报 23514，破坏该探针的归因）。
3. **`latest_archive_of` 的 tie-breaker 语义** —— `ORDER BY archived_at DESC, archive_id DESC`
   在**同一 `archived_at`** 时按 `archive_id` 全序；跨租户不可见由 (c1) 的显式谓词
   + RLS 双保险。

另：`I(b6-c)` 与 `I(b6-c2)` 是**一对**（前者证明正向判据先抓、后者证明负向判据独立有牙）；
`I(e2-a/b/c)` 三个变体故意同报 (e2)（`C6` 的 `expect_dup_ok` 之外的组必须互异，这三条
属于同一判据的三类输入，故同标签是预期的 —— 脚本内已按 `EXPECT` 表核对）。

## 9. 本轮留下的可迁移教训

1. **"判据被字面量满足"比"判据无锚点"更隐蔽** —— 后者至少"哪一处命中说不清"，
   前者是"命中了一处**不是代码**的地方"（RAISE 消息 / 注释），而自证**每次都绿**。
2. **防御纵深会掩盖本层失效** —— (e3) 只看"抛没抛"，就被库层外键的 23503 掩盖。
   ⇒ 行为断言必须断言 **SQLSTATE + 消息内容**，而不只是"抛了"。
   **同一件事的每一层防线都要有独立的判据**（(e3) P0001 / (e8) 23503）。
3. **幂等/重放类用例必须传"对抗性输入"** —— 传相同内容时 `DO UPDATE SET` 与
   `DO NOTHING` 不可区分（静默假绿）。**要证明"没有改写"，就要拿"会被改写的内容"去试。**
4. **判据不得过度收紧（假红也是缺陷）** —— (b8) 把等价的谓词书写判成错，
   会让**正确的重构**报红 ⇒ 断言应锚定**语义**（"按 archive_id 等值匹配"），
   而非**某一种语法写法**。
5. **PG ARE 正则里 `\(` 是字面括号**（不像 PCRE 是分组）—— 要分组必须写**裸 `(`**，
   否则报 `无效的正则表达式: parentheses () not balanced`。
6. **Python 正则不支持 PG 的 `\M`（词尾边界）** —— 诊断脚本须用 `psql` 复现 PG 语义。
7. **注入用例自身也要被核对** —— `I(f2)` 首跑"注入强度不足/形态不对"，伪装成"缺陷未修"：
   只让 `case_archive` 的清场失效，会使 `DELETE FROM customer` 撞上复合外键
   ⇒ 报 23503（**归因错误的红**），执行流走不到 (f2)。**必须整段 no-op。**
   `I(e5-b)` 同族：注入的 RAISE 消息不含自身标签字样 ⇒ 首报错"无标签" ⇒ 假失败。
8. **元门禁的朴素形态可能误报** —— C6 首版要求"全网互不相同"，但
   `b6`/`b6neg` 同报 (b6) 是设计使然 ⇒ 改为 `EXPECT` 表 + 声明式 `expect_dup_ok`。
