## 2. 🛑 本脚本抓出的真实缺陷

### 缺陷 ①（核心）：(c4) 判据被函数体【注释】满足 ⇒ 并发正确性这条判据从未在工作

**成因**：PG 把 `AS $tag$ ... $tag$` 之间的内容**原样**存进 `pg_proc.prosrc`，
**注释也在里面**。V19 的 `deprecate_scale` 函数体注释里逐字写着它自己要做的事：

```sql
--     🛑 谓词里带 `status <> 'deprecated'` 是为了让这条 UPDATE 在并发下**正确**：
--        两个并发废弃都会通过第 (4) 步的读（都读到非 deprecated），
--        若 UPDATE 不带这个条件，两次都会"成功"，第二次的 updated_at 会覆盖第一次的
```

而 (c4) 的初版判据是裸的：

```sql
v_deprecate_body !~ 'status\s*<>\s*''deprecated'''
```

**既无锚点、也没剥注释** ⇒ **删掉代码处那句谓词完全不会被抓住**。

**实测**（本脚本 `I(c4)`）：

| 注入 | 修复前 | 修复后 |
|---|---|---|
| 删掉回归语里那句 `AND status <> 'deprecated'`（代码改动，语法仍合法） | 自证打印**"自证通过"**（静默假绿） | 自证报 **(c4)** |

### 缺陷 ②：(b5) 判据无锚点 ⇒ 2 处代码 + 1 处注释同时命中

`ON\s+CONFLICT` 在 `register_scale` 函数体里有 **2 处代码 + 1 处注释**同时命中
（`raw=3 / code=2`）⇒ 连"**哪一处**满足了判据"都说不清。用例 `I(b5)` 钉住。

### 处置 ①②（同一处置，纯 PL/pgSQL，**不产生任何 DDL**）

把 V19 **已有**的"逐行剥注释"机制（原本只用在 (b1)(b2)(b3) 上）**推广到全部语句形态判据**：

```sql
SELECT string_agg(regexp_replace(ln, '--.*$', ''), E'\n')
  INTO v_register_code
  FROM regexp_split_to_table(v_register_body, E'\n') AS t(ln);

SELECT string_agg(regexp_replace(ln, '--.*$', ''), E'\n')
  INTO v_deprecate_code
  FROM regexp_split_to_table(v_deprecate_body, E'\n') AS t(ln);
```

再在这些**代码态**上匹配，**同时保留锚点**：

```sql
IF v_register_code  !~ 'INSERT\s+INTO\s+scale\M[^;]*ON\s+CONFLICT' THEN          -- (b5)
IF v_deprecate_code !~ 'UPDATE\s+scale\M[^;]*status\s*<>\s*''deprecated''' THEN   -- (c4)
```

🛑 **只剥注释会丢失适用范围，只加锚点仍会被注释命中 —— 两者都需要。**

### 🆕 元门禁 C7 / C7b（把这条教训变成**每次运行都成立**的机械断言）

## 3. V19 相对 V18 的两处特有形态（本脚本的重点）

### (bb)/(b12) 版本冲突对（V18 没有）

- **(bb)** 保证有"版本冲突"的 RAISE 分支；

两者**必须成对** —— 只有 RAISE 而没有那次读，RAISE 会变成**无条件抛错**，

"读回动作在不在"与"分支行为对不对"。

全部建立在"当前角色受 RLS 约束"之上。用例 `I(a0)`（BYPASSRLS 角色）与 `I(a1)`

🛑 **V18 当初就是缺这两条守卫**，导致它在 BYPASSRLS 角色下报出【归因错误】的红

## 5. C6：DDL 净效果等价性（本仓"改迁移文本"的处置依据）

本仓纪律（`verification/117` 文件头）：**迁移文本一改，已应用的库就必须做一次显式处置**
—— 要么证明 DDL 净效果相同（⇒ 对齐 checksum），要么承认变了（⇒ 重建库 / 补新迁移）。
**最坏的反应是"把 checksum 改成新值就完事"。**

本轮为修 (b5)/(c4) 的假绿改了 V19 文本（**只落在第 4 节自证**，不含 DDL）
⇒ 必须给出"净效果相同"的机械证据。

**净效果口径**（与 118/119 一致）= V19 实际产生/改变的四类东西：

1. 函数签名（`proname` + 参数 + 返回类型）
2. **函数体原文**（`prosrc`）—— V19 唯一有内容的产出
3. 函数 `EXECUTE` 权限（第 2 节 GRANT 段的效果）
4. `schema_migration` 中 V19 一行的 `description`（第 3 节登记段的效果）

本轮实测：`before/after 文本长度差 = 557 字符`，**DDL 净效果逐字相同**。

### 🛑 还原函数 `strip_code_normalization()` 踩过的坑（值得记住）

第一版还原用全局替换把 `v_register_code → v_register_body`，**连 `DECLARE` 段那两行
声明也一起改了** ⇒ 还原后的文本里出现两次 `v_register_body text;` ⇒
**PL/pgSQL「重复声明」**，C6 的 before 文本**根本跑不起来**（实测报
`错误: 重复声明 在 "v_register_body" 或附近的`）。

**修法**：还原顺序必须是
① 先用正则删掉 `DECLARE` 段那两行 `v_*_code text;`（含其上说明注释）→
② 再删两条 code 构造语句 → ③ 最后才做 `_code → _body` 改名 →
④ 还原本轮新增的两处锚点 → ⑤ 断言无残留。

🛑 **"还原出的文本必须仍是合法 PL/pgSQL"** 是 C6 的隐含前提 ——
**"净效果比对跑得起来"本身就是一条待证的事**，不是想当然。

### C6b 选点纪律（本轮又踩一次）

C6b 要证明"净效果比对对真实改动有反应"。首跑选的是 **deprecate 的 (5) UPDATE 谓词**
作为篡改点 ⇒ 那处正是 V19 自己 (c4) 判据保护的对象 ⇒ **V19 自身报 (c4)、整条链 apply
失败** ⇒ C6b 变成"测不出来"而不是"测出有反应"。

**修法**：篡改点必须同时满足
① 落在**函数体内**（本比对只看 `prosrc` + 签名 + 权限 + 登记）；
② **不触发 V19 自身的任何一条自证**。
⇒ 改用 deprecate 步骤 (4) 的 SELECT（不被任何 b/c 正则判据覆盖），
加 `AND true` 是语义等价的真实代码改动，行为段 (e7)(e9) 也不受影响。

## 8. V19 第 5 节已记录、本轮识别但**未修**的边界（诚实）

本脚本**不判**"这些自证是否覆盖了全部业务语义"。以下三条是**已知缺口**，
登记在 V19 第 5 节，须由后续迁移或应用层承担（**不在本脚本的覆盖面内**）：

2. **`dimension_set_json` 7 维取值集无 CHECK** —— 本迁移不冻结 7 维
   （探针维度集是 `{"probe":"v19-witness"}`），取值集约束尚未落库。
3. **`reactivate_scale` 未提供** —— 废弃是单向的，没有反向操作原语。

另：`I(e1)` / `I(e6)` 各只覆盖一类注入；`I(b)` 无独立用例
（V19 无 (b2)/(b3) 的独立标签形态差异，由 `C5` 的字面量清单覆盖其存在性）。

## 9. 本轮留下的可迁移教训

1. **「判据被注释满足」比「判据无锚点」更隐蔽** —— 后者至少"哪一处命中说不清"，
   前者是"命中了一处**不是代码**的地方"，而自证**每次都绿**。
2. **处置必须"剥注释 + 锚点"并用**：只剥注释丢失适用范围，只加锚点仍被注释命中。
3. **把一次性检查升格为常驻元门禁**（`C7`/`C7b`）：教训会随人遗忘，机械断言不会。
4. **"净效果比对跑得起来"本身就是待证的事** —— 还原出的文本必须仍是合法 SQL。
5. **改文本与对齐 checksum 必须同一轮做完**，否则"对齐 → 又改 → 失配"往返。
6. **注入强度不足会伪装成"缺陷未修"** —— `I(bb)` 首跑只改了同一条 RAISE 里两处
   字面量中的一处 ⇒ 判据仍成立 ⇒ 假失败。**注入用例自身也要被核对**：
   本脚本已加 `if left_in_raise: raise SystemExit`，把"注入强度"钉成前提。
