为什么这份证据必须放在 src/test/resources/ 而不是 target/
-----------------------------------------------------------
本文件最初只落在 dy-config/target/ 下。target 是构建产物：一次 `mvn clean`
就把它整目录删掉，证据随之消失，而"曾经做过反向验证"这件事将无法举证
（只能靠人记得）。故它必须与源码同源、被版本控制收录。

同一问题在 dy-audit 模块也被独立发现（证明脚本从 target/design-evidence/
迁到 src/test/resources/design-evidence/），两处结论一致。

守护方式
--------
本证据由 ConfigReverseVerificationEvidenceTest 守护：
  · 断言本文件存在于版本化资源目录中，且路径不含 /target/（#1 本文件不被再次挪回 target）
  · 断言生产源码中不残留任何 INJECTION 标记（#2 注入必须被清理干净）
  · 断言配置缓存键仍以 tenant_id 为结构组成部分（#3 注入 2 不能复活）
  · 断言配置 DDL 仍对两张租户表同时具备 ENABLE 与 FORCE ROW LEVEL SECURITY（#4 注入 1 不能复活）

关于 3a 与 3b 的执行顺序
------------------------
3a 注入后，default-test execution 先失败并短路，gate execution 不再有机会运行。
这是 Maven 的正常行为（前一个 execution 失败即中止该模块），不是门禁失效。
为拿到 3b 的独立证据，先把 3a 恢复，再单独注入 3b 重跑。两次注入的失败断言因此
分属不同 execution，上面已分别标注。

哪些Assertion是有牙齿的（自我审视）
===================================
判断标准：如果注入之后测试**仍然绿**，那条断言就是无效的，必须重写。
本次三次注入共触发 11 条失败断言，没有出现"注入了却依然绿"的断言 —— 即
被断言的每一条性质都是承重的。其中三条我认为信息量最高，值得单独记住：

  1) 45 → 90（注入 1）：把"RLS 是否生效"从布尔判断变成一个可核对的**行数**，
     泄漏规模肉眼可见，且必须用非超级用户连接才能得到这个数
     （超级用户本来就不受策略约束，用它测会永远得到 90 并误判为"RLS 没用"）。
  2) M-WX-FG → M-APP（注入 2）：断言具体**值**而非"不相等"，
     于是失败信息直接说明"谁的值污染了谁"，而不是一句抽象的键不等。
  3) 两层各测一次 fail-closed（注入 3）：内存层与真库层是两条独立实现路径，
     只测一层会留下另一层的空洞。

A-1 声明表：45 条、编号集合、#42 缺席
--------------------------------------
  SELECT count(*) AS total_slots, bool_or(config_no = 42) AS has_42 FROM config_slot;
  SELECT array_agg(config_no ORDER BY config_no) AS slot_numbers FROM config_slot;

  +-------------+--------+
  | total_slots | has_42 |
  +-------------+--------+
  |          45 | f      |
  +-------------+--------+

  slot_numbers =
    {1,2,3,...,40,41,43,44,45,46}
  ↑ 41 与 43 之间没有 42。#43~#46 齐备（PRD §10 的 4 条附加项），编号未漂移。

A-2 #42 不可被占用（以非超级用户 dy_app，SQLSTATE 23514）
---------------------------------------------------------
  第一次尝试缺 description 列，先撞 NOT NULL(23502) —— 这说明断言必须把
  所有 NOT NULL 列补全，否则"被拒绝"的原因是错的，会得出假结论。补全后重试：

  INSERT INTO config_slot (config_no, config_key, value_type, allowed_values,
                           forbidden_values, initial_value, prd_item_name, description)
  VALUES (42, 'cfg:injected.test', 'INT', NULL, NULL, '1', '非法占用空号',
          '反向验证：试图复用历史空号');

  错误:  23514: 关系 "config_slot" 的新列违反了检查约束 "config_slot_no_42_stays_vacant"
  DETAIL:  失败, 行包含(42, cfg:injected.test, INT, null, null, 1, 非法占用空号, ...)
  CONSTRAINT NAME:  config_slot_no_42_stays_vacant

  ↑ 空号封死发生在**数据库层**（CHECK 约束），不是靠应用代码判空。
    任何写入路径（应用 SQL、DBA 手工 psql、批量导入）都绕不过。

A-3 RLS 元数据：两张表都 ENABLE + FORCE，owner 是业务角色
---------------------------------------------------------
  SELECT relname, relrowsecurity AS enable_rls, relforcerowsecurity AS force_rls,
         pg_get_userbyid(relowner) AS owner
    FROM pg_class WHERE relname IN ('app_config','app_config_history') ORDER BY relname;

  +--------------------+------------+-----------+--------+
  |      relname       | enable_rls | force_rls | owner  |
  +--------------------+------------+-----------+--------+
  | app_config         | t          | t         | dy_app |
  | app_config_history | t          | t         | dy_app |
  +--------------------+------------+-----------+--------+

  ↑ 关键在 force_rls = t **且** owner = dy_app：owner 自己就是业务角色。
    若没有 FORCE，owner 会绕过策略（实测泄漏 45 → 90，见注入 1）。
    "owner_ok" 这一列的意义正在于此 —— 光看 ENABLE 是会被骗的。

A-4 策略同时约束读写，且用 NULLIF 归一化空上下文
-------------------------------------------------
  SELECT polname, polcmd, pg_get_expr(polqual, polrelid) AS using_expr,
         pg_get_expr(polwithcheck, polrelid) AS with_check_expr
    FROM pg_policy WHERE polrelid IN ('app_config'::regclass,
                                      'app_config_history'::regclass);

  polname = tenant_isolation, polcmd = *（FOR ALL）
  using_expr      = (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true),
                                          ''::text))::uuid)
  with_check_expr = (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true),
                                          ''::text))::uuid)

  ↑ 两个表达式都存在：只有 USING 的话，INSERT/UPDATE 仍能把行写进别的租户。
    NULLIF(...,'') 处理的是"未设置 app.tenant_id 时 current_setting 返回空串"
    这一情形 —— 若不归一化，空串会与 NULL 行为不一致。

A-5 FORCE RLS 对 owner 真实生效（最强的一条）
---------------------------------------------
  以**表 owner dy_app** 连接，不设置任何上下文：
    SELECT count(*) FROM app_config;          →  0
    SELECT count(*) FROM app_config_history;  →  0

  以超级用户 postgres 连接（不受 RLS 约束，作对照）：
    SELECT count(*) FROM app_config;          →  90
    SELECT count(*) FROM app_config_history;  →  99

  +----------------------------------------+----+
  | superuser 无上下文可见 app_config 行数 | 90 |
  | superuser 无上下文可见 history 行数    | 99 |
  +----------------------------------------+----+
  +--------------------------------------------+---+
  | owner(dy_app) 无上下文可见 app_config 行数 | 0 |
  | owner(dy_app) 无上下文可见 history 行数    | 0 |
  +--------------------------------------------+---+

  ↑ 表里确实有 90 行数据，但 owner 自己一行都看不到。这是 FORCE 生效的直接证明：
    策略连表拥有者一并约束。若只看"应用读不到别的租户"，无法区分
    "RLS 生效" 与 "本来就没数据"；这里用 90 vs 0 的对照把两者分开了。

A-6 租户隔离的正向取值（仍以 owner dy_app 身份）
------------------------------------------------
  BEGIN; SET LOCAL app.tenant_id = 'aaaaaaaa-1111-1111-1111-111111111111';
    租户A 可见 app_config 行数                →  45
    租户A 可见 config_no=42 的行数（必须 0）  →   0
  COMMIT;
  BEGIN; SET LOCAL app.tenant_id = 'bbbbbbbb-2222-2222-2222-222222222222';
    租户B 可见 app_config 行数                →  45
  COMMIT;
  BEGIN; SET LOCAL app.tenant_id = 'cccccccc-3333-3333-3333-333333333333';
    未配置租户C 可见 app_config 行数（必须 0）→   0
  ROLLBACK;

  ↑ 每个租户各 45 行（45×2 = 90，与 A-5 超级用户看到的 90 吻合）；
    未配置租户看到 0 行 —— RLS 不区分"租户存在但没配"与"租户不存在"，
    两者都读不到，与 fail-closed 语义一致（读不到 → getRequired 抛 2001）。

附录 C：一个必须知道的坑 —— dy-app 与 dy-config 共用同一个测试库名
==================================================================
`dy-app/src/test/java/.../rls/RlsGateSupport.java:34` 与
`dy-config/src/test/java/.../it/ConfigGateSupport.java:34` 都声明了
`DB = "diaoyuanyun_rls_test"`，且各自的 provision() 都会
`DROP DATABASE IF EXISTS ... WITH (FORCE)` 再重建。

后果：在 `mvn clean package`（反应堆全量）里，dy-app 排在 dy-config 之后执行，
它会把 dy-config 刚建好的配置表整库重建掉。若随后手工连库采集证据，
