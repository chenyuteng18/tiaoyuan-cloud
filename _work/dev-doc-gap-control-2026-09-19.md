## 三、真机验证执行方案（唯一技术未闭环项）

### 3.1 目标
判定 `uniapp SDK → 微信小程序（mp-weixin）` 在**真机**环境下能否完成 BLE 配对与数据读取。**这是 `M-WX-FG` 的生死项。**

### 3.2 前置物料

| # | 物料 | 状态 |
|---|------|------|
| 1 | 厂商 SDK **真包**（非 RAR 占位）| ⏳ 发函索取 |
| 2 | GTL1 手环样机 ×1 | ⏳ 待确认 |
| 3 | 安卓真机（**Android 8+，蓝牙 4.0+**）×1 | ⏳ |
| 4 | 微信开发者工具 + **体验版小程序** | ⏳ |
| 5 | 最小测试工程（见 5.3）| 可立即编写 |

### 3.3 最小验证脚本（**4 步，半天可判定**）

| 步 | 动作 | 期望 | 失败含义 |
|----|------|------|----------|
| **V1** | 小程序内 `wx.openBluetoothAdapter` → `wx.startBluetoothDevicesDiscovery` → 发现 GTL1 | 能发现设备 | 平台层不通 → **M-WX-FG 出局** |
| **V2** | 连接 → `sdk.pair()` → `notify(res.value)` 解包，取 `NotifyType.Pair` | 配对成功 | 协议层不通 → 理论可行但需自研协议层（**+6~15 人日**）|
| **V3** | `sdk.getVersion()` | 返回 `bufferSize: 4000` | SDK 未正确初始化 |
| **V4** | `sdk.getStepHistory({今天})` + **`sdk.getValidHistoryDates(...)`** | 拿到今日步数 + **有效日期数组** | 数据链路不通 |

### 3.4 判定与分岔

```
V1~V4 全通
  → M-WX-FG 成立 → 第 3 批开工 → 用 V4 的 validHistoryDates 实测 N

V1 通，V2~V4 不通
  → 平台可用但 SDK 不可用 → 评估「自研 BLE 协议层」（+6~15 人日）
    或改走厂商通用 BLE GATT（视问询 #9b 答复）

V1 不通
  → M-WX-FG 出局 → 回退 config #44 选项 M-APP（客户装即米 App）
    （回退成本可控，config #44 已保留该选项）
```

### 3.5 额外必测项（一次真机行程全做完）

| # | 测试 | 目的 |
|---|------|------|
| A | **N 实测**：`getValidHistoryDates` 返回的最早日期 → 今天差值 | **直接定 N**（替代厂商问询 #19）|
| B | **`isWear` 无效值**：摘下手环观察返回值 | 验证是否 `-1/255`（问询 #20）|
| C | **A6 无数据语义**：调一个确定无数据的日期 | 看是空数组还是明确标记（问询 #21）|
| D | **A13 强制激活**：**不装即米 App** 直接配对 | 若失败 → M-WX-FG 出局（问询 #22）|
| E | **iOS 对照**：iOS 真机重复 V1 | iOS 授权不可逆，须单独验证 |

> **一次真机行程把这 5 项测完，可一次性关闭 4 条 P0 问询 + 定 N。**

**证据分层（防过度声称）**：
- `exp1-A/B.log` 中 **`pg_advisory_lock` / `pg_advisory_unlock` 返回 `t`** 是 **`02-ensure` 的单连接 reset 锁**（持锁时长约 0ms）。

**Harness 五处缺陷（本轮修复，逐条）**：
1. `local tag="$1" a="$OUT/$tag-A.log"` —— 同一条 `local` 内 `$tag` 读不到刚声明的值，`set -u` 下 `tag: unbound variable` 终止 ⇒ **该 harness 从未跑通**。

4. `pg_locks` 探针**天生看不见**本场景（`pg_try_advisory_lock` 自旋失败不登记等待行）⇒ 用途仅剩"排除阻塞式等待者"，已写明。
5. 判定逻辑原以 `mutex_waited_ms > 0` 为主证据 ⇒ 指标自相矛盾（见上）⇒ **改判据为门禁类耗时差 > 30s**。
