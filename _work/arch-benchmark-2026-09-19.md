### 0.3 对被对标平台的体量校准（这是全篇判断的基准）

**这是本报告最重要的前置判断。** 拿 Slack 的架构去指导一个刚起步的多门店中医 SaaS，等同于拿波音 787 的航电架构去指导造一架农用无人机。下表是校准依据：

| 平台 | 公开的规模量级 **[一手/二手]** | 与调元云的可比性 |
|---|---|---|
| Slack | 千万级 DAU、峰值 400 万并发 WebSocket、峰值 230 万 QPS MySQL、数千台 MySQL 主机（2020 年数据，Slack 工程博客）**[一手]** | 差 4~5 个数量级。**架构结论基本不可直接迁移** |
| Stripe | 约 3000 名工程师 / 360 个团队、每 10 秒产生 5 亿个指标（AWS re:Invent 2023 联合演讲）**[一手]** | 差 4~5 个数量级。**但 API 契约规范可迁移，因为它是"规范"不是"规模产物"** |
| Notion | 2021 年 200 亿 block 行 → 后续 2000 亿+，数百 TB；480 逻辑分片 / 32→96 物理库 **[一手]** | 差 4~5 个数量级。**但其"分片数取值方法论"极有价值且零成本** |
| Shopify | 数万亿级 GMV 平台，限流按 app×store 组合计费 **[一手]** | 差 4 个数量级。**限流模型可借鉴，分值设定不可照抄** |
| Atlassian | 10 万+ 客户迁移至多租户（Vertigo 项目，10 个月无中断）**[一手]** | 差 3~4 个数量级。**其"每租户限连接数"的做法最接近本项目可落地形态** |
| HubSpot | Hublet 多区域 pod 架构改造动用约 1000 名工程师、1 万+ PR **[二手]** | 差 4 个数量级。**明确不适用** |
| Salesforce | 47000+ 组织（该白皮书发布时）**[一手]** | 差 3~4 个数量级。**元数据驱动的"思想"可学，其自研 UDD/多租户内核绝不可仿制** |

> **核心结论（全篇纲领）**：调元云应从这些平台迁移的是**"约束与契约"**（隔离不靠自觉、错误码可编程、契约先于代码、配置可审计可回滚），而**不是"分布式基础设施"**（分片中间件、多区域 active-active、自研多租户内核、微服务网格）。前者成本极低、收益极高、且越早做越便宜；后者是规模驱动的产物，提前引入只会带来灾难。

## A. 多租户隔离模式

### A.1 三大模型的权威定义与取舍

**AWS Well-Architected SaaS Lens**（AWS 官方白皮书，Publication date 2023-04-04，2024/2025 修订版）是多租户架构的权威框架，其明确定义了三种隔离模型。**[一手]**

| 模型 | 机制 | 隔离强度 | 成本曲线 | 典型适用 |
|---|---|---|---|---|
| **Pool（池化）** | 全部租户共享应用与数据库，隔离在逻辑层实现 | 中 | 对数曲线（第 1000 个客户成本远低于第 10 个） | 中小租户、自助注册、绝大多数长尾客户 |
| **Bridge（桥接）** | 按组件混搭，如"池化的 Web 层 + 竖井的存储层" | 中高 | 中 | 成熟平台的实际终态 |
| **Silo（竖井）** | 每租户独立资源（独立库/独立栈） | 最高 | 线性成本 | 有强合规、数据驻留、付费能力的企业租户 |

SaaS Lens 特别强调两点 **[一手]**：
1. 竖井只有在"被共享的身份、入驻、计量、运营所包裹"时才仍然是 SaaS，否则你只是意外地做了一家托管服务公司，且丢掉了 SaaS 的经济性；
2. Bridge 模型的引入是为了承认"SaaS 业务并不总是纯竖井或纯池化"这一现实。

另有权威二手解读指出 Pool 模型可带来 **60%~80% 的基础设施成本节约** **[二手，webkorps]**，以及"一条遗漏的中间件代码就会造成跨租户数据泄漏"的风险本质 **[二手，webkorps]**。

**AWS 官方对竖井的描述补充** **[一手]**：竖井可以是"每租户一个 VPC"或"每租户一组容器"，且**仍可能存在跨租户管理的共享基础设施**。

### A.2 「存储层强制隔离」到底靠什么强制？

这是本项目最核心的诉求（"跨租户查询直接拒绝"）。公开实践中共有四种强制层级，强度递增：

#### 层级 1：应用层自觉（最弱，明确不推荐作为唯一防线）

PlanetScale 官方博客（Postgres 托管服务商，针对 tenancy 的官方观点）**[一手]** 指出：

> "The inherent risk of shared-schema is that every query must include `WHERE tenant_id = ?`."（共享 schema 的根本风险在于每条查询都必须带租户条件）

其建议用 ORM 全局作用域、中间件或统一数据访问层**自动注入**租户过滤条件，而不是依赖每条查询手写。

#### 层级 2：PostgreSQL RLS + FORCE（数据库引擎强制，本项目的答案）

公开的多租户 Postgres 最佳实践给出了完整且可执行的配方 **[一手/二手混合，dfieldsolutions / mydba.dev / fastapi-tenancy 官方文档]**：

```sql
-- 1) 每张租户表必须有 tenant_id，且 NOT NULL
ALTER TABLE <t> ADD COLUMN tenant_id UUID NOT NULL;
CREATE INDEX idx_<t>_tenant ON <t> (tenant_id);   -- 索引是性能前提

-- 2) 启用 + FORCE（关键！）
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <t> FORCE  ROW LEVEL SECURITY;        -- 让表 owner 也受策略约束

-- 3) 策略用 NULLIF 兜底，未设置租户时"静默失败"而非报错
CREATE POLICY tenant_isolation ON <t>
  FOR ALL
  USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);

-- 4) 运行期用 SET LOCAL（事务级），绝不用 SET（会话级）
BEGIN;
SET LOCAL app.tenant_id = '<uuid>';
-- 此处所有 SELECT/UPDATE/DELETE 被引擎自动过滤
COMMIT;
```

**必须知道的 5 个 RLS 失效陷阱**（公开实践已系统总结 **[二手，dfieldsolutions]**，且与 Postgres 官方语义一致）：

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 只 ENABLE 不 FORCE | 表 owner 绕过全部策略 | 必须 `FORCE ROW LEVEL SECURITY` |
| `app.tenant_id` 未设置 | 若不用 NULLIF 则"失败开放"（fail open） | 用 `NULLIF(current_setting(..., true), '')` 实现 fail closed |
| 生产用 superuser 连接 | 绕过 RLS | 应用连接使用非 superuser 专用角色 |
| `SECURITY DEFINER` 函数 | 默认绕过 RLS | 显式标记为 INVOKER |
| `RETURNING *` 无 SELECT 策略 | 静默失败 | 每张表策略覆盖 `FOR ALL` |

**连接池的关键坑（本项目必然踩到）** **[一手 mydba.dev / 二手 dfieldsolutions]**：

> 在 PgBouncer **transaction pooling** 模式下使用 `SET`（会话级）会导致变量残留在被归还的连接上，下一个借到该连接的客户端**继承上一个租户的 tenant_id**——会表现为"RLS 有 bug"，实质是连接池 bug。
>
> **必须使用 `SET LOCAL`**（事务结束即失效）；或配置 PgBouncer 的 `server_reset_query` 执行 `DISCARD ALL`。

**RLS 的边界必须诚实说明** **[一手 mydba.dev]**：

> "Any client that can execute arbitrary SQL can also execute `SET app.tenant_id = 99` and read someone else's tenant. Session-variable RLS is a convenience boundary for a trusted application tier that only ever runs queries you wrote. It is not a defense against an attacker who has raw SQL access to the app role."

即：**RLS 防的是"应用层忘了写 WHERE 子句"和"LLM 生成的 SQL 漏了租户条件"，不防"已拿到数据库账号的攻击者"**。若要防后者，需改为"每租户一个数据库角色 + 基于角色的策略"。

#### 层级 3：Bridge 的 schema-per-tenant

Callista Enterprise 的公开多租户系列（Spring Boot + Hibernate，共 8 篇）**[一手，作者为 Spring 生态知名实践者]** 完整给出了 `MultiTenantConnectionProvider` + `CurrentTenantIdentifierResolver` + 单一 DataSource 装饰 `SET search_path` 的实现，并给出结论：

> Schema-per-tenant 相比 Database-per-tenant 的关键优势是**不需要每租户一个 DataSource**（后者是主要可扩展性瓶颈）。

隔离强度高于 RLS（不会意外跨 schema 查询），代价是 schema 数量膨胀与迁移管理成本 **[二手，hld.handbook.academy]**。

#### 层级 4：CI 强制「租户泄漏测试」（成本最低、收益最高的一个动作）

公开实践给出的具体做法 **[二手，dfieldsolutions]**，原文称"40 行的基础测试文件即可捕获 90% 的策略 bug"：

> 每次迁移（migration）在 CI 中运行"租户泄漏测试"：以租户 A 创建一行 → 切换到租户 B 上下文 → 尝试读取 → **必须返回零行**。对每一张新表都做一次。

#### 反方意见：PlanetScale 官方明确不推荐 RLS **[一手，重要反对意见]**

PlanetScale 官方博客（PlanetScale 是主流 Postgres/MySQL 托管平台）明确写道：

> "We generally don't recommend relying on RLS. It shifts security logic into the database, where policy misconfiguration, silent failures, and connection pooling interactions are difficult to debug. Keep tenant isolation enforced in your application code."

**如何裁决？** 我的判断是：PlanetScale 的反对针对的是"把 RLS 当唯一防线"。它自身的推荐是「应用层注入 + 明确的分区」，而非"不做数据库层约束"。对调元云而言，正确姿势是**三层并存（纵深防御）**：
1. 应用层：统一数据访问层强制注入 `tenant_id`；
2. 数据库层：RLS + FORCE 兜底（防遗漏）；
3. CI 层：租户泄漏测试（防回归）。

三者**任何单独一层都不足**——这一结论在公开实践中被反复强调 **[二手，dfieldsolutions]**。

### A.3 租户上下文的传递机制

**AWS 官方安全博客**（Security practices in AWS multi-tenant SaaS environments）**[一手]** 给出了权威描述：

> SaaS 应用接收到 JWT 后校验并解包，token 中的 claims 构成所谓的 **tenant context**。**就像环境变量可以影响命令行程序一样，tenant context 影响 SaaS 应用如何处理请求。** 使用 JWT 后，应用无需频繁访问外部身份提供方或集中服务即可处理请求。

AWS 官方给出的 tenant context 传递链（以 Cognito 为例）**[一手]**：
- 个体通过 `sub` claim 标识，租户通过 `cognito:groups` claim（或自定义属性）标识；
- 其他 IdP 允许在用户上加自定义属性，从而反映到 access token；
- **关键实践：应用必须校验 JWT 签名（拉取 `.well-known/openid-configuration` 公钥），验证 `iss`/`aud`，然后才可信 token 中的 tenant_id 与 role** **[一手，AWS Builder Center 文章]**。

**AWS 官方点名的红线** **[一手]**：

> **Never trust tenant ID from request body or query parameters. Always derive it from the authenticated token.**
> （永远不要相信请求体或查询参数里的 tenant_id，必须从已认证的 token 推导）

并且建议 tenant context "**should be resolved once, early in the pipeline**"（在管道早期解析一次）并沿层级下传，包括后台任务 **[二手，devessence]**。

### A.4 噪音邻居（noisy neighbor）

**AWS 官方架构博客与 APN 博客**给出了问题定义与解法工具箱 **[一手]**：

> 多租户 SaaS 除了保护系统免受入站流量尖峰影响外，还有额外的**公平性**关切：某个租户的过度流量需要有选择地被限流，而不影响其他租户体验——这就是"noisy neighbor"问题。AWS 自身几乎对所有服务 API 都施加了限流与配额。

AWS 官方解法层级 **[一手]**：

| 层 | 手段 | 说明 |
|---|---|---|
| 边缘 | API Gateway **Usage Plans + API Keys** | Usage Plan 定义阈值，API Key 标识流量归属并映射到对应 Usage Plan；**按租户 tier 分别建 Usage Plan** |
| 配额 | Usage Plan Quota | 按天/周/月设上限，超出返回 **HTTP 429** |
| 计算 | 每租户并发限流 | 如 Lambda reserved concurrency |
| 队列 | 按租户 tier 优先级队列 / 每租户队列 / 公平轮询 | 共享队列中一个租户灌满会拖慢所有人 |
| 数据库连接 | **每租户连接数上限** | Atlassian 的实际做法（见下） |
| 自适应 | 低负载期放宽、竞争期收紧，并尊重 tier 优先级 | AWS Agentic AI Lens 的 Level 4 成熟度 |

**Atlassian 的真实做法（本项目最可参考的一条）** **[一手，Atlassian 官方工程博客]**：

> 为避免 noisy neighbor 问题，我们对每个租户可获得的**数据库连接数**施加了限制。同时还有**每个 JVM 上每租户的连接数限制**。

Atlassian 同时披露了其架构的真实教训 **[一手]**：
- Vertigo 架构（每区域多个租户分片，每分片含 Amazon RDS for PostgreSQL、SQS、EC2 Web 节点、EC2 Worker 节点、ElastiCache for Memcached）；
- **每租户在 RDS 实例上有专属 SQL 数据库**；
- 后续瓶颈正是**数据库连接**：连接耗尽时客户在峰值期间错误率上升，异步 worker 进一步加剧，不得不在峰值期限流 worker。

**AWS 官方还点出一个常见错误** **[一手，Agentic AI Lens AGENTPERF07]**：

> 只在 API 边缘限流，租户会通过长耗时的下游操作绕过边缘限制。
> 且"隔离是被假设的而非被测试的"——微小的变更（新工具、更重的 prompt、流量结构变化）会静默侵蚀隔离边界，只在真实事故中暴露。
> **最佳实践要求定期运行 noisy-neighbor 测试来验证隔离声明。**

### A.5 三大模型对本项目的裁决

调元云的三级结构 `tenant（品牌方）→ region（区域）→ store（门店）` **不是三个租户**，而是**一个租户内部的层级**。这是本项目最容易被误设计的地方，必须点明：

- **租户（tenant）的边界 = 品牌方**。`region` 与 `store` 是租户内的组织维度，用 `tenant_id + region_id + store_id` 三级过滤，**不需要** shard/schema/database 级别的三等分隔离；
- 若把 region 也当租户隔离单元，会立即把逻辑 shard 数放大到"租户数 × 区域数"，而竖井/schema 隔离的成本是线性的——这是典型的"用错隔离粒度把成本曲线从对数拉成线性"。

| 结论 | 分级 | 理由 |
|---|---|---|
| 采用 **Pool（共享库 + 共享 schema + `tenant_id` 列 + RLS FORCE）** 作为唯一隔离模型 | 🟢 **直接适用** | 调元云租户数在可预见未来是两位数到低三位数（连锁品牌方），Pool 的 60~80% 成本优势与运营简洁性是决定性因素；竖井的隔离强度对本项目是过度设计 |
| 存储层强制 = **非 superuser 应用角色 + RLS ENABLE/FORCE + `SET LOCAL app.tenant_id` + NULLIF fail-closed** | 🟢 **直接适用** | 直接对应"跨租户查询直接拒绝"的诉求；失败闭合（返回零行）比抛异常更符合"不返回 404 以避免存在性探测"的安全取向 |
| 租户上下文**一次解析、链路透传**，并**绝不信任请求体/查询参数中的 tenant_id** | 🟢 **直接适用** | 这是零成本的安全红线 |
| 强制使用 **`SET LOCAL`** 而非 `SET`，并配置连接池归还连接时重置 | 🟢 **直接适用** | 本项目必然使用连接池，这是真实泄漏源 |
| **CI 租户泄漏测试（每张新表）** | 🟢 **直接适用** | 成本极低、收益极高，且是唯一能防"策略回归"的机制 |
| **不引入 schema-per-tenant / database-per-tenant** | 🔴 **不适用（明确反对）** | ① 项目 22 实体、租户数少，schema 隔离带来的迁移/管理复杂度收益比极差；② Atlassian 需要它是因为 10 万+ 客户且规模化迁移成本可摊薄，本项目无此规模；③ schema 数量会随租户线性增长，运维负担线性上升，而团队规模不增长 |
| **不采用每租户专属数据库连接池 / 每租户 VPC / 容器组** | 🔴 **不适用（明确反对）** | 这是 Slack（400 万并发连接）、Atlassian（10 万客户）量级才需要的资源隔离；本项目用"每租户连接数上限 + 慢查询超时"即可解决噪音邻居 |
| **RLS 不设为唯一防线** | 🟡 **需改造** | 采纳 PlanetScale 的反对意见：应用层统一数据访问层注入 + RLS 兜底 + CI 测试，**三层并存**。只上 RLS 会形成"以为安全了"的假象 |

> **对本节的一句话建议**：调元云采用「应用层统一注入 + Postgres RLS(FORCE/SET LOCAL/NULLIF) + CI 租户泄漏测试」三层纵深隔离，租户边界严格定义为品牌方（region/store 仅作租户内组织维度），并明确拒绝 schema/库级隔离与每租户专属资源——那是 10 万客户量级的问题，不是你的问题。

## B. 分层与模块边界

### B.1 顶级 SaaS 的实际分层选择（以及一个重要的反直觉事实）

**反直觉事实 1：顶级 SaaS 的"模块边界"常常是组织边界的映射，而非纯粹的技术选择。**

Atlassian 官方工程博客 **[一手]** 坦白：

> 我们从"少量单体代码库"走向"更多分布式系统和服务"时，产生了非预期的复杂度。我们最初在增加新能力时，**难以达到过去的迭代速度与信心**。

并且明确列出微服务的代价 **[一手]**：development sprawl（开发蔓延）、指数级基础设施成本、额外的组织协调开销、调试困难、缺乏标准化、缺乏明确所有权。原文的一句关键判断：

> **"If you are a single product company, microservices may not be necessary."**（如果你是单一产品公司，微服务可能没有必要）

**反直觉事实 2：顶级 SaaS 的多数选择是"先单体多租户化，再渐进分解"，而不是"直接微服务"。**

- Atlassian **[一手]**：Vertigo 的目标是先"从有状态单租户单体 → 无状态多租户云应用"，**再随时间分解为微服务**（"Then we would decompose them over time into microservices"）。该项目迁移 10 万+ 客户、耗时两年、10 个月完成迁移且无服务中断。
- Confluence Cloud 的后续分解 **[一手]**：因为数据库连接成为瓶颈，才把**最昂贵的表**分解为独立服务，且明确以"降低爆炸半径、团队自主权"为动机——**是瓶颈驱动，不是架构审美驱动**。
- Notion **[一手]**：**明确拒绝**走微服务路线。公开解读总结其三条理由：跨服务的分布式事务会复杂化其核心 block 数据模型、保持单体保护了开发速度、其层级内容结构在数据同址时表现更好。**它把全部精力投在持久层的水平分片上。**
- Slack **[一手]**：长期是 PHP/Hack 单体（"The Webapp"），逐步演进。

### B.2 单体模块化（modulith）vs 微服务的公开判据

**Spring Modulith 官方生态的公开判据** **[一手，Spring 官方项目 + 官方作者博文]** 给出了清晰的决策边界：

**适合模块化单体的场景**：
- 团队 5~50 人（不同来源给出 5-20 / 10-50 的区间）**[二手]**
- 业务复杂度中等、有清晰业务边界
- 无专门 DevOps 团队
- 需要低延迟、强一致性（本地 ACID 事务）
- 已有单体需渐进改造

**该考虑微服务的信号**：
- 50+ 开发者，多个独立团队需要独立部署
- 技术异构（不同模块需不同技术栈）
- **部分模块需要独立弹性伸缩（某模块需 100x 而其他持平）**
- 核心模块需要独立的高可用保障
- 团队需要完全独立的发布流水线

**Spring Modulith 的关键机制（这些是可落地的具体能力）** **[一手]**：
- `ApplicationModules.verify()` —— 基于 **ArchUnit**，在**测试期**校验模块之间只能通过顶层包/公开 API 交互，且不成环；**2.0 起新增在应用启动时校验**；
- 模块的 `internal` 子包对其他模块不可见（包私有）；
- `@ApplicationModuleTest` 只启动单个模块的 bean，测试速度远快于 `@SpringBootTest`；
- **Event Publication Registry**：基于数据库的事件发布注册表，保证事件最终被处理（即使服务重启），**在没有 Kafka 的情况下获得可靠性**；
- `@Externalized` 可把内部事件外发到 Kafka，**无需改动事件 schema** —— 这是"从模块化单体平滑迁移到微服务"的迁移路径；
- 从实际代码生成 PlantUML 组件图与 Application Module Canvas 文档，**不会像手绘架构图那样漂移**；
- 2.0 新增模块级 Flyway 迁移。

**一条重要的迁移性判断** **[二手，多方一致，含 Spring 官方生态观点]**：

> **"Extraction is easier than amalgamation."**（拆分比合并容易）——即使你最终需要微服务，从模块化单体拆出去也比从大泥球拆出去便宜得多。所以"先模块化单体"几乎是无风险的默认选择。

### B.3 依赖方向如何"强制"（这是架构能否维持的关键）

**Simon Brown（C4 模型作者）在《Clean Architecture》补章中的核心论点** **[一手，书籍内容；结构对比见公开解读]**：**架构如果依赖开发者自律就会失败；能被执行工具强制的架构才会成功。**

公开解读给出的四种打包策略的强制强度对比 **[二手，luminhkhuong.dev 对书籍章节的转述]**：

| 打包策略 | Java 强制力 | 风险 | 说明 |
|---|---|---|---|
| Package by Layer（按层分包） | **无** | 高 | 任何类可调用任何类；改一个功能要动多个包；架构从结构上看不出来 |
| Package by Feature（按功能分包） | **无** | 中 | 功能改动局部化、架构更可见，但功能间仍可互相直调 |
| Ports and Adapters（六边形） | **弱** | 中 | 领域层被隔离，但 Java 不阻止领域层反向 import 基础设施 |
| **Package by Component（按组件分包）** | **强（包私有）** | 低 | 组件只暴露一个公开接口，实现类为包私有，**编译器强制边界** |

**Spring Boot 官方生态的推荐组合** **[一手，Spring 官方博客系列]**：
- 主包的直接子包视为**模块**；
- 模块只能通过**顶层包**互相访问，不得形成环；
- 模块间用**事件**通信（`ApplicationEventPublisher`），而非直接方法调用——**事件用于副作用与最终一致性；直接调用用于查询与强事务不变式**；
- 用 `ApplicationModules.verify()` 或 ArchUnit 把规则**变成测试**，进 CI。

**ArchUnit 的实战注意事项** **[一手，loiane.com 实测]**：
- 在"按功能分包"的代码库里，**包名规则无法区分层次**，必须改用**命名约定**做层次标记（如 `*Service` 不得依赖 `*Controller`）；
- **Surefire 3.5.3 存在 bug（TNG/ArchUnit#1442）会导致 @ArchTest 字段规则静默不执行** —— 表现为构建全绿但 `Tests run: 0`。必须核对 `Tests run` 计数，而不只看构建颜色。这是一个非常实用的踩坑提示。

### B.4 对本项目的裁决

调元云的客观条件：**已有 22 实体数据字典、三端接口契约、46 条非空可配置项（#1–#48）**，且业务方已拍板 Spring Boot 3。团队规模未在任务背景中给出，但从"单产品 + 一个架构规格书 + 一个骨架工程"的任务编排看，**处于早期**。

| 结论 | 分级 | 理由 |
|---|---|---|
| **采用模块化单体（modular monolith）**，并按 **Package by Component / 按领域分包 + 包私有 + 公开门面** 组织 | 🟢 **直接适用** | ① 与 Spring Boot 3 天然匹配；② 22 实体、单产品，微服务的"独立伸缩/异构技术栈/独立发布"收益全部不存在，而分布式事务、调试、运维成本全部立刻发生；③ Atlassian 官方自己说"单一产品公司微服务可能没必要" |
| **模块边界按领域切分**（建议：租户与身份、门店与组织、客户与档案、调理服务与判定、评估与基线、设备与体征数据、配置与元数据、计费与计量、审计与合规） | 🟡 **需改造** | 需结合 22 实体数据字典做一次真实的领域聚类；不要照搬任何对标平台的模块划分 |
| **依赖方向强制**：`web → application → domain ← infrastructure`（领域层零框架依赖），**用 ArchUnit / `ApplicationModules.verify()` 落成 CI 测试** | 🟢 **直接适用** | 这是"约束与契约"类收益，成本极低而长期回报极高。Simon Brown 的论点直接适用：不靠自律，靠工具 |
| **模块间通信：同步直接调用用于查询与强事务不变式；事件用于副作用**（如"判定完成"触发"基线更新"、"体征异常"触发"通知"） | 🟢 **直接适用** | 与 Spring Modulith 官方建议一致 |
| **使用 Spring Modulith 的 Event Publication Registry 替代引入 MQ** | 🟡 **需改造** | 优点：无 Kafka/RocketMQ 运维成本即可获得事件可靠性。但需评估其"事件表"对 22 实体库的侵入，以及本项目 append-only/可回放要求是否与之冲突（见 D 节） |
| **不引入微服务** | 🔴 **不适用（明确反对）** | ① 团队规模与产品形态不匹配（微服务的收益门槛是 50+ 开发者、多独立团队）；② 调元云有强 ACID 诉求（判定结论、协议快照、基线评估的一致性），拆成微服务会立刻把本地事务变成 Saga；③ 22 实体规模下，微服务只会让一次功能改动同时触碰 3~5 个仓库与 N 条流水线；④ Atlassian 的公开反思（迭代速度下降、开发蔓延、缺乏标准化）是对照抄者最直接的警告 |
| **不引入 Kubernetes / 服务网格 / 自研 PaaS** | 🔴 **不适用（明确反对）** | Atlassian 有"Micros"自研 PaaS、HubSpot 有 Hublet 体系，这些是千人工程师量级才能摊销的平台投资。本项目用一个可复现的容器化部署 + IaC 即可 |
| **不做多区域多活（active-active）** | 🔴 **不适用（明确反对）** | 见 F 节灾备部分 |

> **对本节的一句话建议**：调元云走「模块化单体 + 按组件分包（包私有强制边界）+ ArchUnit 进 CI + 事件解耦副作用」，并用 Spring Modulith 的单模块测试与文档生成提升可维护性；**明确不做微服务**——Atlassian 官方已承认微服务让单一产品公司的迭代速度下降，这不是你可以提前承受的成本。

## C. API 设计规范

### C.1 版本化策略

**Stripe 的版本化模型**（行业标杆，官方文档）**[一手]**：

- 采用 **日期 + 命名主版本**格式：如 `2024-09-30.acacia`、当前 `2026-08-26.dahlia`，格式 `YYYY-MM-DD.release_name`；
- **每月的次版本只含向后兼容变更**，可安全升级；**每年两次的主版本（如 Acacia、Dahlia）含破坏性变更**；
- 通过 **`Stripe-Version` 请求头**指定版本；使用**组织级 API Key** 的请求必须带该头；
- **每个账户被固定（pinned）在其创建时的 API 版本**，因此 Stripe 发布新版本时既有集成**不会静默破坏**；
- 从 `2024-09-30.acacia` 起采用的实现方式：**响应先生成于当前资源定义，再沿时间"向后回退"依次应用版本变更模块，直到响应符合账户所固定的版本** —— 这样旧版本成为固定的维护成本，而不是散落在核心代码路径里的死分支 **[二手，digitalapplied 对该机制的转述；Stripe 官方确认了版本固定与升级语义]**；
- **主版本升级后有 72 小时回滚窗口** **[二手，digitalapplied 引用 Stripe 升级文档]**；
- 兼容性定义（官方明确列举）**[一手]**：新增 API 资源、新增可选请求参数、新增响应属性、改变响应属性顺序、改变不透明字符串的长度/格式（含增删固定前缀）、新增事件类型 **均属向后兼容**；
- 官方明确警告：**不要假设开放枚举（open enum）的值是穷尽的**，代码必须有安全兜底分支；对象 ID 最长达 255 字符，MySQL 中存 `VARCHAR(255) COLLATE utf8_bin` **[一手]**。

**GitHub 的版本化模型** **[二手，digitalapplied 引用 GitHub 官方]**：同样采用日期版本，通过 `X-GitHub-Api-Version` 头；**每个版本在更新版本发布后至少支持 24 个月**；无头请求默认落到指定旧版本；请求已过期版本返回 **410 Gone**。

**版本化策略的工程权衡**（公开决策矩阵）**[二手，netguru / digitalapplied]**：

| 策略 | 示例 | 优点 | 缺点 |
|---|---|---|---|
| URI 路径 | `/v2/payments` | 显式、CDN 缓存天然分键、易于网关路由、日志可见 | 违反 REST 资源标识原则；消费者需改 base URL |
| Query 参数 | `?api-version=2` | 不需重构 URL | **部分 CDN 会忽略 query 参数的缓存键**，导致版本塌陷 |
| Accept 头 | `Accept: application/vnd.api+json;version=2` | URI 干净、符合 HTTP 内容协商 | 工具支持弱；网关需显式配置；**若无 `Vary` 头会缓存污染** |
| 日期版本 | `2026-03-10` | 精确、可排序、直接映射 changelog | 需配套支持窗口政策 |

另有一致性建议：**无论选哪种主策略，`Sunset` 头都应出现在所有 API 设计中**，把弃用契约写进 HTTP 响应本身 **[二手，netguru]**。

> **本项目已定 `/api/v1`**，即 URI 路径版本化。这一选择对本项目的合理性 🟢：三端（小程序/APP/Web）消费方多样且部分不可控（小程序发版滞后），URI 版本化的"显式 + 缓存友好 + 日志可见"是最务实的。**建议补充 `Sunset` 头与明确的版本支持窗口政策**（🟡）。

### C.2 幂等键（本项目必须有）

**Stripe 的幂等实现（事实标准）** **[一手]**：

- 通过 **`Idempotency-Key` 请求头**传递，客户端生成；
- 键**最长 255 字符**；官方建议用 **V4 UUID** 或其他高熵随机串；
- **官方明确警告：不要用敏感数据（如邮箱、个人标识）作为幂等键**；
- 语义：保存第一个请求的**状态码与响应体**，无论成功还是失败；**后续同键请求返回相同结果，包括 500 错误**；
- **键的有效期 24 小时**（公开实践普遍以 Stripe 的 24 小时为惯例基准）**[一手 Stripe + 二手多源一致]**。

**边界情形的公开最佳实践** **[二手，restguide / kokil.com.np，但内容与 Stripe 官方行为一致]**：

| 情形 | 处理 |
|---|---|
| 并发同键请求（第一个未完成） | 用原子锁（如 Redis `SET key NX EX`），未抢到锁者返回 **409 Conflict** |
| 同键不同请求体 | 返回 **400 / 422**，明确报错（Stripe 返回 400） |
| 存储内容 | 只存状态码与响应体，**不存响应头**（含请求相关值如 Date） |
| 重放标识 | 返回 **`X-Idempotent-Replayed: true`** 头，便于客户端与排障 |
| 过期 | 24 小时 TTL + 夜间清理任务 |
| 监控 | 观测 `duplicate_key_replays`、`conflict_409_rate`；409 突增往往意味着客户端发布回归了重试逻辑 |
| 安全 | 键**不可猜测**（禁止顺序整数），必须与 token 鉴权配套 |
| 关键的语义红线 | **首次失败后的重试必须重放相同的 400/500 响应**，不得"因重试而静默成功"（除非 API 契约显式允许纠正流程） |

**关于标准化的现状**：公开资料提到 **IETF 正在推进 `Idempotency-Key` 头的标准化草案** **[二手]**。我未能核实该草案当前状态，**公开信息未明确其是否已成 RFC**。

**Shopify 的 webhook 幂等** **[一手，Shopify 官方文档/官方生态指南]**：
- Shopify **保证至少一次投递（at-least-once）**，因此处理器**必须幂等**；
- 使用 **`X-Shopify-Webhook-Id` 头**作为去重键，存储已处理的 webhook ID 并跳过重复；
- 非 2xx 响应会触发指数退避重试，**最长 48 小时**后移除订阅；
- 通用建议：webhook 处理器应将提供方的 event ID 存为**唯一索引**，重复时返回 200 让发送方停止重试。

### C.3 错误码体系

**Stripe 的错误响应结构（行业最被推崇的设计）** **[一手，结构描述见 apidog 对其官方文档的整理，字段与 Stripe 官方文档一致]**：

```json
{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds.",
    "param": "source",
    "doc_url": "https://stripe.com/docs/error-codes/card-declined",
    "request_log_url": "https://dashboard.stripe.com/logs/req_xxx"
  }
}
```

**其设计要点（可迁移性极高）**：
- `type` + `code`：支持**程序化分支处理**；
- `decline_code`：更细的具体原因；
- `message`：**可安全展示给终端用户**；
- `param`：**指出是哪个字段导致的**（对表单类客户端极有价值）；
- `doc_url`：直达排障文档；
- `request_log_url`：一键跳转请求日志。

**Shopify 的一个反面案例值得注意** **[一手]**：GraphQL 被限流时**返回 HTTP 200，但响应体内含 `THROTTLED` 错误码**；而 REST 被限流时返回 **429**。这是一个真实存在的"同一平台两种限流信号"的不一致，提示我们：**错误信号必须在一开始就统一设计，否则后期无法纠正**。

**本项目已有错误码表 1001~9001 与统一响应信封 `{code,message,data,trace_id}`**。逐项对标后：

| 建议 | 分级 | 理由 |
|---|---|---|
| 保留信封 + 错误码表 | 🟢 | 已定，且与"三端契约统一"诉求一致 |
| **补充 `param`/字段级定位能力**（即使放在 `data` 内） | 🟡 | 表单类客户端（小程序）体验直接受益，Stripe 证明其价值 |
| **补充 `doc_url`（错误码 → 文档锚点）** | 🟡 | 成本极低；本项目三端 + 外部集成方多，能显著降低支持成本 |
| **`trace_id` 与请求日志可跳转** | 🟡 | 本项目信封已有 `trace_id`，建议配套一个内部日志检索入口，形成"Trace ID → 日志"闭环（Stripe 的 `request_log_url` 思路） |
| **绝不像 Shopify 那样让同一语义有两种信号** | 🟢 | 本项目错误码表已统一，务必坚持"限流也走统一错误码"，不要在不同端出现 429 vs 200+码 的混用 |
| **`message` 必须做用户可展示性审查** | 🔴→必须 | **本项目存在"客户端一个字都不许出现『退款』"的合规红线**。Stripe 的 `message` 设计假定"可安全展示给用户"，但本项目的服务端错误消息**必须先过合规词表**，否则会把红线词直接送到小程序界面上 |

> **这条是本项目与所有对标平台最大的差异点，必须单独立规**：对标平台的错误消息是"技术向用户友好"的单目标优化；调元云的错误消息是**双目标**——技术可用 + 合规安全。建议建立"错误码 → 客户端文案"的**独立映射层**，服务端 `message` 永不直出客户端（🟢 强建议）。这与"同一 APP 内不同角色可见字段不同、服务端裁剪"的既有原则一脉相承。

### C.4 分页与限流

**分页** **[一手，Stripe 官方 + 二手整理]**：
- Stripe 使用**游标分页（cursor-based）**：`GET /v1/charges?limit=10` 返回 `{data, has_more, url}`，下一页用 `starting_after=<最后一条 id>`；
- 优点：数据变动时**不会跳过或重复**、无需数据库 count offset、实现简单；SDK 提供自动翻页；
- 通用建议：游标应为**对稳定且有索引的列的引用**（UUID 或 `created_at` + 打破平局的 tie-breaker）；响应含 `next_cursor`，`null` 表示末页；
- **明确警告**：对高频写入资源使用 offset 分页会产生难以调试的不一致结果集。**[二手，netguru]**

**Shopify 的分页硬限制（值得参考的"显式封顶"思路）** **[一手]**：
- 数组分页上限 **25,000 个对象**，超过此深度应改用过滤器收窄；
- **count 查询也受此限制**：超过 25,000 时返回 25,001 作为"超过 25,000"的信号；
- 数组入参最大 **250 个元素**（所有 API 一致）。

**限流：Shopify 的令牌桶/漏桶 + 按次计费模型（本项目最值得借鉴的模型）** **[一手]**：

- **GraphQL Admin API 按"计算出的查询成本"限流**，不是按请求数；
- 成本按字段计算：标量=0、枚举=0、对象=1、接口=取可能选择的最大值、联合=同上、Connection=按 first/last 参数计、Mutation=10；Shopify 保留手动指定字段成本的权利；
- **桶同时按 (app × store) 组合授予**：同一 store 上不同 app 互不影响；同一 app 对不同 store 互不影响 —— **这是天然的多租户友好设计**；
- 桶容量与恢复速率**按 store 的付费计划**：
  - Standard 100 points/秒；Advanced Shopify 200；Shopify Plus 1000；Enterprise 2000；
  - Payments Apps API 27300 / 54600 / 109200；
- **漏桶（leaky bucket）**：配额持续补充，短时突发可接受，只要平均成本低于恢复速率；
- **单次查询硬上限 1000 points**（无论计划），在执行前基于"请求成本"强制；
- **成本区分 requested 与 actual**：执行前桶内必须有足够容量支付 requested cost；执行完成后**按 requested 与 actual 之差退还**；
- 响应内含节流状态，客户端可**主动降速**：

```json
"extensions": {
  "cost": {
    "requestedQueryCost": 101,
    "actualQueryCost": 46,
    "throttleStatus": { "maximumAvailable": 1000, "currentlyAvailable": 954, "restoreRate": 50 }
  }
}
```

- 调试：请求头 `Shopify-GraphQL-Cost-Debug=1` 可拿到逐字段成本明细；
- **资源型限流**：store 超过 500,000 个产品变体后，每日新增变体上限 10,000，超出返回 **429**（Plus 计划除外）；
- **官方明确立场**：由于 Shopify 有时需要强制限流防滥用，**应用应对所有端点都做好限流处理，而不仅是文档中列出的端点**；
- **REST 版本**：漏桶容量 40、泄漏率 2/秒；响应头 **`X-Shopify-Shop-Api-Call-Limit: 32/40`** 暴露桶的实时水位；
- 官方对应用的要求：**使用业界标准技术来限流调用、缓存结果、负责任地重试**。

**重试策略的公开推荐** **[二手，多源一致]**：指数退避 + 抖动（jitter）；base 500ms~1s；上限 30s；连续多次失败后记录并告警。核心原则：**在服务故障时立即全速重试会叠加放大负载**。

### C.5 契约优先（contract-first）流程

**公开的完整落地配方** **[二手，但工具链与做法在业界高度一致，且引用的是各工具的官方行为]**：

1. **`openapi.yaml` 作为唯一真相源，先写后实现，并提交入版本库**；
2. **设计与实现必须在同一次 PR 中同步更新契约**（防止漂移）；
3. **CI 四道闸门（按成本从低到高排序，前一道失败不跑后一道）**：
   - **Lint**：Spectral（或 Redocly）按规则集校验规范，可自定义规则编码组织约定；
   - **破坏性变更检测**：`openapi-diff` / **`oasdiff`** 对比 PR 分支与基线分支，**不兼容即失败**；
     - 破坏性（失败）：删除端点、删除必需的响应字段、新增必需的请求字段、收窄枚举取值；
     - 兼容（放行）：新增可选字段、新增端点、扩展枚举取值、新增可选 query 参数；
   - **validate**：`openapi-generator-cli validate` 校验规范完整性；
   - **漂移检查**：重新生成类型并 `git diff --exit-code`，**若生成的类型与提交的规范不一致则失败** —— 保证"不能只改规范不改生成物，也不能只改生成物不改规范"；
4. **Mock 服务器**（Prism）供消费方在实现完成前联调；
5. **生成客户端 SDK**（`openapi-generator`），让客户端与服务端共享同一契约词汇表，**类型不匹配在编译期而非生产期暴露**；
6. **消费者驱动契约测试（Pact）** 作为补充：OpenAPI 校验结构兼容，Pact 校验**行为**兼容，两者覆盖不同维度；
7. **弃用管理**：在操作上用 `deprecated: true` 标记，给出由规范背书（而非仅靠邮件通知）的 sunset 时间线；
8. **常用禁忌（公开列出）** **[二手]**：规范事后补写、示例缺失、过度使用枚举、泄漏内部字段/主键/堆栈、**没有错误契约**（客户端因此脆弱）、无版本化的 base URL。

**需要注意的批评声音** **[二手，asoasis]**：契约优先的代价是"设计评审前置"和 CI 门禁的初始投入；迁移应采用渐进路线（先生成初始规范 → 冻结 v1 → 上 CI 门禁 → 逐步扩展），并对破坏性变更**批量归入计划好的主版本发布**。

### C.6 对本项目的裁决

本项目已定：`/api/v1`、统一信封 `{code,message,data,trace_id}`、错误码表 1001~9001。

| 结论 | 分级 | 理由 |
|---|---|---|
| 保留现有信封与错误码表，**补 `param`/字段定位 + `doc_url`** | 🟡 | 三端体验与支持成本双收益 |
| **落盘 OpenAPI 契约并纳入 CI 闸门（Spectral lint + oasdiff 破坏性检测 + 生成物漂移检查）** | 🟢 **直接适用** | 本项目"三端接口契约"已存在，把它**变成可执行的门禁**是本报告性价比最高的一条建议。尤其"三端发版节奏不同"这一现实，使自动破坏性检测的价值远高于一般项目 |
| **`Idempotency-Key` 头 + 24h TTL + 409 并发 + 400 载荷不符 + `X-Idempotent-Replayed`** | 🟢 **直接适用** | 本项目存在"判定结论/协议快照/基线评估等 append-only 不可覆盖数据"，一次重复提交若产生重复判定记录，将直接破坏"判定依据可回放"的语义。**幂等键不是可选优化，是正确性要求** |
| **错误消息与客户端文案解耦（服务端 message 不直出客户端）** | 🟢 **必须** | 合规红线（"退款"等词客户端一个字都不许出现） |
| **分页采用游标分页** | 🟡 **需改造** | 建议对 append-only 型数据（判定记录、审计日志、体征时序）用游标分页；对稳定的配置类小集合可保留 offset+total 以便前端展示总页数。**混合策略需在契约中显式区分** |
| **限流：按租户 tier 分级 + 漏桶 + 响应内暴露节流状态（可主动降速）** | 🟡 **需改造** | Shopify 的模型方向正确，但**其分值（100/200/1000 points 每秒）与单查询 1000 点上限完全不可照抄**——那是万亿级 GMV 平台的标定。本项目应先用"每租户 X 请求/秒 + 突发容量 Y"的简单双参数起步，并在响应头暴露水位（学 Shopify 的 `X-Shopify-Shop-Api-Call-Limit` 思路） |
| **提前定义并测试限流路径** | 🟢 | Shopify 官方的教训："应对所有端点做好限流处理，不仅是文档列出的" |
| **不使用 GraphQL** | 🔴 **不适用（明确反对）** | Shopify 的按成本限流、单查询 1000 点上限、requested vs actual 退还是 **GraphQL 特有的复杂度**。本项目 `/api/v1` REST + 三端契约 = 更简单、更可控、更容易做字段级裁剪（本项目"同一 APP 内不同角色可见字段不同"用 REST + 服务端 DTO 裁剪比 GraphQL schema 裁剪更直接） |
| **不采用日期版本化** | 🔴 **不适用（明确反对）** | Stripe/GitHub 的日期版本化是为"消费方极度多样且长期不可控的外部平台"设计的，其代价是**永久维护多个历史版本的响应生成逻辑**（Stripe 需要"向后回滚应用版本变更模块"的机制）。本项目三端均为自研可控，`/api/v1` + `Sunset` 头 + 明确支持窗口已足够 |

> **对本节的一句话建议**：把已有的三端契约从"文档"升级为"CI 门禁（Spectral + oasdiff + 漂移检查）"，并**优先把幂等键做进所有 append-only 数据的写路径**——因为对判定结论/协议快照这类不可覆盖数据，重复提交不是性能问题而是数据正确性问题；同时建立服务端 message → 客户端文案的独立映射层以守住"退款"合规红线。

## D. 可观测性

### D.1 三支柱的构成与各自职责

公开的工程共识给出了清晰的职责边界 **[二手，cloudnative-tech / bitloops，内容与业界一致]**：

| 信号 | 回答什么问题 | 设计重点 | 常见风险 |
|---|---|---|---|
| 指标（Metrics） | 是否异常、趋势如何、是否需告警 | **低基数标签**、统一命名、稳定采集 | 标签过多导致存储与查询成本失控 |
| 日志（Logs） | 具体发生了什么、错误上下文 | 结构化字段、请求 ID、错误码、**脱敏** | 无级别、无上下文、**敏感信息泄漏** |
| 链路（Traces） | 请求经过哪些服务、瓶颈在哪 | Trace ID、Span 命名、关键依赖覆盖 | 采样策略不当导致关键请求缺失 |
| 事件（Events） | 最近发生了什么变更 | 发布、配置、扩缩容、故障切换记录 | 只记录结果，不记录操作者与原因 |

**统一标签的关键约束** **[二手]**：先统一**服务名、环境、版本**三类标签；再补团队、地域、集群、**租户**。但"**标签越多越灵活，也越容易带来基数膨胀**" —— 建议**从排障必需字段开始**。

> **这条对调元云至关重要**：Metric 上的 `tenant_id` 是一个**高基数标签**。若把 tenant_id 直接打进指标标签，随着租户增长会导致时序库爆炸。行业做法是：**指标上不直接放 tenant_id，而把租户维度下钻交给日志与 Trace**；或对租户级指标做独立聚合与限额。

**日志的脱敏红线** **[二手]**：生产日志必须避免输出明文 Token、手机号、身份证号、连接串；错误日志应含可定位的错误码、请求标识与关键上下文，**但不要把整段请求体无控制地打印**。

### D.2 SLO / SLI / SLA 的定义惯例

公开惯例（多源一致）**[二手，bitloops 等]**：

| 概念 | 定义 | 示例 |
|---|---|---|
| **SLI**（指标） | 对服务质量的**测量** | "API 延迟 P99 是 100ms"、"错误率 0.1%"、"数据新鲜度 < 1 分钟" |
| **SLO**（目标） | 对 SLI 的**内部目标** | "API 延迟 P99 应 < 100ms"、"错误率应 < 0.5%" |
| **SLA**（协议） | 对客户的**承诺，违反需赔付** | "我们保证 99.9% 可用性"、"P99 < 500ms" |

**误差预算（error budget）的算法与用法** **[二手]**：

> SLO 99.9% 可用性 → 误差预算 0.1% × 525600 分钟/月 ≈ **52.5 分钟/月** 的允许停机。
> 用法：**预算耗尽则冻结高风险发布；预算充裕则可承担更大风险。**

**SLO 设计流程（公开推荐）** **[二手，cloudnative-tech]**：
1. 先选**用户旅程**（登录、下单、支付、查询、模型推理等核心路径）；
2. 定义 SLI（成功率、P95 延迟、误差预算消耗、队列等待时间）；
3. 设定 SLO 目标与**统计窗口**（7 天 / 30 天 / 业务活动周期）；
4. 约定**误差预算消耗后的动作**（冻结高风险发布、扩容、修复依赖、降级）；
5. 将 SLO 与告警、复盘、发布策略**关联**，而不是只放在报表里。

公开批评 **[二手]**：若只按单实例 CPU/内存或接口 200 状态码告警，会忽略用户真正关心的"交易是否成功、页面是否可用、核心接口是否在可接受时间内响应"。

**告警疲劳** **[二手]**：对策是少量高信噪比告警、智能分组、配套 runbook、超时未响应则升级。

### D.3 分布式追踪的租户维度

**AWS 官方给出的多租户可观测实践** **[一手，re:Invent 2025 相关内容]**：

> 当函数启用 JSON 格式日志时，Lambda **自动把 tenant ID 注入每条日志条目**，无需手工埋点。
> 由于执行环境是租户专属的，**每个 CloudWatch 日志流属于单一租户**，可按 tenant ID 过滤 Live Tail，或用 Logs Insights 按时间窗口查询某租户的日志流。
> 对于自定义指标，**AWS Lambda Powertools 支持为指标发射添加 tenant 维度**。

**AWS Agentic AI Lens 的成熟度要求** **[一手]**：
- Level 1：**没有每租户遥测**，噪音邻居效应与 SLA 违规只在客户投诉后才发现；
- Level 3：**每租户看板**跟踪消费与 SLA 合规；
- Level 4：**对每租户的限额接近度与 SLA 违规告警**；
- Level 5：**每租户的成本与性能报告给租户面看板**。

### D.4 审计日志的不可篡改性

**这是本项目合规要求在架构上的最直接投影**（append-only / 判定依据可回放）。公开工程实践给出了完整配方 **[二手，techinterview.org / auditboard / hyrelog / aplindo，多源一致]**：

**技术手段（按强度递进）**：
1. **仅追加表（append-only）**：**撤销所有用户（包括应用服务账号）对 audit_log 表的 UPDATE / DELETE 权限** —— 应用只能 INSERT。**即使应用被攻破也无法删除日志**；
2. **哈希链（hash chaining）**：每条记录包含前一条的哈希，`entry_hash = SHA256(prev_hash + event_data)`。任何一条被修改或删除，后续所有哈希失效。校验方式为**重算整条链**；
3. **写入外部隔离系统**：复制到独立隔离的系统（**启用 Object Lock 的专用 S3 桶**、WORM 存储）；主数据库无法触及该系统；
4. **数字签名**：按批用服务私钥签名，用公钥验证；修改即失效。

**审计日志必须记录的最小字段** **[二手]**：`event_id`、`timestamp`（含时区、毫秒精度）、`actor_id`、`actor_ip`、`actor_user_agent`、`action_type`（LOGIN/LOGOUT/CREATE/UPDATE/DELETE/EXPORT/**VIEW_PII**）、`resource_type`、`resource_id`、`outcome`（SUCCESS/FAILURE/UNAUTHORIZED）、`request_id`、**`before_state`（JSON 快照）**、**`after_state`（JSON 快照）**。

**几个非常关键的具体要求** **[二手]**：
- **认证事件要同时记录成功与失败登录**（失败模式可检测暴力破解）；
- **对敏感数据的只读访问也要记录**（HIPAA 对 PHI 访问有明确要求 → **对本项目的心率/血氧/睡眠等 PIPL 敏感个人信息同样适用**）；
- **审计日志必须与应用程序日志分离存放**：应用日志是运维性的（debug/warn/error），审计日志是合规级的（谁访问了什么），两者**保留期、访问控制、完整性要求都不同**；
- 对非授权查看者**做 PII 掩码**，只有合规官与安全工程师可见完整 PII；
- 安全事件（多次失败登录、批量导出、管理员授权）应触发实时 SIEM 告警。

**存储与检索架构** **[二手]**：审计日志**写多读少**（只在调查或审计时查询），应**为写优化**：
- PostgreSQL 仅追加 + **按月分区**（旧分区归档到冷存储，不影响活跃写性能）；
- Elasticsearch 用于调查期的全文与过滤查询（按 actor_id / resource_type / 时间范围），经 CDC（Debezium）从主库同步；
- S3 + Athena 归档分区 Parquet 用于合规导出。

**保留期（公开的监管地板值）** **[二手]**：
- **中国等保（三级）：日志留存不低于 6 个月；医疗行业实践要求不少于 12 个月** —— 见下节；
- PCI DSS v4.0：12 个月（其中至少 3 个月可立即获取）；
- SOC 2 / ISO 27001：通常 1 年；
- HIPAA：6 年；
- EU AI Act 第 12 条：高风险 AI 系统部署者至少保留 6 个月日志；
- SEC 17a-4：要求 WORM 存储。

**跨租户的组织方式** **[二手，hyrelog]**：可选择集中式账本或按租户分散账本；决策依据包括多租户要求、数据驻留约束、查询性能、合规隔离、故障边界。**集中化简化调查，分散化增强隐私与隔离，许多平台两者结合。**

**"审计日志必须能在租户删除后继续存活整个保留期"** **[二手]** —— 这一条与 PIPL 的删除权存在真实张力，必须在设计里显式裁决（见 E 节）。

### D.5 对标 Stripe 的可观测性规模（反面参照）

**AWS re:Invent 2023 联合演讲（Stripe 工程）** **[一手]**：
- 规模：**约 3000 名工程师、360 个团队、每 10 秒产生 5 亿个指标**；
- 为应对该规模，Stripe 做了**五类架构改造：分片（sharding）、聚合（aggregation）、分层存储（tiered storage）、流式告警（streaming alerts）、隔离（isolation）**；
- 并强调"建立自给自足（self-reliance）的文化，让用户容易实施有效的可观测实践"。

> **这份数据本身就是一个警告**：Stripe 需要"分层存储、聚合、隔离"来支撑可观测性，是因为其指标量级是"每 10 秒 5 亿"。调元云若照抄这套架构，成本会全部沉在基础设施上，而真正的业务价值（判定正确性、合规可回放）一分未增。

### D.6 对本项目的裁决

| 结论 | 分级 | 理由 |
|---|---|---|
| 三支柱齐备：结构化日志 + 指标 + 链路，**统一服务名/环境/版本标签** | 🟢 **直接适用** | 成本低、收益直接 |
| **指标上禁止把 `tenant_id` 作为标签**（高基数） | 🟢 **必须** | 本项目租户数会增长，指标基数爆炸是低成本就能避免的陷阱。租户维度下钻交给日志与 Trace |
| **审计日志与应用程序日志物理分离** | 🟢 **直接适用** | "判定结论/协议快照/基线评估 append-only 且可回放"这一约束，本质上就是审计级需求。混在应用日志里将无法满足不可篡改与长保留期 |
| **审计日志：仅追加表 + 撤销 UPDATE/DELETE 权限 + 哈希链 + 定期校验端点** | 🟢 **直接适用** | 直接支撑"判定依据可回放"。哈希链与 `evidence_snapshot` + `threshold_version` 的既有设计天然互补 |
| **审计日志按月分区 + 冷归档** | 🟢 **直接适用** | 写多读少，分区是 Postgres 上成本最低的长期方案 |
| **必须记录敏感个人信息的"只读访问"** | 🟢 **必须** | 心率/血氧/睡眠属 PIPL 敏感个人信息；等保与医疗行业实践均要求记录访问行为 |
| **关键业务事件的 before/after 快照** | 🟢 **直接适用** | 这是"判定依据可回放"的实现基础 |
| **日志脱敏（手机号、身份证、连接串、Token）** | 🟢 **必须** | 合规要求 + 日志留存期长会放大泄漏后果 |
| **定义 3~5 个以用户旅程为中心的 SLI/SLO + 误差预算策略** | 🟡 **需改造** | 方向适用，但目标值必须自定。建议围绕"调理师 APP 核心路径""客户小程序核心路径""判定链路正确率"设定，而非笼统的可用率。**注意：医疗健康场景中"判定正确率"比"接口 200 率"更接近用户价值** |
| **Trace 中携带 tenant_id（但仅在有采样控制时）** | 🟡 **需改造** | 租户维度追踪有价值，但需配采样策略，否则 Trace 存储同样会被高基数拖垮 |
| **不引入 Stripe 式的分层存储/聚合/隔离体系** | 🔴 **不适用（明确反对）** | 那是"每 10 秒 5 亿指标"量级的方案。本项目应先用一套标准可观测栈（日志 + 指标 + Trace），把租户维度做进日志与审计，避免过早复杂化 |
| **不引入独立 SIEM** | 🔴 **不适用（明确反对）** | 多源建议的实时 SIEM 告警适用于有专职安全运营团队的规模。本项目可用"审计日志 + 关键事件告警规则"覆盖 |

> **对本节的一句话建议**：把"审计日志"当作一等公民独立建设（独立表/独立权限/哈希链/按月分区/长保留期/记录只读访问与前后快照），这直接承载了本项目"append-only 可回放"与 PIPL/等保的双重合规诉求；同时坚持指标上不放 tenant_id 标签，用日志与 Trace 承载租户维度。

## E. 安全合规

### E.1 多租户下的认证：JWT vs Session

**AWS 官方立场** **[一手]**：以**签名 token**（JWS/JWT）表示身份；token 由 IdP 签名，可**无需查询集中式数据库或服务即可校验**；token 内的 claims 构成 tenant context；**使用 JWT 后，应用可处理请求而无需频繁引用外部 IdP 或集中服务**。

**AWS 官方的 JWT 安全要求** **[一手，AWS Builder Center]**：
- **必须校验签名**（从 `.well-known/openid-configuration` 拉公钥），证明未被篡改；
- **校验 `iss`（签发者）与 `aud`（受众）**；
- 校验通过后，才可信任从 payload 解出的 `tenant_id` 与 `role`；
- **绝不让下游（含 AI Agent）自行"推断"租户与角色** —— 必须从已校验的 JWT 读取，因为推断易受注入/冒充攻击。

**AWS 官方的 ABAC 进阶方案** **[一手，AWS Security Blog]**：通过 `AssumeRoleWithWebIdentity` API + JWT 中的 `https://aws.amazon.com/tags` claim，把租户 ID 映射为**会话标签**，换取**租户作用域的临时凭证**；IAM 角色策略用 `aws:PrincipalTag` 变量限制访问。这使"共享基础设施 + 租户隔离"由云平台强制而非应用自觉。

**多租户 IdP 的组织方式（公开三种模式）** **[二手，dev.to]**：
1. **共享用户池 + Groups**：所有租户在一个池，租户成员关系用 group；简单但隔离有限；
2. **共享用户池 + 自定义属性**：租户 ID 作为自定义属性；**适合多数场景**；
3. **每租户一个用户池**：隔离最强但运维复杂度高，仅考虑给企业租户。

**共享池的三个真实陷阱** **[二手]**：
- "全局邮箱问题"：共享池中邮箱必须全局唯一，同一邮箱无法在租户 A 与租户 B 同时注册 → 修复：**用 `sub`（UUID）作为主标识，租户特定档案存自有数据库**；
- **自定义属性数量上限（如 Cognito 25 个）**：不要把租户元数据浪费在这里 → **只存 tenant_id，其余（角色、权限、偏好）存应用数据库**；
- 租户差异化的 IdP/密码策略需求 → 需要用 App Client 或"单元化（Cell-based）"架构。

### E.2 租户级密钥与字段级加密

**公开的合规架构实践** **[二手，bindbee / gbest / dchost，多源一致]**：
- 行业实践基线：**静态数据 AES-256、传输 TLS**，覆盖服务间通信、API 调用、数据库连接；
- **多租户环境下，客户专属的密钥管理（per-tenant encryption key）能加强数据隔离**；
- **按租户分离密钥**是"技术隔离"从"行级"上升到"加密级"的手段。

**等保 2.0 三级对加密的具体要求（中国语境）** **[二手，测评服务机构文章，非官方标准原文，需项目侧向合规机构确认]**：
- **传输加密**：敏感数据采用 **TLS 1.2 及以上**，禁用弱加密套件，杜绝明文传输；
- **存储加密**：患者信息、身份证、手机号等核心数据，要求采用**国密 SM4 算法加密存储**；
- **数据防泄漏**：支持敏感数据识别、**动态脱敏**、外发管控，杜绝批量导出、私自拷贝、越权查看明文数据。

> ⚠️ **诚实标注**：SM4 等具体算法要求来自**测评服务机构的技术解读文章（二手）**，我未能核验《信息安全技术 网络安全等级保护基本要求》标准原文的具体条款。**建议本项目在架构定稿前由合规/等保测评机构确认加密算法要求**，不要以本报告作为合规依据。

### E.3 数据主体权利（PIPL 删除/导出）如何在多租户架构中落地

**这不是"做两个接口"的问题，而是一个跨存储的系统工程。** 公开实践的核心洞察 **[二手，hld.handbook.academy 等]**：

> 用户的个人数据并不存在于单一数据库中，而是分散在：主存储、只读副本、搜索索引、缓存、特征库、数仓、ML 训练集、可观测性日志、CDC 管道、备份、第三方处理方。

**"软删除"（`deleted_at = now()`）在上述每一处都留下数据。监管者将删除权解读为"删除"，而非"在查询中隐藏"。**

**唯一能穿透不可变备份与仅追加日志的模式：Crypto-shredding（密钥销毁）** **[二手，多源一致，机制清晰]**：

1. 写入时，用**每主体（per-subject）的数据加密密钥 DEK** 加密其 PII 字段；
2. DEK 存入 KMS（采用信封加密：用 KEK 包裹 DEK）；
3. 收到删除请求时，**销毁 DEK**；
4. 密文仍存在于所有备份、副本、事件日志中，但**在计算上不可恢复**；
5. **一次 KMS 操作即完成彻底删除。**

对**事件溯源（Event Sourcing）**系统的适配 **[二手]**：把 PII 放在可被 crypto-shred 的事件载荷内；非 PII 字段（事件类型、时间戳、聚合 ID）保持明文以便重放与分析。删除时销毁密钥，事件日志结构完整但 PII 已消失。

**删除 DAG 的拓扑要求** **[二手，重要且易被忽略]**：

> 删除流程必须覆盖**每一个衍生存储**：搜索索引、缓存、特征库、数仓、日志、第三方处理方，**全部确认删除后**才销毁源 DEK。这个拓扑顺序可防止后续重放把已不可解密的密文重新灌回衍生存储。

**必须直面的失败模式** **[二手，原文明确警告]**：

> Crypto-shredding 有一个关键失败模式：**如果因操作失误（而非有意销毁）丢失了 DEK，用户自己的数据就不可恢复了。** DEK 的备份与访问控制必须与数据本身同等严格。

**密钥粒度选择** **[二手，oneuptime]**：每用户一把（隔离最强、管理开销最高）/ 每组一把（按租户、区域、群组分；删除单个用户需为余下用户重新加密）/ **每记录一把 DEK，用用户级 KEK 包裹（多数系统最实用）**。

**多租户下的实操模式** **[二手，dchost]**：
- **中心身份映射表**：一张表把主体（用户）映射到其在**每个租户**下的全部数据位置；
- 对"立即硬删操作上复杂"的数据，用**软删除 + 周期性清理任务**；
- **租户作用域导出端点**：把某用户全部数据打包为单个可下载归档，**按 tenant_id 过滤**。

**关于备份** **[二手，dchost]**：GDPR 通常**允许**在不可变备份归档中保留已删除数据至配置的保留期，前提是该数据不再被主动使用并将按计划清除；**关键是能清晰解释并记录这一行为**。

### E.4 PIPL 的具体要求（中国语境，本项目的主合规框架）

**PIPL 对敏感个人信息的定义** **[一手，法律条文，多源转述一致]**：生物识别、宗教信仰、特定身份（身份证号）、**医疗健康**、金融账户、行踪轨迹、**不满 14 周岁未成年人**的个人信息。

> **本项目的项目心率/血氧/睡眠数据明确落入"医疗健康"类别 → 构成敏感个人信息。**

**处理敏感个人信息的加重要求** **[一手，PIPL 第 28~30 条、第 55 条]**：
- 具有**特定的目的和充分的必要性**；
- 取得**单独同意**（第 29 条）；
- **事前告知**处理的必要性及对个人权益的影响（第 30 条）；
- 开展**个人信息保护影响评估（PIPIA）**（第 55 条）。

**个人权利** **[一手，PIPL 第 44~49 条]**：知情决定权、查阅复制权、更正补充权、**删除权**（处理目的已实现/撤回同意/违规处理时）、解释说明权、可携带权。

**跨境传输** **[一手，PIPL 第 38~40 条]**：
- 三种机制之一：**CAC 安全评估 / 标准合同并备案 / 认证**；
- 需**单独同意**并告知接收方名称、联系方式、目的、方式、数据类型，以及行使权利的方式（第 39 条）；
- **本地化门槛**：处理个人信息达 **100 万人以上**，或自上一年 1 月 1 日起累计向境外提供 **10 万人以上**个人信息，或 **1 万人以上**敏感个人信息的处理者，须境内存储，出境需 CAC 安全评估 **[二手转述 CAC 门槛，规则随法规更新，需项目侧核实]**。

**罚则** **[一手]**：最高 **5000 万元人民币或上一年度营业额 5%**；可责令暂停/终止服务、吊销业务许可；**对责任个人的罚款与任职限制**。

**实践合规步骤（公开归纳）** **[二手]**：评估义务 → 开展 PIPIA → 选择传输机制 → 实施技术控制（加密、访问控制、**审计记录所有数据访问与传输**、数据分类分级）→ 建立境内代表。

### E.5 等保 2.0 三级的具体要求（中国语境）**[二手，需复核]**

来自等保测评服务机构的技术解读（**非标准原文**）：

- **日志留存不低于 6 个月**；医疗行业实践要求**不少于 12 个月**；
- **审计日志不可篡改、不可删除**，记录登录/查询/修改/删除/导出行为，含操作时间、源 IP、操作人员、操作内容；
- **三级系统每年测评一次**，备案后 30 日内提交材料；
- **三级必须搭建统一安全管理中心**（全网设备状态监测、风险集中告警、日志统一汇总、策略统一调度）；
- **堡垒机**管控所有运维操作、全程录屏审计；
- 每半年至少一次应急演练，留存记录；
- 核心数据**本地实时备份 + 异地容灾备份**；每日自动备份、**每月测试数据恢复能力**。

**PIPL 与等保的关系（本项目需要同时满足）** **[二手，归纳]**：等保是"网络安全底线"（定级备案 + 定期测评 + 基础部署 + 日志留存 + 应急演练）；PIPL 是"数据合规核心"（分级防护 + 权利响应 + 合规评估 + 跨境评估）；《数据安全法》是"配套保障"（分类分级 + 授权可追溯 + 最小权限 + 留存操作日志）。

### E.6 对本项目的裁决

| 结论 | 分级 | 理由 |
|---|---|---|
| **认证采用 JWT（access token 携带 tenant_id + role），且必须校验签名/iss/aud，绝不信请求体中的 tenant_id** | 🟢 **直接适用** | AWS 官方红线，零成本 |
| **服务端按角色裁剪字段（已有原则），并把"裁剪后的 DTO"作为唯一出口** | 🟢 **必须** | 本项目已确立"服务端裁剪，非前端不渲染"。建议在契约层把"同一端点的不同角色响应 schema"显式化，避免裁剪逻辑散落 |
| **租户级密钥（per-tenant DEK）+ 信封加密** | 🟡 **需改造** | 方向正确。但需先确认：本项目是否需要"租户级密钥"还是"主体级密钥"？**若目标是响应 PIPL 删除权，则必须是主体级（per-subject）**——租户级密钥无法删除租户内的单个用户。建议：**每主体 DEK + 用租户级 KEK 包裹**，兼顾删除权与租户隔离 |
| **字段级加密用于敏感个人信息（心率/血氧/睡眠）** | 🟢 **直接适用** | PIPL 敏感个人信息 + 等保存储加密要求双重驱动 |
| **Crypto-shredding 作为删除权的实现机制** | 🟡 **需改造（强烈建议评估）** | 与本项目最契合：**"判定结论/协议快照/基线评估 append-only 且可回放"意味着数据不会被物理删除**，那么"(以密文形式) 永久留存 + 销毁密钥"是唯一能同时满足"可回放"与"被遗忘权"的机制。**但必须配套 DEK 备份与访问控制的极高纪律，否则会出现"密钥丢失 = 用户自己的调理记录永久不可读"的灾难** |
| **删除 DAG：列出全部衍生存储并逐一确认** | 🟡 **需改造** | 本项目需先做一份数据地图：主库、备份、日志/审计、缓存、检索索引（若有）、数仓（若有）、消息留存 |
| **中心身份映射表（主体 → 各租户下的数据位置）** | 🟢 **直接适用** | 这是 multip-tenant 下响应删除/导出请求的必备基础设施，越早建越便宜。**本项目有三级结构，映射表须能表达 tenant/region/store 三级归属** |
| **租户作用域的数据导出端点（按 tenant_id 过滤，打包归档）** | 🟢 **直接适用** | PIPL 查阅复制权 + 可携带权；同时服务 B 端客户的数据导出诉求（合同解约时的数据返还） |
| **审计日志记录所有敏感个人信息访问** | 🟢 **必须** | PIPL 实践要求 + 等保要求 |
| **合规红线：客户端"退款"一词一个字不出现** | 🟢 **必须** | 建议实现为**编译期/构建期扫描**（前端词表检查进 CI），而非仅靠代码评审——参考 ArchUnit 的"不靠自律靠工具"原则。同时服务端 message 与客户端文案解耦（见 C.3） |
| **暗色数据/影子数据清理** | 🟡 | 公开实践指出常见泄漏源在非生产环境：staging 误用生产库、把生产快照复制到 dev 且未脱敏、分析系统聚合多租户数据而无充分掩码。对策：**dev/staging 使用独立数据库 + 仅加载脱敏或合成数据** |
| **不引入 CAC 安全评估 / 标准合同 / 认证的完整流程（若不出境）** | 🔴 **条件性不适用** | 若调元云数据全部境内存储且不出境，则第 38~40 条的出境机制**不触发**。但**本地化义务与 PIPIA 仍适用**。**这一点必须在架构定稿前由合规方确认**（若使用境外云服务或在境外做运维访问，则可能触发"跨境"） |
| **不引入每租户独立用户池 / 每租户 IdP** | 🔴 **不适用（明确反对）** | 共享池 + tenant_id 自定义属性已满足本项目；每租户池的运维复杂度对两位到三位数租户规模是纯负担 |
| **SM4 等具体算法要求** | ⚠️ **待确认** | 来源为二手，**必须由等保测评机构确认后再写入架构规格书** |

> **对本节的一句话建议**：把"敏感个人信息 → 每主体 DEK + 字段级加密 + crypto-shredding 删除"这条链路作为架构的一等公民，因为它同时满足"判定数据 append-only 可回放"与"PIPL 删除权"这两个看似矛盾的约束；同时立刻建立"主体 → 各租户下数据位置"的中心映射表与数据地图，并把"退款"红线做成构建期扫描而非人工评审。

## F. 商用关切

### F.1 计费与用量计量

**AWS SaaS Lens 的成本/计量最佳实践（官方，两级问题）** **[一手]**：

**SaaS COST1：如何度量单个租户的资源消耗？** 三个递进层次：
1. **近似消耗**：用一个简单指标（如请求数）做近似分配，人工与账单关联，得到粗略的每租户成本；
2. **构建丰富的消耗视图**：对应用各资源分别计量并归属到租户，聚合后得出详细估算；
3. **用消耗洞察驱动运维与架构效率**：把消耗数据用于运营与架构团队，引入策略分析并改进多租户系统的成本效率。

**SaaS COST2：如何把租户消耗与基础设施成本关联？**
1. **人工聚合**：工具收集聚合某期成本数据，人工与租户消耗关联，算出每租户成本；
2. **自动化关联**：自动化机制获取成本数据并与租户消耗分配关联，确定每租户成本，**支持更实时的成本趋势评估**。

**AWS 官方的明确态度** **[一手]**：

> 缺乏这一能力会导致对租户实际活动缺乏可见性，进而无法把租户消耗与资源使用对齐，难以做出相关决策。**应当从运营 SaaS 方案的第一天起就努力建立对该方面的良好理解。**

**实践层面的计量维度（公开归纳）** **[二手，danguisinger]**：
- API 调用次数（CloudWatch 自定义指标或专用计量服务）；
- 计算时长（Lambda duration、容器任务时间）；
- 存储（对象大小、数据库行数）；
- 数据传输（响应体大小）；
- **共享成本的分摊模型**：按用量比例分摊（最准确）/ 均摊（最简单）/ 按 tier（企业租户承担更多）/ 混合（直接成本直接归属，共享成本按用量分摊）。

**计量 → 计费的公开参考实现** **[二手，hld.handbook.academy 案例]**：
- 用量事件从应用层流入 Kafka，**按 tenant_id 分区**；
- ClickHouse 消费者按 event_id 去重后追加到租户分区表；
- **夜间对账任务聚合用量，带幂等键推送 meter event 到 Stripe**。

> **注意**：该案例的"Kafka + ClickHouse + Stripe 计费对账"是完整商业计费系统的参考，其复杂度远超本项目当前需要。

### F.2 配额与限流

见 C.4（Shopify 漏桶与成本计费）与 A.4（AWS tiering/throttling）。

补充一条**官方的重要技术警告** **[一手，AWS 官方博客]**：

> **API Keys 只是简单标识符，不是授权令牌或加密密钥。API Keys 仅用于限流与配额管理，不适合作为安全机制。**

这条对本项目有直接意义：**若为限流引入 API Key 概念，绝不能把它当鉴权手段**。

**AWS 官方的 tiering 与 throttling 是"业务策略"而非纯技术手段** **[一手]**：

> 限流与配额也可以是企业策略的一部分，允许 SaaS 提供方创建不同的 tiering 策略，为不同客户与角色提供不同体验。这些 tier 与定价选项让客户按需与预算选择。**预测事务速率与容量的能力帮助 SaaS 提供方让支撑基础设施的成本与客户需求对齐。**

### F.3 SLA 承诺与赔付

**公开的定义惯例** **[二手]**：SLA 是对客户的合同承诺（如"保证 99.9% 可用性"、"P99 < 500ms"），**违反时客户可获得赔付**；SLO 是内部目标；SLI 是测量值。（定义见 D.2）

> 我没有找到可信的一手资料说明主流 SaaS 平台**具体的赔付比例与条款结构**（例如"未达 99.9% 返还月度费用的 X%"）。**这部分公开信息未明确**，若本项目的投资人材料或销售赋能需要，建议直接引用目标客户的采购标准或参考公开可查的服务条款原文，而不要以本报告为依据。

**Atlassian 的真实 SLA 事件值得引为教训** **[一手，Atlassian 官方事后复盘（2022 年 4 月故障）]**：

> 该次事件中，**我们未达到 RTO，但达到了 RPO。**

这句话的信息量很大：**RTO 与 RPO 是两个独立的指标，"备份存在"不等于"能在承诺时间内恢复"**。官方复盘还明确了两个概念的定义：
- **RTO（恢复时间目标）**：灾难中数据能多快恢复并返还给客户；
- **RPO（恢复点目标）**：从备份恢复后数据有多新、自上次备份以来会丢多少数据。

**另一个公开的警示** **[二手，cloudandclear]**：

> 恢复区域在生产运行后，往往收到的更新更少、密钥轮换滞后、黄金镜像陈旧、IAM 策略漂移。**一个 18 个月前测试过热身备站、之后没再测过的组织，应当假定它无法达到其声明的 RTO。**
> **RTO（目标）与 RTA（实际达成）之差才是真正重要的，而多数组织从未测量过后者。**

### F.4 灾备 RTO / RPO 惯例值

**AWS Well-Architected Reliability 支柱定义的四种 DR 策略及其 RTO/RPO**（多源一致，均引用 AWS 权威文档）**[一手框架 / 二手具体数值]**：

| 策略 | RTO | RPO | 成本 | 适用 |
|---|---|---|---|---|
| **Backup & Restore** | 一整天或更多（小时级） | 小时级 | 最低（无待机计算） | Tier-3：内部工具、批处理报表、归档系统 |
| **Pilot Light** | 数十分钟 | 分钟级 | 低（仅数据库层常驻复制） | Tier-2：有真实压力但非即时的中型 SaaS |
| **Warm Standby** | 分钟级 | 秒级 | 中（全天运行缩放版） | 金融/医疗等有严格 SLA 的平台 |
| **Multi-site Active/Active** | 近零 | 近零 | 最高、最复杂 | 全球平台、大型市场、交易系统 |

**公开的 tiering 惯例值** **[二手，多源一致]**：

| Tier | RTO | RPO | 示例 |
|---|---|---|---|
| Tier 1 关键 | **< 15 分钟** | 近零 | 支付处理、核心 SaaS 平台 |
| Tier 2 业务关键 | **1~4 小时** | **< 1 小时** | ERP、CRM、内部 API |
| Tier 3 重要 | **12~24 小时** | **< 24 小时** | 预发环境、报表系统 |
| Tier 4 非关键 | **48~72 小时** | **< 72 小时** | 开发/测试、归档 |

**公开指出的最大预算错误** **[二手]**：**把所有系统都归类为 Tier 1**。组织常因多年前的风险评估勾选而多花 3~5 倍于必要的 DR 预算。建议**每年结合实际业务影响数据复核 tier 划分**。

### F.5 多环境与灰度

**公开的推荐做法** **[二手，多源一致]**：
- **多环境必须物理或逻辑分离**：dev / staging / prod 使用**不同的服务器或数据库**；
- **非生产环境只加载匿名化或合成数据**；
- 分析型存储应用更严格的保留与掩码规则；
- 若要真实数据做性能测试，**构建一次性匿名化管道，产出少数代表性租户的假名化副本**，再用于非生产环境。

**渐进式发布（灰度）的可迁移机制（LaunchDarkly 官方文档）** **[一手]**：
- **flag 版本可回滚**：变更历史中可恢复到之前版本（**仅限最近 30 天的状态**）；恢复后旧版本"前移"成为新版本号；恢复前展示**代码 diff** 与预览；不能恢复与当前版本一致的版本；无法回滚由实验、受保护发布或渐进式发布控制的状态；
- **受保护发布（Guarded Rollout）的自动回滚**：LaunchDarkly 在以下情形自动回滚——**检测到回归且启用了自动回滚**；检测到**样本比例不匹配（SRM）**（无论是否启用自动回滚）；
- **回滚阈值必须在推进之前定义**，而不是等指标动了再定义；
- 发布序列：**先内部员工 → 再 beta 群组 → 再更大 tier**；flag 在每个阶段都是 kill switch；
- 平台声明的可靠性指标值得参考其**量级**：全局 flag 变更传播 **< 200 毫秒**、企业客户 **99.99% 可用性 SLA**、每日 **42 万亿次** flag 评估、100+ 全球接入点 **[一手，厂商自述]**；
- **审批工作流**：Anthropic 类的实践共识是"**没有任何 prompt 模板、模型 ID 切换或超参变更可以在没有记录在案的评审步骤下进入生产**" **[二手]**；LaunchDarkly 提供带自定义角色的审批流程；GrowthBook 支持 draft/revision/合并冲突处理/必需审批；Unleash 企业版提供四人批准（four-eyes）变更请求。

**配置变更的审计与回滚的核心理由（公开表述）** **[二手，growthbook]**：

> 一个显示"谁在何时批准了这次变更、以及之前的值是什么"的审计记录，**正是你的安全与合规团队对代码部署所期望的同一份证据**。如果配置住在 feature flag 里，它就自动继承了那份审计记录。

### F.6 配置化与元数据驱动（含"46 条非空（#1–#48）可配置"）

#### F.6.1 Salesforce 的元数据驱动（思想可学，实现不可仿）

**Force.com 多租户架构白皮书（官方一手白皮书，Salesforce）** **[一手]** 的核心机制：

- **元数据驱动架构**：应用的表单、报表、工作流、用户访问权限、租户定制与业务逻辑、**甚至底层数据表与索引的定义**，都是"存在于 Universal Data Dictionary (UDD) 中"的元数据抽象构造；
- **关键设计**：当你定义一张自定义表或写一段过程化代码时，**Force.com 并不创建"实际的"数据库表，也不编译任何代码**；它只存储元数据，由平台的运行时引擎**在运行时生成"虚拟"应用组件**；
- **清晰的边界分离**：编译后的运行时引擎（kernel）、租户数据、描述应用功能的公共元数据、以及各租户的元数据 —— 这四个边界的分离使"独立升级系统内核 / 修改核心应用 / 定制租户特定组件"互不影响；
- **性能关键**：由于元数据是核心成分，运行时引擎必须优化元数据访问，否则频繁访问会阻碍扩展。为此 Force.com 使用**大规模且复杂的元数据缓存**，把最近使用的元数据留在内存中，避免磁盘 I/O 与代码重编译；
- **存储实现（重要，且是"不可仿"的部分）**：**少数几张大型数据库表作为"堆存储"保存所有虚拟表的数据**；通过 `MT_Objects` / `MT_Fields` 等系统表管理租户 schema 元数据（含对象唯一标识 ObjID、拥有该对象的组织 OrgID、对象名）；用一组**反规范化的"枢轴表（pivot tables）"**支持索引、唯一性、关系等用途；平台还有独立的**外部搜索服务**异步更新租户与用户级索引；
- **平台化收益（官方陈述）**：单实例服务多组织、仅一套硬件、少量管理员即可管理、开发者只维护单一代码库；以及"改进质量、用户满意度和客户留存"——因为多租户应用是"一个由提供方自己托管的大型社区"，可收集运营信息（哪些查询慢、发生什么错误）并对整个用户群同时做频繁的增量改进。

> **🔴 明确判定：Force.com 的多租户内核（堆存储 + UDD + 枢轴表 + 虚拟表运行时物化）绝不可仿制。**
> 理由：① 这是 Salesforce 的**专利技术**（白皮书自述"the patented technology"），且是二十年持续投入的产物；② 它解决的是"让第三方开发者在平台上定义任意自定义对象与自定义代码"的问题——**调元云是自研单一产品，不存在"第三方定义 schema"的需求**；③ 仿制它将导致所有查询退化为"堆表 + 枢轴表 join"，失去 Postgres 的索引与查询优化能力，性能会崩溃；④ 本项目已有 22 实体数据字典且已定 PostgreSQL，实体是**编译期已知**的，元数据驱动的最大价值（运行时未知 schema）不成立。
>
> **🟢 但它的"思想"必须学**：**把"变的东西"从"不变的东西"里分离出来，并给"变的东西"配版本、审计、回滚与缓存。** 这正是本项目"46 条非空（#1–#48）可配置项不得硬编码"的正解。

#### F.6.2 配置化在本项目的正确形态

综合公开实践，本项目应采用的配置分层（这是本报告对"46 条非空（#1–#48）可配置项"的核心建议）：

| 层 | 内容 | 存储 | 变更机制 | 审计/回滚 |
|---|---|---|---|---|
| **L1 系统常量** | 与租户无关的技术常量（如超时、重试次数） | 配置文件 / 环境变量 | 随代码发布 | Git 历史 |
| **L2 系统默认配置** | 46 条非空（#1–#48）配置项的默认值 | 配置文件（版本库内） | 随代码发布 | Git 历史 + PR 评审 |
| **L3 租户级配置** | 品牌方对 46 条非空（#1–#48）配置的覆盖值（含区域/门店粒度覆盖） | **数据库表（带版本）** | 运行时 API + 审批流 | **变更历史表（who/when/before/after）+ 一键回滚** |
| **L4 阈值与判定版本** | `threshold_version`（判定阈值） | **数据库表 + append-only 版本链** | 严格流程 | **必须不可变，且与 `evidence_snapshot` 绑定** |

**关键设计原则（有公开依据）**：
1. **L3/L4 必须与 L1/L2 分离**：L1/L2 随代码发布（有 Git 审计），L3/L4 运行时可变（需要数据库级审计）**[推断自 LaunchDarkly 的"配置即版本化实体"原则 + Salesforce 的"元数据与数据分离"原则]**；
2. **L3 的每次变更必须记录 before/after 与操作者，且支持回滚**（LaunchDarkly 的 flag 版本恢复机制是其公开证明）**[一手，LaunchDarkly]**；
3. **L4（判定阈值）必须 append-only**：因为它被 `threshold_version` 引用，而 `threshold_version` 又与 `evidence_snapshot` 一起构成"判定依据可回放"的完整性基础。**若阈值可被就地修改，历史判定的可回放性立即失效**；
4. **配置读取必须走统一入口并带缓存**（学 Salesforce 的元数据缓存思想：频繁访问的配置不能每次打数据库）**[一手，Salesforce 白皮书的缓存论证]**；
5. **L3 变更必须有审批流**（公开共识："没有任何配置变更可以在没有记录在案的评审步骤下进入生产"）**[二手]**；
6. **配置的分层覆盖语义必须显式定义**：`tenant 默认 → region 覆盖 → store 覆盖` 的优先级与继承规则必须写进契约并测试。**这一条是本项目特有的复杂度，对标平台没有对应物**。

**关于配置格式的一条实战建议** **[二手，growthbook]**：把相关的多项配置**打包成一个多元 JSON flag，而不是拆成多个独立开关**——因为拆开会产生无法清晰推理的交互效应。对本项目的启发：**46 条非空（#1–#48）配置应按语义分组为若干"配置集"，而非 46 个独立开关**。

#### F.6.3 一条必须避免的陷阱

公开警告 **[二手]**：**不要在运行时做 DDL**。多租户 SaaS 案例中明确列出"Custom fields via metadata (**no runtime DDL**)"作为设计前提。对本项目：**46 条非空（#1–#48）可配置项应作为数据行的值（或 JSON 列），绝不允许"新增一个配置项就 ALTER TABLE"**。

| **DR 采用 Pilot Light 或 Warm Standby，RTO/RPO 目标按业务影响分析分级设定** | 🟡 **需改造** | 本项目**同时存在两类数据**：① 敏感个人信息与判定结论（高价值、不可再生）→ 需要低 RPO；② 会话/缓存（可再生）→ 可高 RPO。建议：**数据库层用 Pilot Light（分钟级 RPO），整体 RTO 目标 1~4 小时（Tier 2 级别）**。**明确不做 active-active** |
| **明确定义 RTO/RPO 并写入 ADR（架构决策记录），每年及重大架构变更后复核** | 🟢 **直接适用** | 公开推荐做法；且 Atlassian 的教训证明"未测过的备站等于没有备站" |
| **定期 DR 演练，并测量 RTA（实际达成）而非只声明 RTO** | 🟡 **需改造** | ⚠️ **但要说明**：等保三级与医疗实践要求"每月测试数据恢复能力"，作为早期项目，建议**从季度演练起步，随合规进程加密到月度** |
| **dev / staging / prod 三环境分离 + 非生产只用脱敏或合成数据** | 🟢 **必须** | 这是公开实践点名的合规泄漏源（生产快照进 dev 是典型违规） |
| **渐进式灰度发布 + 每次发布前先定义回滚阈值** | 🟢 **直接适用** | 本项目涉及判定逻辑与敏感数据，**"先定义回滚阈值再推进"比任何工具都重要** |
| **46 条非空（#1–#48）配置分层：L2 默认值进版本库 / L3 租户级覆盖进数据库带版本与审计 / L4 阈值 append-only 不可变** | 🟢 **直接适用（本报告最高价值建议之一）** | 直接把"不得硬编码"与"判定依据可回放（`threshold_version`）"两个既有约束统一到一个模型里 |
| **配置变更走审批流 + 变更历史 + 一键回滚（学 LaunchDarkly 的版本恢复）** | 🟢 **直接适用** | 成本可控；且合规团队要求的正是这份审计证据 |
| **引入独立配置中心（如 Nacos/Apollo/Consul 集群）** | 🔴 **需谨慎／不适用** | 🔴 **明确反对引入外部配置中心作为主存储**：① 本项目 L3/L4 配置**必须与数据库中的判定数据在同一事务边界内保持强一致**（判定发生时读取的 threshold 必须与该判定绑定的 `threshold_version` 严格对应）；② 把阈值放到外部配置中心会引入"配置已变但判定未更新"的不一致窗口，直接破坏可回放性；③ 外部配置中心是微服务/多语言异构场景的产物，本项目单体 + Spring Boot 用**数据库表 + 缓存 + Spring 的配置抽象**即可满足。**如确需动态推送，可用其作为"推送通道"而非"真相源"** |
| **不做运行时 DDL** | 🟢 **直接适用** | 配置项的值变化绝不 Admission `ALTER TABLE` |
| **不照抄 Force.com 的 UDD / 堆存储 / 枢轴表内核** | 🔴 **不适用（明确反对）** | 专利技术 + 二十年投入 + 解决"第三方定义 schema"问题（本项目不存在该问题）+ 会摧毁 Postgres 的查询优化能力 |

## G. 配置化与元数据驱动（独立成节的理由与补充）

> 说明：任务清单将 G 节与 F 节分开。G 节的"配置中心/元数据驱动最佳实践"与"配置变更的审计与回滚"已在 F.6 完整展开（因为二者在架构上不可分割）。此处补充 G 节特有的三点：**配置与元数据的关系、跨租户配置的隔离风险、以及配置化的反面代价**。

### G.1 "配置"与"元数据"在本项目中其实是同一件事的两面

公开实践中两者的边界常被混淆。我的梳理：

| 概念 | 定义 | 本项目对应物 | 变更频率 | 是否影响可回放性 |
|---|---|---|---|---|
| **数据** | 业务事实 | 客户档案、体征记录、判定结论 | 极高频 | 是（判定结论本身） |
| **配置** | 影响系统行为但不改变"事实"的参数 | 46 条非空（#1–#48）可配置项、tier、限流参数 | 中频 | **是（若配置参与判定）** |
| **元数据** | 描述数据/配置结构的信息 | 数据字典、字段可见性规则、角色-字段映射 | 低频 | 否（但影响 schema 演进） |

**关键判断**：本项目的 **`threshold_version`（判定阈值）是"配置"，但它参与生成"事实"（判定结论），因此它必须被当作"数据"来管理（append-only、不可变、可回溯）**。这是本项目最容易出错的一点——绝大多数团队会把阈值当配置（可随时改），而它将导致历史判定无法回放。

**这条推论是本报告对架构设计最有价值的单点贡献，请务必在架构规格书中显式表达。**

### G.2 多租户配置的隔离风险（对标平台未覆盖、本项目特有）

公开的 RLS 讨论聚焦**数据行**隔离，但**配置行**同样需要隔离，且风险更隐蔽：

- 46 条非空（#1–#48）配置若存于单表，**其 RLS 策略必须与业务表同等严格**（`tenant_id` 列 + ENABLE/FORCE + 策略）；
- **配置缓存是最大风险点**：若配置缓存键不含 `tenant_id`，则租户 A 的配置会被租户 B 命中 —— 这是"缓存键必须带 tenant_id 前缀"这一公开实践的配置版本 **[二手，hld.handbook.academy]**；
- **L1/L2（系统级）配置是跨租户共享的**，因此**必须明确声明其"无租户语义"**，并禁止在其中放入任何租户相关的默认值逻辑；
- **三级覆盖（tenant/region/store）的解析结果必须可缓存且可失效**，失效粒度至少要能精确到"某租户的某门店"。

### G.3 配置化的反面代价（明确反对过度配置化）

公开实践中有一条容易被忽略的警告 **[二手，asoasis]**：**"Over-using enums: every value change can break clients."**（过度使用枚举：每个取值变化都可能破坏客户端）

**对本项目的推论（明确反对意见）**：

> **不要把"可配置"等同于"什么都可以配"。** 46 条非空（#1–#48）之外，凡是**参与合规判定、参与字段可见性、参与 append-only 数据生成**的逻辑，**都不应该被做成租户可任意配置的项**。理由：
> 1. 若判定规则可由租户配置，则"判定依据可回放"需要同时回放"当时的全部配置"——可回放性成本呈指数上升；
> 2. 若字段可见性可配置，则"服务端裁剪"的合规保证会被前端配置绕过；
> 3. 若多租户可配置项的组合空间过大，**测试矩阵会爆炸**：N 个租户 × M 个配置组合，无法穷举验证。
>
> **建议：把 46 条非空（#1–#48）明确分为"可配置"与"受控可配置"两类**——后者只允许在预设的离散取值集合内选择（而非自由文本/自由数值），且变更需要更强审批。这既满足"不得硬编码"，又保住可回放性与可测试性。

### G.4 对本节的裁决汇总

| 结论 | 分级 | 理由 |
|---|---|---|
| **把 `threshold_version` 当"数据"而非"配置"管理（append-only、不可变）** | 🟢 **必须（最高优先级）** | 这是"判定依据可回放"能否成立的唯一分水岭 |
| **配置表的 RLS 策略与业务表同等严格** | 🟢 **必须** | 配置泄漏同样构成跨租户数据泄漏（泄漏的是业务规则与客户结构） |
| **配置缓存键必须含 tenant_id（+ region + store）前缀** | 🟢 **必须** | 公开实践明确点名的跨租户缓存碰撞风险 |
| **46 条非空（#1–#48）分为"可配置"与"受控可配置"，后者限定离散取值** | 🟡 **需改造** | 防止测试矩阵爆炸与可回放性成本失控 |
| **不把参与合规判定与字段可见性的逻辑做成租户可配项** | 🔴 **明确反对过度配置化** | 会破坏服务端裁剪的合规保证与可回放性 |
| **不引入外部配置中心作为真相源** | 🔴 **不适用（明确反对）** | 见 F.6 裁决；会引入"配置已变但判定未更新"的不一致窗口 |

> **对本节的一句话建议**：本项目最关键的一步是把"判定阈值"从"配置"重新归类为"不可变的版本化数据"（append-only + `threshold_version` 绑定），并让配置表的隔离强度与前缀缓存键与业务表完全对齐——这两条做到，46 条非空（#1–#48）可配置与"判定依据可回放"就不再互相冲突。
