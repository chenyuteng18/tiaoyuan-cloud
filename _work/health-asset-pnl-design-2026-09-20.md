## §1 概念定义与命名（含方向翻转）

### 1.1 「健康资产」与「资产损益」的精确定义

**先说清楚一件事**：产品负责人的构想里有两个可以分离的部件，**必须拆开评价**，否则会得到一个"看起来很美、实则错位"的设计。

| 部件              | 内容                                               | 独立评价                                                                     |
| --------------- | ------------------------------------------------ | ------------------------------------------------------------------------ |
| **部件 A · 方向翻转** | 把症状分翻转为**正向健康指数**                                | **独立成立、且必要**。与"资产"隐喻**无关** —— 任何命名为"健康指数"的正向指标都能达到同样效果                   |
| **部件 B · 会计结构** | 期初余额 / 期末余额 / 本期损益 / 损益方向 / 重大性门槛 / 可比性准则 / 审计留痕 | **独立成立、且是本构想真正的价值所在** —— 它强制"两次离散测量"变成"一个有期初期末的结构"，从而**把"可比性"从可选变成结构必需** |

**定义（正式）**：

> **健康资产**（口径 · `internal_health_asset`；**v2：内部 / 对外同名**）：
> 指某客户在某一时点的**同源量表症状负担的正向镜像值**，即 `H = T_max − T`。
> 其中 `T` = 该客户锁定分龄题组的 7 维症状总分，`T ∈ [0, 112]`（依据 config #35，PRD **L1127**：量程统一 0–4 五级，维度满分 0–16，总分 0–112）；`T_max = 112`。
> **`H` 的量纲与 `T` 同宽（0–112），`H` 越大表示症状负担越轻。**

> **资产损益**（口径 · `internal_health_asset_pnl`；**v2：内部 / 对外同名**）：
> 指同一客户**同源可比的期初与期末两个时点**之间的健康指数变动，即 `ΔH = H_cur − H_base`。
> **它是两个时点之差，不是多次服务次数之和** —— 这正面回应负责人原话「**和调理次数没有关系**」：`ΔH` 的表达式里**不含服务次数 `visit_no`**，只含两次评估的分数。
>
> ⚠️ **但必须并列声明一条**：服务次数**不出现在公式里**，却**出现在可比性前置条件里** —— 周期评估节点本身由"每 7 次服务触发"（config #1，PRD **L1093**；config #3，**L1095**）。**所以"和次数无关"应精确表述为「损益的量与次数无关；损益的可测性与次数有关（次数不足则无期末读数）」**。把这两层混为一谈，会在"客户做了 3 次就想看资产损益"时无法回答。

### 1.2 方向陷阱与翻转公式

#### 1.2.1 陷阱的精确形态

量表方向为**症状向**：

| 事实                                                      | 出处                                     |
| ------------------------------------------------------- | -------------------------------------- |
| `item_direction` **仅允许 `symptom`**（不适 / 症状向）            | config **#34**，PRD **L1126**           |
| 量程 0–4 五级；维度满分 0–16；总分 0–112                            | config **#35**，PRD **L1127**           |
| MCID 判据&#x4EE5;**"下降"为正**：「模块总分（0–16）**下降 ≥3 分**……→ 改善」 | config **#33**，PRD **L1125**           |
| IR 公式分子为 `S_base − S_cur`，**允许负值不截断**（负值 = 变差）          | metric-spec **§1.3 L80**；数据字典 **L690** |

**因此：`T` 下降 = 症状减轻 = 变好；`T` 上升 = 症状加重 = 变差。满分 112 分是"最重"，0 分是"无症状、最佳"。**

#### 1.2.2 为什么"不翻转会导致资产增值被全体读反"

只做**算术**，不做**语义**：

| 情形   | 症状总分 `T`                | 若把 `T` 直接命名为"健康资产"                | 真实语义         | 读反后果                |
| ---- | ----------------------- | --------------------------------- | ------------ | ------------------- |
| 调理有效 | `T: 40 → 25`（**下降 15**） | "资产从 40 降到 25" → 读者结论：**资产减值 15** | 症状减轻，**是改善** | ❌ **完全读反**          |
| 调理无效 | `T: 40 → 55`（**上升 15**） | "资产从 40 升到 55" → 读者结论：**资产增值 15** | 症状加重，**是恶化** | ❌ **完全读反，且把恶化读成改善** |

> **这一条比"读反"更危险的地方**：第二行（**恶化被读成增值**）在管理看板上会**直接把"效果最差的门店"排到最前面**。而这条看板的读者是**区域督导与总部运营**（config #40 `refund_visibility` 中可见者），他们会据此做出资源投放与稽核判断。**一个把恶化读成增长的看板，比没有看板更有害** —— 这是本构想在落地前**必须先解决**的唯一硬技术问题。

#### 1.2.3 翻转公式（按总分）

```
定义（总分级翻转）：
    H(t)  = T_max − T(t)                ，T_max = 112
    H_base = 112 − T_base               （期初余额）
    H_cur  = 112 − T_cur                （期末余额）
    ΔH     = H_cur − H_base
           = (112 − T_cur) − (112 − T_base)
           = T_base − T_cur
           = −ΔT                        （与症状总分变化等量反号）
```

**`ΔH` 与症状分变化 `ΔT` 绝对值相同、符号相反。翻转是零信息损失的线性镜像。**

#### 1.2.4 翻转公式（按维度 / 模块）

**这里必须给两种粒度，且必须说明它们的可用性不同**：

```
粒度① —— 按 7 维翻转（维度级）
    H_dim = 16 − T_dim        ，T_dim ∈ [0, 16]（4 题 × 0–4）

粒度② —— 按 M1–M5 模块翻转（模块级）
    H_m = 16 − S_m            ，S_m ∈ [0, 16]
```

| 粒度                  | 是否可落地                                       | 原因（见 §0.1 C-4 / C-5）                                                                                                                                                                                    |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **总分级（0–112）**      | ✅ **可落地**（期初有 `total_score`；期末需由模块求和 —— 见下） | `baseline_assessment.total_score`（PRD **L1306**）；`cycle_assessment.module_scores`                                                                                                                       |
| **7 维级（0–16 / 维）**  | ⚠️ **不可全量落地**                               | 期末只有 **M1–M5**（数据字典 **L387**），**没有 7 维**。7 维 ↔ M1–M5 的映射在 metric-spec **§2.1（L109-132）**&#x4E2D;已标明**2 个孤儿维**：面部气色肤质（部分承载，推荐 A 补题）、**记忆专注（孤儿，推荐 B 不纳入判定）**；且 PRD **L801**（P0-13）明确「**记忆专注维度明确不参与效果判定**」 |
| **M1–M5 模块级（0–16）** | ✅ **可落地，且与既有判定体系同粒度**                       | 数据字典 **L387**；config #33（PRD **L1125**）以模块总分为基准；metric-spec **§1.3 L75**                                                                                                                                |

> 🛑 **结论（粒度纪律）**：  
> **展示层用总分级（0–112）正向指数；判定层沿用模块级（0–16）现成的 IR + MCID。两层不得互替** —— 用一个总分 `ΔH` 去套模块级的 MCID（≥3 分）是**量纲错误**：`ΔH` 的 3 分可能来自 7 个模块各降 0.43 分，而 MCID 要求的是**某一个模块降 ≥3 分**。两者不是同一个判据。

### 1.4 「资产」隐喻带来的真实产品价值 —— 独立核实

**产品负责人的判断**（team-lead 转述）：「它强制把对外表达从"症状分"翻转为"正向指数" —— 客户看到"从 72 升到 88"比"从 40 降到 25"直觉正确。」

**我的独立核实结论：判断方向正确，但因果归属需要修正。**

| 核实项                                         | 结论                                                                                                                                                                                                                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **「客户看到"从 72 升到 88"比"从 40 降到 25"直觉正确」是否成立** | ✅ **成立，且我给出机理解释**：症状分的**数值方向与体验方向相反**（分降 = 感觉变好），客户需要一次**心算反转**才能理解。正向指数把这个反转**在系统层做掉**，客户不再需要心算。**这是真实可测的认知负担差异**（客户不是不能理解，而是**理解成本高的地方最容易理解错** —— 尤其"从 40 降到 25"这句话高度依赖上下文，在一句口头转述或一张窄屏卡片上极易被读成"变差了"）                                                      |
| **这个价值是否由「资产」隐喻带来**                         | ❌ **不成立。这个价值由「方向翻转（正向指数）」带来，与"资产"二字无关。** 把它命名为"健康指数""状态分""体能分"，效果完全相同                                                                                                                                                                                        |
| **「资产」隐喻真正不可替代的贡献是什么**                      | ✅ **是"结构"，不是"方向"** —— 它强制引入 **期初余额 / 期末余额 / 本期损益 / 重大性门槛 / 可比性准则 / 审计留痕** 这一整套结构。其中**最有价值的一条是「可比性准则」**：会计上"期初期末须同一口径"是记账的前提，同理**健康指数须同源（题组 ID 同源 ∧ 量程 0–4 ∧ 测量人同一）才可相减** —— 而这条在既有系统里**已经有了**（数据字典 **L689** 同源断言、`migratable` 四要素），只是**没有被"资产"这个框架强制地摆在第一位** |
| **「资产」隐喻的净成本**                              | ⚠️ **三项**：① 财产属性争议（§4 风险 B）；② 该词对外不能用（削弱了它作为统一命名的能力，内部一套、外一套）；③ 容易被读成金融承诺（§4 风险 A 的近邻）                                                                                                                                                                       |

> **独立结论（三条）**：  
> ① **构想的实质价值 = 「正向指数」+「期初期末结构」两件，二者都可保留，且都不需要"资产"这个词**；  
> ② **方向翻转必须独立定义为「症状分 → 正向健康指数」，不得依赖"资产"隐喻** —— 因为隐喻一旦被业务方在某个场合撤回（对外禁用），翻转逻辑若挂在隐喻上会一起失效；  
> ③ **建议：内部保留"健康资产损益"作为结构隐喻（它确实强制了可比性），但把翻转公式写成一条独立、与命名无关的变换，并在实现层把 `H` 与 `ΔH` 定义为纯函数** —— 这样命名可改、公式不动。

> - ✅ **可给**：总分级损益（`ΔH`）；M1–M5 模块级损益（`ΔH_m = −ΔS_m`）—— **且必须注明"仅方案涉及模块"**；
> - ⚠️ **不可给**：面部气色肤质的损益 —— 补题前**期末无读数**，只可显示"基线档案值，暂无对照"；
> - ❌ **禁止给**：**记忆专注的损益** —— 该维**不参与效果判定**，给它一个"损益"等于**把一个不可归因的指标放上判定台**（metric-spec **§2.2 L132** 原文：「中医调理对记忆的因果链弱、**归因噪声大**，纳入判定会被质疑"拿不可归因指标做疗效承诺"」）。

#### 不对称 ② · 缺失不对称：期末"仅填方案涉及模块"→ **总分会被系统性低估**

`cycle_assessment.module_scores` 的定义是「**仅填方案涉及模块**」（PRD **L1370**）。因此出现了**方向陷阱的第二种形态**：

| 情形               | 基线总分 `T_base` | 期末（只填了 3 个模块）         | 若直接把两个总分相减                                          | 真实语义                       |
| ---------------- | ------------- | --------------------- | --------------------------------------------------- | -------------------------- |
| 客户方案只涉及 M1/M3/M5 | 40（**全 7 维**） | 假设 3 个模块各降 2 分，实际症状减轻 | 期末未填模块按 0 计 → `T_cur = 0` → `ΔH = +40` → **"资产暴涨"** | 只是**没测**，不是**治好了**         |
| 若未填模块用基线值补       | 40            | `T_cur = 34`          | `ΔH = +6`                                           | 更接近真实，但**引入了"未测 = 未变"的假设** |

> 🛑 **这是本设计件发现的、比"读反"更隐蔽的一类失真**：**它不会产生一个荒谬的大数（会被看出来），而是产生一个"看起来合理、实际被未测模块稀释或放大的数"**。
>
> **必要条件（写死，不可省）**：  
> ① **期末"总分"不得直接与期初总分相减**，除非**两次测量覆盖的模块集合一致**；  
> ② 报告总分级损益时，**必须同屏给出"可比模块覆盖率"**（= 本期已测模块数 / 基线已测模块数），**未达 100% 时不得单独给出总分 ΔH**；  
> ③ 该覆盖率**属内部口径**，**客户端不得出现** —— 依据 `scan2_negative.words` **L45**（`覆盖率` 为该表 `negative counting` 组成员），且 W-2（PRD **L289**）要求客户端**一律用正向计数**（只显示「已采集 N 天」与「该日暂无数据」）→ **「覆盖率」是比率、不是正向计数，属禁列**。

> **关于是否需要新增字段**：见 §3.3 —— **本件建议不新增存储，改为在派生口径中把"可比模块集合"作为显式入参**。

## §3 数据落位

### 3.1 是否需要新增存储字段？（结论：**不新增**）

**本件结论：`健康指数` 一律不新增存储字段，从既有 JSON 列派生。**

| 理由              | 内容                                                                                                                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **R-1 · 纯函数**   | `H = 112 − T` 是**无状态纯函数**。存 `H` 等于存 `T` 的冗余副本 —— 一旦某次迁移 / 回填只改了一边，系统里就出现"两个数"                                                                                                          |
| **R-2 · 期初已锁**  | `baseline_assessment.locked = true`（数据字典 **L246**），**基线锁定只读**、不可覆盖。存储派生的 `H_base` 会与"锁定只读"的语义**叠加一层无意义的锁**，增加迁移成本                                                                      |
| **R-3 · 期末不安全** | `cycle_assessment` 是**追加、不可覆盖**（数据字典 **L391**）。派生值随 `module_scores` 追加而变化 —— **存储它就要在每次追加时重算，属"可维护性负债"而非"性能优化"**                                                                       |
| **R-4 · 双题库隔离** | config **#39**（PRD **L1131**）：「**两库分数不得相加、不得互相代入改善率分子/分母**」。派生口径**必须携带 `scale_id + scale_type + scale_version` 三元组**（数据字典 **L234** 明确要求判定依据快照须携三元组）—— **存储一个不带三元组的裸 `H` 会为"两库混算"留下入口** |
| **R-5 · AE 反证** | 若为性能而物化，**物化视图是可接受的**，但必须**带上三元组与 `threshold_version`**，并**只在一个地方计算**（单一计算点 = 防"两个数"的唯一有效手段）                                                                                           |

**唯一的例外情形（若确需物化）**：

- 场景：管理端看板要对**大规模客户**做"损益分布"聚合，实时派生代价高；
- 建议形态：**物化视图（非表）** `mv_health_index`，字段 = `{tenant_id, customer_id, cycle_id, T_base, T_cur, T_cur_modules[], delta_h, scale_id, scale_type, scale_version, threshold_version, computed_at}`；
- 代价：**约 1~2 人日**（视图定义 + 刷新策略 + 权限）；**风险：必须写死"唯一计算点"**，否则即为 R-4 破口。
- **本件建议：第一期不做** —— 先以派生口径落地，出现性能问题再物化（避免过早引入第二计算点）。

### 3.2 **必须定义稳定口径**（否则同一份数据会算出两个数）

**这是本件对产品负责人构想的第二个硬性补充。** 派生方案能省存储，**但代价是：任何一处自行实现 `112 − T` 的地方都可能取错 `T`**。

**稳定的派生口径（写死七条）**：

| #       | 规则                                                                                                                                           | 依据                                                             |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **P-1** | **`T` 的唯一来源**：期初取 `baseline_assessment.metrics_json` 的总分（等价于 `total_score`，PRD **L1306**）；期末取 `cycle_assessment.module_scores` 中**本期已测模块**之和 | 数据字典 **L689** IR 口径同源                                          |
| **P-2** | **同源前置**：题组 ID 同源 ∧ 量程 = 0–4 ∧ 测量人同一；任一不满足 → **不输出 `ΔH`，输出"不可比"**（与 `IR = NULL` 同处置、同出口）                                                     | 数据字典 **L689**；config **#32**（PRD **L1124**）                    |
| **P-3** | **`H` 的输出条件**：`migratable = true`（数据字典 **L247**：题组 ID / 量程版本 / 测量人 / 时间戳**四要素齐备**）；`false` → 不输出                                             | 数据字典 **L247** / **L693**                                       |
| **P-4** | **量纲**：`H ∈ [0, 112]`，**不给百分比**                                                                                                              | 见 §4 风险 C（百分比是"率"的形态）                                          |
| **P-5** | **模块集合对齐**：输出总分级 `ΔH` 时，`T_base` 必须**重算为与期末相同的模块子集**，不得用全 7 维基线总分对期末子集总和                                                                     | §2.3 不对称②                                                      |
| **P-6** | **`baseline_zero`**：某模块 `S_base = 0` → 该模块**不进 ΔH 计算**，标 `baseline_zero`，走"新发症状"路径                                                           | 数据字典 **L690**；metric-spec **§1.3 L87-88**                      |
| **P-7** | **负值不截断**：`ΔH < 0` 一律保留，**不得截断为 0**                                                                                                          | 数据字典 **L690**；metric-spec **§1.3 L89**（「截断会系统性掩盖恶化，是**二次失真**」） |


> **P-5 是本件新增的一条、也是唯一一条会改变数值结果的规则** —— 如果不加 P-5，**"期末总分"这一层派生若在两个小组各写一遍，就会算出两个不同的数**。**建议把 P-1~P-7 写成一份可测试的口径卡，与既有 `config #32`（IR 计算口径，PRD L1124）同级收口。**

### 3.3 健康指数与 `improvement_rate` —— **是同一个数换了方向，还是两个不同的数？**

> **本件结论（明确、不含糊）：既不是"同一个数换了方向"，也不是"两个不相干的数"。它们的关系是「分子共享、分母不同、颗粒度不同」三方错位。**

**逐层拆解**：

```
【第一层 · 层内（模块级）】
    S_base, S_cur ∈ [0,16]                    —— 模块总分（0–16）
                                              依据：metric-spec §1.3 L75；config #33（PRD L1125）
    ΔS_m = S_base − S_cur
    IR_m = (S_base − S_cur) / S_base × 100%   —— 现成：cycle_assessment.improvement_rate
                                              依据：metric-spec §1.3 L80；数据字典 L689 与 L690

【第二层 · 总分级】
    T_base = Σ S_dim（全 7 维）∈ [0,112]
    T_cur  = Σ S_m（本期已测模块）∈ [0, 96]
    H_base = 112 − T_base
    H_cur  = 112 − T_cur
    ΔH     = H_cur − H_base = T_base − T_cur

【层间关系（关键）】
    ΔH 与任一 IR_m 的分子 ΔS_m 不是同一个量 —— 前者是 7 维/多模块之和，后者是单模块
    但 ΔH 的 {T_base, T_cur} 与「模块级 IR 的分子之和」共享同一批底层题项数据
    ⇒ 同一批数据，两个不同的加法
```

| 比较项          | `health_index`（`H`）                           | `improvement_rate`（IR）                                 | 判定                     |
| ------------ | --------------------------------------------- | ------------------------------------------------------ | ---------------------- |
| **颗粒度**      | **总分级（0–112）**                                | **模块级（0–16）**                                          | ❌ **不同**               |
| **形态**       | **绝对水平**（一个水位读数）                              | **相对变化率**（相对基线的比例）                                     | ❌ **不同**               |
| **一个还是两个时点** | **一个时点一个值**（期初一个、期末一个）                        | **两个时点算一个值**                                           | ❌ **不同**               |
| **数学关系**     | `ΔH = T_base − T_cur`                         | `IR_m = (S_base − S_cur)/S_base`                       | ⚠️ **分子族共享、分母不同**      |
| **除零点**      | `H_base → 0` 时"增值率"发散（**但若只给 `ΔH` 绝对值则无此问题**） | `S_base = 0` → `baseline_zero`（**已有处置**，数据字典 **L690**） | ⚠️ **若定义"增值率"会新引入除零点** |
| **同源前置**     | 必须同源（P-2）                                     | 必须同源（数据字典 **L689**）                                    | ✅ **相同**               |
| **可对外**      | ❌ 不可（若含"资产"/"率"）                              | ❌ **不可**（`改善率` 在 `scan3_derived.words` **L40**）        | ✅ **相同**               |

> **正式结论（四条）**：
>
> **① 「健康指数」（`H`）= 新概念、但数学上无新量** —— 它是 `T` 的线性镜像，`ΔH` 与 `ΔT` 等量反号。**独立于 IR 存在，但与 IR 共用底层题项数据。**
>
> **② 「健康指数变动额」（`ΔH`）与 IR 不是同一个数，但 `ΔH` 是 IR 的"分子族的和"** —— 精确地说：`ΔH = Σ ΔS_m`（对本期已测模块），而 `IR_m = ΔS_m / S_base,m`。**`ΔH` 是 IR 分子之和；IR 多除了一次各自的基线分母。**
>
> **③ 「健康资产增值率」（若定义为 `ΔH / H_base`）= 一个全新的数，本件建议不建设** ——
>
> - 它是唯一一个"IR 的镜像版"：`IR_m_img = ΔH_m / (16 − S_base,m)`，**分母从"基线症状负担"翻转为"基线健康存量"**；
> - **代价**：新引入除零点 `H_base = 0`（即 `T_base = 112`，基线极重者）。此时 `H_base = 0`，而 `ΔH = 0 − T_cur ≤ 0` —— 比率形态无意义。**IR 无此问题**（IR 的发散点 `S_base = 0` 已被 `baseline_zero` 处置）；
> - **且它一旦要对外展示，就只能是百分比** —— 而"率"的形态正是 §4 风险 A 的核心（**会被举证为"宣传有效率"**）；
> - **结论：不建设。** 需要"变化幅度感"时，用 **`ΔH` 绝对值 + 方向标签**表达，不用比率。
>
> **④ 因此"重复建设"的风险点不在 `H` 与 IR 之间，而在以下两处（本件明确标出，供评审拦截）**：
>
> - **风险点 1**：有人会把 `ΔH`（总分级）**直接套用** config #33 的 MCID（**模块级** ≥3 分）→ **量纲错误**。**拦截条款：MCID 判定只认模块级，总分 `ΔH` 不得用于判定。**
> - **风险点 2**：有人会为"期末总分"**另建一个字段**（因为 `cycle_assessment` 没有总分）→ 与 §3.2 P-5 的"模块子集对齐"规则**冲突**。**拦截条款：期末总分不落库，只作为派生中间量，且必须带"已测模块集合"。**

### 3.4 7 维各自的损益如何落位？

| 颗粒度          | 是否逐维 / 逐模块给指数                          | 落位                                                    | 依据                                                       |
| ------------ | -------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| **7 维**      | ❌ **不全量给**                             | 期末端**无 7 维数据**（只有 M1–M5）                              | §2.3 不对称①                                                |
| **M1–M5 模块** | ✅ **给**（`H_m = 16 − S_m`，仅限**本期已测模块**） | 直接派生自 `cycle_assessment.module_scores`（数据字典 **L387**） | metric-spec **§2.1**                                     |
| **面部气色肤质**   | ⚠️ **暂不给损益**                           | 补题前期末无读数 → 显示"基线档案值，暂无对照"                             | metric-spec **§2.2 L127**（推荐 A 补题）；PRD 未覆盖               |

> **模块级损益的可比性前置（必须写进实现）**：
>
> - `baseline_assessment` 的模块分**并非直接存在** —— 基线存的是 `dimension_scores[7]`（PRD **L1304**）。**要得到基线模块分，必须先做 7 维 → M1–M5 的映射**，而该映射**有 2 个孤儿维**。
> - **因此模块级 `ΔH_m` 必须携带"映射版本"** —— 否则 metric-spec **§2.1 L121** 的判定标准（「维度与模块必须一一或一多对应，且每维度都有周期复评题项，否则该维度不得进入效果判定」）会在实现层被遗忘。**建议把"模块映射版本"并入 `threshold_version` 的语义**（数据字典 **L388**），而非新开字段。

### 3.5 ★ 三源融合 —— 手环 / 评测 / 客户反馈如何进入「健康指数」

> **业务方原话第一句**：「**手环数据，评测数据，客户反馈数据**」—— 即业务方设想的"健康资产损益"是**三源共同构成**的。
>
> **本节必须回答**：**这三源各自以什么身份进入 `H` / `ΔH`？**（**若某源不进，写明为何**。）

#### 3.5.1 结论先行（三源的身份分配）

| 源 | 代表数据 | **进不进 `H` / `ΔH`** | 身份 | 依据 |
|---|---|---|---|---|
| **评测数据** | `baseline_assessment`（期初）／`cycle_assessment`（期末） | ✅ **唯一构成源** | **`H` 的分子、`ΔH` 的两个端点 —— 全部来自它** | 本件 §1.2.3 / §2.1 |
| **手环数据** | `band_telemetry`（**字段白名单见 §3.6.2**） | ❌ **不进 `H` / `ΔH`**<br/>✅ **进"展示层"（趋势 / 背景 / 过程线）** | **旁证与趋势，不是分数** | PRD **L763**：「手环**只进"依从性"输入，绝不进"效果核心指标"主判据**」；PRD **L21 关键决策②**：「手环数据只进「依从性」、绝不进「效果主判据」」 |
| **客户反馈数据** | 见 §3.5.3（**分三类，处置不同**） | ⚠️ **部分进、且只以结构化形态进** | **佐证 / 上下文，需按形态分流** | PRD **L970**（Non-goals #6）；数据字典 **L335**（`answers_json` **全点选**） |

> **v3 补充（手环字段口径）**：本行原列举"睡眠 / 步数 / 心率 / 静息心率 / 血氧 / 运动"沿用的是 PRD **L270**（手环可见性矩阵表头）的六项，**未含"压力"（P0-10 含）**，且**静息心率**本件已归入"仅内部"（无规格与 SDK 依据，见 **U-17**）。**⇒ 展示层字段以 §3.6.2 白名单为准**；本行列举仅代表"PRD 原有的可见性口径"。**注：血氧沿用既有裁定，客户端可展示**（见 §3.6.2「血氧裁定」块），故本行无需为血氧做例外。**⚠️ 另注：本行列举中的"静息心率"在 PRD 口径里本属客户可见（L272），本件因"无可交付数据"暂归内部 —— 两者不矛盾，属"裁定未撤、实现悬空"，见 U-17。**

> 🛑 **一句话**：**「健康指数」是纯量表派生量；手环与客户反馈都不进入它的数值。** —— 把三源都塞进一个分数，会同时违反 PRD **L763**（手环不得进效果主判据）与 PRD **L970**（自由文本不能进判定引擎）。
>
> **但这不等于"三源不融合"** —— 融合发生在**展示层的"四栏并列"**上（见 §3.5.4），**不发生在"一个分数"里**。

#### 3.5.2 手环数据：为什么不进，以及它如何被"看见"

**为什么"不进"是硬约束，不是设计偏好**：

| # | 理由 | 依据 |
|---|---|---|
| **①** | **PRD 已把它写成关键决策** —— 「手环数据**只进「依从性」**、**绝不进「效果主判据」**，结构性缺失不扣分」 | PRD **L21**（关键决策 ②）；PRD **L763**；P0-10（**L798**） |
| **②** | **手环是自愿的，且缺失不可归因于客户** —— 「**不强制手环佩戴**」（PRD **L64**）；结构性缺失（未同意佩戴）`applicable=False`、**不计扣分**（PRD **L755**）。**若把自愿数据接进效果分，等于对"未佩戴者"给出了一个系统性的低分** | PRD **L64 / L755** |
| **③** | **量纲不可通约** —— `H` 的量纲是"症状题项 0–4 × 4 题"（config #35，PRD **L1127**）；手环量纲是分钟 / 步 / 次 / bpm。**二者相加在数学上没有定义** | config #35；数据字典 §四 |
| **④** | **会破坏"同源断言"** —— `H` 的同源前置是「题组 ID 同源 ∧ 量程 = 0–4 ∧ 测量人同一」（数据字典 **L689**）。**手环不携带任一要素** → 接进去即等于引入一个永远 `migratable = false` 的成分 | 数据字典 **L689 / L247** |

#### 3.6.3 ★ 手环如何体现"过程线"（**问题 2**）

**★★ 影响 1（本节最重要的论证）：手环是「逐日高频」，量表是「周期低频」——两者在这套概念里的角色天然不同**

| 源 | 时点密度 | 天然能表达什么 |
|---|---|---|
| **量表**（`baseline_assessment` / `cycle_assessment`） | **只有两个端点**（期初 / 期末） | **只能算损益** —— 一个差值 |
| **手环**（13 条逐日历史接口 + 分时点数组） | **逐日 + 分时点** | **天然能画过程曲线** |

> **⇒ 这正是"资产"这个词真正需要的东西**：**只有期初期末两个点，客户看到的是一个"差值"；加上手环的逐日数据，才能画出"净值曲线"** —— **这才是"资产"的完整体验。**
>
> **这条论证同时强化了本件 §1.4 的独立核实结论**：「**"资产"隐喻真正不可替代的贡献是"结构"，不是"方向"**」 —— 现在可以补一句：**该结构要成立，需要"端点 + 过程线"两件；而"过程线"的数据来源，只有手环能给**（量表按周期触发，客户反馈是非连续的）。**所以手环对"资产"这个隐喻的价值，不在它的数值，而在它的时点密度。**

**🛑 但必须与既有裁定对齐（否则这条论证会被误读为"手环要进 `ΔH`"）**：

- 手环**不进 `H` 数值** —— PRD **L21 关键决策②**（「手环数据只进「依从性」、绝不进「效果主判据」」）+ PRD **L763**（「手环**只进"依从性"输入，绝不进"效果核心指标"主判据**」）。
- **正确的分工：手环做「过程线」，量表做「端点」** —— 两者在展示层**并列、不合成一个分数**（本件 §3.5.4 已写死"不求和、不加权、不做综合评分、不做因果归因"）。

**🛑 但必须写死一条边界（"单列"不等于"互相解释"）**：

> **睡眠栏位与量表「睡眠质量」维度：并列展示，不互相解释、不做一致性校验、不做"客观印证主观"的表述。**
>
> **理由（三条）**：
> 1. **会触发因果归因** —— 任何"手环显示深睡增加，量表睡眠质量也改善"的表述，都是**把两源读成互为证据** → 落入 §4.2.2 **A-4** 与 C.7.2 L1561（**效果写进书面凭证 = 合同条款**）。
> 2. **会与"手环不进效果主判据"冲突** —— 若两者被要求"一致"，就产生了隐式的交叉验证 → 手环事实上成了效果判据的一部分 → 违反 PRD **L21 / L763**。
> 3. **两者的口径本身不保证可比** —— 量表维度是 4 题 × 0–4（config #35，PRD **L1127**）；手环是分期时长。**"睡眠质量 12/16"与"深睡 78 分钟"之间没有既定换算关系**，强行并列解释会造一个无依据的推断。

**睡眠栏位的展示口径（写死）**：
- ✅ **可给**：分期时长 / 分期结构 / 逐日趋势；采集状态（正向计数 + 同步时间）；四态中性文案。
- 🛑 **不可给**：任何"睡眠得分""睡眠评分"（**本件不新建睡眠分** —— 理由同 §5.3：本项在指标层零新增）；任何与量表睡眠维度的对照表述；任何"达标 / 未达标"评价。

### 4.2 风险 A · 疗效承诺（**最重**）

#### 4.2.1 风险陈述与机理

> **对客户说"您的健康资产增值 12%"，等于一个数字化的疗效承诺。**

**为何与既有禁用表述同类、且更危险**：

| 维度   | 竹溪县市监局禁用的表述                | "增值 12%"                                                                                                                |
| ---- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 形态   | "X 天见效""有效率" —— **自然语言承诺** | **一个带单位的客观数字**                                                                                                          |
| 可举证性 | 客户 / 监管需要**主张**它是一句承诺      | **它本身就是"量化结果"的书面记录** —— 依据 **C.7.2 L1561**（海南乐东法院 2024：收据写"无效全额退款"被认定构成明确承诺，判全额退还；教训原文：「**效果写进书面凭证 = 合同条款，且经营者负举证责任**」） |
| 归因   | 需要证明"见什么效"                 | 数字自带"我方服务导致的变化"的因果暗示                                                                                                    |

> 🛑 **精确结论**：**"增值 X%"比"X 天见效"更危险** —— 后者是**陈述**（可辩称是宣传口径与履行情况的差异），前者是**带数值的书面记录**，直接落入 C.7.2 描述的情形。
>
> ⚠️ 另一半：**它同时落入 C.7.1 L1554 的射程** —— 若门店持《医疗机构执业许可证》，《医疗广告管理办法》第七条禁止「**宣传治愈率、有效率**」；而"**增值率 12%**"在形态上就是"率"。

#### 4.2.2 合规的对外形态（**按 v2 裁定 A 改定**）

**v1 时的 team-lead 倾向**：只给「健康指数 + 变化方向 + 中性正向描述」，**不给比率、不用"资产"这个词、不做门槛对比**。

> **v2 处理：业务方裁定 A 已把「不给期初分」「不用"资产"」两条撤下**（客户端给原始值 + 评分 + 结论，命名对外同名）。**故本节改为：保留全部"与承诺有关的禁令"，撤回"与信息量有关的限缩"。**
>
> **一句话判据（本节的骨架）**：**限制"怎么说"，不再限制"给多少"。** —— 效果承诺的风险产生于**措辞与因果归因**，不产生于**客户知道自己期初多少分**。

|---|---|---|

### 4.3 风险 B · PIPL 财产属性

#### 4.3.1 风险陈述

> 叫"资产"会引入「**谁拥有、能否处置**」的问题，而健康数据是**敏感个人信息**，不是财产。

**事实基础**：数据字典 **L743**：「心率 / 血氧 / 睡眠 / 血压属 **PIPL 第 28 条敏感个人信息** → **单独同意 + 最小必要**（`consent.auth_scope_json` 分项勾选）」。

#### 4.3.2 三个具体争议点

| #       | 争议点         | 可能的主张                         | 后果                                                                                                                               |
| ------- | ----------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **B-1** | **权属**      | "这是我的健康资产，你们凭什么用它做门店排名 / 稽核？" | 现有 `consent.auth_scope_json` 的授权描述若不含"用于内部经营指标"，**该用途缺少单独同意的支撑面**                                                                |
| **B-2** | **处置**      | "这是我的资产，我要导出 / 删除 / 带走"       | **删除权受限于合规留痕义务** —— 数据字典 §6.3 **L746**：`refund` / `case_archive` **按举证要求长期保留**、保留期待法务裁定。**"资产"隐喻会让客户产生"我有完整处置权"的预期，而这个预期系统无法满足** |

### 4.4 风险 C · 退款门槛反推

#### 4.4.1 反推链的精确形态（**这是"给不给期初分"的完整论证**）

```

    步骤 1  T_base = 112 − H_base        ← 客户可算（112 是公开满分）
    步骤 2  T_cur  = 112 − H_cur         ← 客户可算
    步骤 3  ΔT = T_base − T_cur          ← 客户可算
    步骤 4  客户见过「≥3 分」← config #33 若在任何一处对客户披露过
    步骤 5  客户自行比照 → 得到「达标 / 未达标」的自我评价
    ⇒ 与 W-1 末句「客户端不得出现任何形式的达标 / 未达标评价」相抵触
```

**关键判断（v2 改定）**：**步骤 4 是链条的软肋，而步骤 5 之后是断头路** ——

- 客户即使没拿到 `3` 这个数字，也会通过**社区 / 门店对话 / 多次观察**反推出一个"大概多少算好"；
- 因此**不能依赖"客户不知道门槛"来防反推** —— **依赖客户不知情的安全设计，等于没有安全设计**；
- 🛑 **但 v2 的关键更正在这里**：**客户完成步骤 5 之后，得到的是一个"自我评价"，而不是一个"退款结果"** —— 因为**效果类退款根本不自动出结论**（详见 §4.4.2 的 L3）。**所以这条链的最坏后果是"客户形成了一个自己的判断"，而不是"客户自动获得了某个权利"。** v1 把这条链读成"必须从第一步切断"，是**高估了链条末端的可达性**。

### 4.6 关于「全平台都要看见」的一条封死建议（**防与 HSI 混淆**）

> **业务方自然会想到的下一步**：「既然每个客户都有损益，那门店也能算一个平均损益 —— 这就能排门店了。」

| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **① 与 HSI 重复建设** | **HSI 是门店级健康度指数**（config **#18**，PRD **L1110**；P1-03，**L822**），已含 8 项加权指标，其中第 1 项 ECC（权重 23）**已经通过 `effect_verdict` 吃到了客户级效果数据**。**再建一个"门店损益率"= 同一件事的第二个视角** |

### 5.3 结论：哪些是同一件事的不同视角、哪些是新的

| 类别                | 项                                               | 说明                                |
| ----------------- | ----------------------------------------------- | --------------------------------- |
| **同一件事的不同视角**     | `H`（健康指数）与 `T`（症状总分）                            | **同一件事的镜像** —— 数学上零新信息（§3.3 结论 ①） |

| **🆕 新的（唯一一处）**   | **「正向指数的展示形态」** —— 即 §4.1 客户端那一层（**v2：对客户露出一份含原始值 / 健康指数 / 变化量 / 维度分 / 手环趋势的对照结构**）       | **这是本项真正新增的东西**：一个**新表达层**，不是新指标  |

| **❌ 不新建**         | 健康资产增值率（`ΔH / H_base`）                          | §3.3 结论 ③                         |
| **❌ 不新建**         | 期末总分字段                                          | §3.3 结论 ④ 风险点 2                   |
| **❌ 不新建**         | 门店级损益聚合指标                                       | §4.6                              |
| **❌ 不进**          | ECC / HSI 权重 / config #18                       | §5.2 写死 ①                         |

> **一句话总结 §5**：**「健康资产损益」在指标层是零新增；它新增的是一个"把症状分翻转为正向指数、并把期初期末摆成一个对照结构"的表达层。承认这一点，才能把它做小、做对；不承认这一点，就会去建重复指标。**

> **★ 6.2.2 ④ 的「为何不新增」论证（team-lead 裁定，完整版）** —— 即：**血氧的判定性措辞，为什么用"设计期 i18n 白名单"挡，而不用"构建期加词表"挡**。
>
> **📌 这一段同时是本项对三张词表最重要的一条贡献：它记录了一个「不该加什么」的决定** —— 避免下一个人重提"往 `scan2_negative.words` 加「正常 / 异常 / 偏低 / 偏高」"。该动作**已被两处既有记录直接约束**（下方 ① ②），**本件不重复提议**。
>
> | # | 理由 | 依据 |
> |---|---|---|
> | ① | **会制造永久误报**。`scan2_negative.words` 对 CJK 词条是**子串匹配**（无词边界）→ 加入「正常」这类**高频无害词**，会立即命中客户端必然出现的中性文案（「手环状态正常」「数据正常同步中」「同步正常」）。**一个常年报红的门禁会被绕过或被改松，比没有门禁更糟** | `scan2_negative.words` **L16-23「MATCHING CONTRACT FOR THIS FILE (important)」** —— 逐字：「**CJK terms -> matched as SUBSTRINGS** …… **DO NOT ADD A SHORT CJK TERM that happens to sit inside an innocuous customer-facing word**」 |
> | ② | **该表已有同类先例被明确拒绝**。裸词「判定」曾被提议加入，**表内留有 `CURATION DECISION ON RECORD` 明确拒绝**，理由正是"会命中合法的中性客户端标签「待判定」→ 永久误报"，并写明「**a gate nobody trusts is worse than no gate**」 | `scan2_negative.words` **L25-31** |
> | ③ | **危险度排序**：「正常」**高于**「判定」—— 「判定」尚属低频专业词，「正常」是**任何状态页都要用的普通形容词**（客户端必然出现「手环状态正常」「数据正常同步中」「请确认蓝牙正常」，甚至 W-2 要求的正向计数也可能写成「采集正常」）→ 误报率更高，后果更严重 | 同上 |
> | ④ | **扫描范围错配**。三张词表的 `roots` **全部只有 `client-package`**（只扫客户端小程序包**源码**）；`scan-manifest.json` · `faces.scan2_negative.roots = ["client-package"]`。而本项要防的是**文案**，且**构建期视图代码尚不存在** → 此刻加词**扫不到任何东西**，只是把风险推迟到实现期才暴露 | `scan-manifest.json`；`scan1_refund.words` **L11**（`SCOPE: the CLIENT (mini-program) package ONLY`） |
> | ⑤ | **正确落点是设计层**。禁的是一组**搭配**（数值 + 单位 + 状态 = 允许；数值 + 判语 = 禁止），不是一组**名词** → 属**文案表逐条比对 + 评审**的控制项，与 §1.3.2「控搭配、不控名词」同源 | 本件 §1.3.2；§3.6.2「血氧裁定」三条措辞约束 |
>
> **⇒ 裁定**：**构建期照扫现有三张词表（硬门禁，不改）＋ 设计期新增 i18n 文案白名单（本项自带）**。**若将来实现期确有证据表明误报可控**（例如改为**词边界 + 搭配正则**而非裸子串），**再议加词**，且**仍由 `a6-compliance-engineer` 裁定**（他是三张词表的 owner）。

> **⚠️ 附：scan3 匹配器的既存漏报面（2026-09-20 由 `a6-compliance-engineer` 实测上报 team-lead；本件独立验证并据此收窄措辞）**
>
> **背景**：本件曾在 §6.2.2 ④ ③ 建议"向 `scan3_derived.words` 新增四个能力溢出字段名，以防其流入客户端包"。**词条已由 A6 落盘（L58-L61）**，但 **A6 在验证时实测出：这四个词条只挡得住"精确形态"**。
>
> **本件独立验证结果**（直接在 `skeleton/compliance/scan_compliance.py` 的匹配函数上跑，**非转述**）：
>
> | 泄流形态 | 门禁 | 说明 |
> |---|---|---|
> | `"blood_sugar"`（独立字面量 / API 字段 / 点路径） | ✅ **拦住** | 整 token 相等即命中 |
> | `"band_blood_sugar"`（i18n key 下划线式） | ❌ **漏** | token = `band_blood_sugar`，切分后各段均 ≠ `blood_sugar` |
> | `MP_BLOOD_SUGAR_TAP: "mp_blood_sugar_tap"`（**埋点事件名**） | ❌ **漏** | 切分为 mp / blood / sugar / tap |
> | `getBloodSugar()` / `class BloodSugarAdapter{}`（camelCase） | ❌ **漏** | 驼峰切分为 blood / sugar |
> | `CLIENT_BLOOD_SUGAR_KEY`（ALL_CAPS 常量） | ❌ **漏** | 同下划线形态 |
>
> **根因（代码级）**：ASCII 词条走"**整 token 相等**"或"**单段相等**"两档（`scan_compliance.py` **L302-319**：先 `norm(raw_token) == needle`，再对 `identifier_segments(raw_token)` 逐段 `norm(segment) == needle`）。**对多字词条（含下划线）而言，"整 token 相等"只有在字段名被原样照抄时才成立；而一旦前后缀被拼接，"整 token"就不再相等，逐段比较也比的是单段（`blood` / `sugar`），永远拼不回多字的 `blood_sugar`。** ⇒ **多字词条实际上只有"被原样引用"这一种形态能被拦住。**
>
> **🛑 关键影响面（本件测算，比 A6 报告的范围更大）**：**`scan3_derived.words` 的 ASCII 词条共 14 个，14/14 全部含下划线**（L24-L33 的 `gap_reason` / `effect_verdict` / `AS_refund` / `a3_value` / `a3_applicable` / `is_compliant` / `achievement_rate` / `adherence_state` / `risk_flag` / `coverage_flag`，＋ L58-L61 本次新增四词）→ **漏报面覆盖 scan3 全部 ASCII 词条，不是本次新增四词独有的问题**。本件抽样验证：`mp_gap_reason_tap` ❌漏 / `mp_AS_refund_tap` ❌漏 / `api_coverage_flag` ❌漏。
>
> **⇒ 本件据此把相关表述收窄三处**（避免设计件给出一个门禁实际兑现不了的承诺）：
> 1. **不得写"已由 scan3 词表拦截"** —— 该表述**仅在"字段名被原样引用"时成立**；
> 2. **可写**："**词条已入表；当前匹配器对"字段名被原样引用"的形态有效，对 `前缀_字段_后缀` / camelCase 形态存在已上报的漏报面（见 `a6-compliance-engineer` 报告，待 team-lead 裁定）**"；
> 3. **本项不因该缺陷改变设计**（白名单 / 过程线 / 睡眠单列均不受影响）—— **它是门禁的覆盖强度问题，不是展示层设计问题**；**修复属匹配器范畴，由 `a6-compliance-engineer` 单独立项**，**本件不代改词表、不代改匹配器**。
>
> **📌 一条附带更正（A6 提出，本件复核确认）**：`scan1_refund.words` / `scan2_negative.words` 的匹配契约注释**举了一个不成立的例子** —— 契约写「ASCII terms -> matched against identifier segments, so `AS_refund` and `/api/v1/refund/x` both fire while `refundable` does not」，但实测 `mp_AS_refund_tap` 命中时 gate 报的是 `[scan1_refund] term='refund'`，**scan3 的 `AS_refund` 并未命中** —— 那个"fire"来自 **scan1 的单词条 `refund`** 在兜底。**⇒ 该例让 scan3 看起来具备段匹配能力，属契约措辞订正项**（由 A6 在立项时一并订正）。
>
> **★ v3 改定后复核**：**总区间不变（仍为 4~9 人日 / 返工风险 +0~1）**。两处改定**均落在既有分块内、未突破任何分块上限**：
