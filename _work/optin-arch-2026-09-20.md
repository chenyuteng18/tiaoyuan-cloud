## §4 选项 B · 中性化落地（推荐）—— 主体

### 4.1 命名落位

**已核对契约原文**（`_work/contract-t6-api-freeze-2026-09-19.md` **L557**）：

```
| **R1** | 客户可见字段名 / 枚举值**不得含"退款"** | `refund_status` / `refund_amount` / `refund_*` | `service_adjustment_state` / `fund_handling_*`（如确有需要） |
```

**沿用口径的读法**：契约给出的**不是两个固定字段名，而是一类命名的口径** —— **中性业务名词 + 状态/处理类后缀**，不含 `refund` 词根。本项按同一口径取名，**不与之冲突**（`service_adjustment_state` 描述的是"服务调整状态"，属**退款相邻语义**；本项描述的是"客户对服务保障方案的参与意愿"，**与退款无关联**，故不占用、也不改写该词）。

**建议命名（三级一致）**：

| 层 | 名称 |
|---|---|
| 中文字段名（文档 / 表单 / 字典口径） | **服务保障方案参与意愿** |
| 存储列（英文标识） | `consent.service_plan_optin` |
| 客户端可见枚举名（按契约 L571「客户可见枚举以 `client_*` 前缀」） | `client_service_plan_optin_state` |
| 枚举中文展示值 | `已选择参与` / `已选择不参与` / `未选择` |
| 对应英文 enum 值 | `participating` / `declined` / `undecided` |

> **口径说明**：本项**没有"内部才可见的参与态"**，因此**不需要**做第二套 `internal_*` 枚举 —— 契约 L571 要求"两套不得共用类型定义"，前提是**存在两套**；此处只有一套，不构成违反。客户端常量名仍带 `client_` 前缀以守住命名空间纪律。

> **一处口径待业务方确认（本项唯一的新增口径问题）**：**「参与状态」是否需要客户"必须表态"？**
> - 建议取 **`未选择` 合法存在**（不强制表态），理由三条：① 本项**不参与任何判定/资格**（红线 1），**系统侧没有"必须知道"的理由**，把它做成必填即"为采集而采集"，与 PIPL 最小必要（数据字典 L743 敏感个人信息节）相抵；② 与 04 表"**分项勾选、可单独拒绝**"的既有风格一致（PRD L790）；③ 一个"必须表态"的动作会在准入页制造额外摩擦。
> - **fail-closed 方向**：`未选择` **不赋予任何权利，也不产生任何义务** —— 系统按"无参与状态"处理。
> - 若业务方坚持"必须表态"，则该口径变更须回写 §4.2 的"必填"行，并评估是否升级为签署门禁（**本件不代为决定**）。

**是改造既有页，还是新增页？—— 改造既有页，不新增页、不新增步骤。**

依据 PRD **L790**（P0-02 知情同意电子签验收第 1 条）原文：

> 「一页承载：禁忌结论回显（只读）+ 个人信息授权（分项勾选，可单独拒绝脱敏沉淀）+ **手环佩戴意愿（愿意/暂不佩戴）**」

以及 **L1353**（04 表 §四）：

> 「04.§四 手环说明+意愿 ｜ `agreement.band_clause_text` + `consent.band_willingness` ｜ text/enum{自愿佩戴,暂不佩戴} ｜ 是 ｜ 不作为单方判定依据 ｜ 合规引文」

**该页的既有结构就是"一页承载多项可单独拒绝的分项"** —— 本项作为**同页的另一个分项**加入，**既有的页结构不需要改造**，只是**多一个勾选项**。**不新增页、不新增步骤、不新增端、不进准入向导的三步骤计数**（P0-17 的三步仍是「禁忌筛查 → 建档 → 签署知情同意书」，本项在第三步**之内**）。

**端约束沿用，不另立机制**：
- **X-1（服务端判定 + 后端 403 兜底，PRD L242）** —— 任何端**不得仅靠前端隐藏**；本项亦受其约束。
- **X-3（APP 内角色级差异化，PRD L244）** —— 调理师与本项的能力差异（只读 vs 无）不得退化为"谁装谁可见"。
- **X-2（小程序包体扫描，PRD L243）** —— 客户端包内不得含退款字样（本项文案须过扫描，见 §4.8）。

### 4.4 时序落位

**落点 = `CONSENTED` 节点**（PRD 状态机 **L898**：`CONSENTED` = 已签知情同意书 04 表；上游 `PROFILED` L897，下游 `ASSESS_BASE` L899；`SCREENING` 在 **L895**）。

**为什么不能放在"禁忌筛查前"（四条，逐条可验）**：

1. **`SCREENING` 是纯临床安全门禁，不是业务采集点。** PRD **L789**（P0-01）原文要求：命任一项禁忌 → 档案置 `REJECTED`，**建档 / 评估 / 出方案入口系统级置灰（后端 403）**；**筛查记录结果不可删除**。在此处插入业务性选择，等于在一个"安全闸门"上挂业务动作。
2. **会与"有禁忌不建档"的既有裁定直接相撞。** PRD **L1290** 原文：「**仅当 `screening_record.result = 通过` 才允许提交 `intake_profile`**；……有禁忌（`result = 不通过`）时**不生成 `intake_profile`**，客户直接置 `REJECTED`。顺序：**禁忌筛查 → 建档 → 知情同意书**。」→ 若选择落在筛查之前，**命中禁忌的客户会留下一条游离于任何档案之外的选择记录**，而 `consent` 表以 `customer_id` 为外键（数据字典 L195），**该记录无处可挂**。
3. **会造成"客户在不知道禁忌结论时先做选择"。** 04 表一页承载的**第一项就是禁忌结论回显**（PRD L790）。顺序颠倒意味着客户基于**不完整信息**表态 —— 而"客户是否参与某个服务保障方案"本身就以"该客户会被服务"为前提。
4. **采集合规性会出问题。** 对最终被拒诊的客户采集其意愿性数据，**超出最小必要**（数据字典 L743：心率 / 血氧 / 睡眠 / 血压属 PIPL 第 28 条敏感个人信息 → **单独同意 + 最小必要**；本项虽非敏感个人信息，但"最小必要"原则同样适用于个人意愿性记录）。

**为什么也不能放在 `ASSESS_BASE` 或更后**：04 表是**准入向导的第三步且不可跳步**（PRD L805 / L889「可续办但不可跳步」）；把它后移到基线评估之后，等于**新造一个步骤**并破坏 L889 的三步连续性。

**落点小结（一句话）**：**在既有第三步之内、与 `band_willingness` 同页并肩、由客户本人自选、无需新增步骤。** 时序与 04 表一致，而**不是**与"禁忌筛查前"一致。

### 4.8 必须写死的红线（五条）

> 以下五条**任一条被推翻，选项 B 即不成立**，应立即回落至 §3（选项 A）或 §5（选项 C）。

**红线 1 · 「参与」绝不等于「自动获得退款资格」。**
本项**不改变任何人的退款权利**。退款资格仍走 **P0-14 三层结构第①层**（PRD **L802**：「资格判定 = 零阈值、系统自动直出」）与 **P0-12 上线前回测门槛**（PRD **L800** 阶段一 `κ ≥ 0.70 且绝对一致率 ≥ 85%`；config **#31**（L1123）`N ≥ 100` / **漏判率 ≤ 5%**）。**「参与」不得成为绕开这两道门槛的资格开关**，且**不得写入任何判定公式、权重、门槛**。
→ **可测**：`service_plan_optin` 的值**不得出现在**判定引擎的任何输入集（`AS_refund` 三维、`effect_verdict` E1–E5、`disposition`）；**契约层断言**：判定域接口的入参 / 响应体中**不含该字段**。

**红线 2 · 手环仍为自愿，且两项选择互不前置、互不降级。**
① 「参与」者可在同页**单独勾选**"愿意佩戴手环"；② **不参与者的手环意愿同样可自愿选择**；③ **两者都不构成服务前置、都不降低服务等级**；④ 本项**不修改** `band_willingness` 的**取值域 / 必填性 / 可见性**（PRD L790 / L943 / L1270 / L1353 / L967 / L570 护栏② / L527 第①行）。
→ **可测**：两字段**独立提交、独立拒绝**；任一字段缺失**不得**导致准入流程阻断（003 表建档 / 04 表签署的后端 403 判定中**不得出现本字段**）。

**红线 3 · 客户端与调理师端全链路无"退款 / 无效退款"字样**（含 i18n / 枚举名 / 常量 / 报错文案 / 埋点名 / 订阅消息模板 / api 路径段）—— **并入既有 ADR-12 扫描，不新开扫描面**。

### 4.9 对 P0-19 / R4c 的连带影响（**本件对该判断给出了否证与限定**）

**团队 lead 的假设**：本项让客户在 04 表自助勾选，等于在准入期留下一个**客户本人产生、带时间戳的选择记录**，**对 R4c 是净改善**。

**本件复核结论：该假设在严格口径下不成立；且若业务方对 §2 必答问题选"答②"，它会反向恶化。**

**理由（三条）**：

1. **事实对象对不上。** R4c（PRD **L1060** / **L1064**）的失效点是**退款诉求在"客户 → 客服 / 前台（→ 调理师）→ 经络师"传导段丢失** —— 其观测对象是**"客户何时提出诉求"**。本项记录的是**"客户是否参与某个服务保障方案"**，**两者不是同一个事实**。本项**不减少 R4c 的发生概率**，也**不为"客户何时提出诉求"提供任何锚点**。
2. **红线 1 进一步切断了它与退款链路的关联。** 既然「参与 ≠ 退款资格」必须写死（§4.8 红线 1），那么这条记录在构造上**就与退款判定解耦** —— 一条**被规定不得影响退款**的记录，**不可能**改善"退款诉求的可观测性"。
3. **答② 下会反向恶化（同构失效，须显式登记）。** 若业务方答"参与了更容易退"，则客户从**准入期**就形成"我有退款权利"的信念，而该记录**按红线 1 又恰恰不能作为资格依据** → 产生 **"客户认为已获得某种地位、而系统里查不到可支撑它的依据"**。**这与 R4c 的形态同构** —— 该同构关系直接引用 PRD **L494** 的既有写法（「同构失效必引」）。**结论：答② 会把本项从"中性字段"变成 R4c 家族的一个新失效入口。**

**本项确实成立的、但**不属 R4c** 的一点正向（须分开记账）**：

> 本项在架构上**验证了一件事**：**`consent` 表 + 04 表页 + B3/B4 的既有结构，可以承载"客户本人产生 + 带时间戳（`signed_at`）+ 服务端判定可见性"的自证型留痕**，且**成本基线只有 2~4 人日**。这是**能力储备**（为一类将来可能的需求备好了落点与报价）。
> **但必须写死一条禁令**：**不得据此把"客户端诉求受理入口"视为已获批准**。任何"给客户一个诉求留痕点"的提议，仍**属「变更业务裁定」→ 触发 §2.2 条款 B**（PRD **L181**：P0-19 **+2~4 人日 + 已完工部分返工 + 重走 `refund_visibility` 冻结**；PRD **L1083** 备查段同源）。**能力已验证 ≠ 授权已获得。**

**对 P1-04 稽核信号的影响（PRD L807 C1-4；P1-04 六类信号见 PRD L823）**：

| 项 | 结论 |
|---|---|

| 是否使既有信号失真 | **不会**。C1-4 度量诉求转交行为，本项与诉求无关（红线 1） |

## §5 选项 C · 变更业务裁定（代价最高）

**触发条件**：业务方**坚持**「调理师端可见 + 强制佩戴」。

### 5.1 精确触发条款（两条，逐字可引）

| # | 条款 | 原文要点 | 行 |
|---|---|---|---|
| **C-1** | **PRD §2.2 条款 B（返工规则）** | 「若业务方在 P0-19 开工之后改口（**泛化：允许任何新角色（含调理师）在系统内登记 / 转交客户诉求**）→ **P0-19 增项 +2~4 人日 + 已完工部分返工**，须**重走 `refund_visibility` 冻结**；此类提议一律按「**变更业务裁定**」处理，**不得按「体验优化」处理**。**条款 B 是 R4c 的全部牙齿**」 | **L181** |
| **C-2** | **PRD §2.6.7 R15（同等级别）** | 「**防复发：任何"给客户看依从性评分"的提议一律按业务裁定变更处理**，不得按体验优化处理（同 §2.2 条款 B 精神）」；同条目另载 **config #43** 客户侧 ③④「**放开 ③④ 属「变更业务裁定」，触发与 §2.2 条款 B 同等的返工与重走冻结流程**」 | **L345** / **L1134** |

**触发后的后果链（四步，缺一不可）**：① `P0-19` **+2~4 人日**；② **已完工部分返工**；③ **重走 `refund_visibility`（config #40）冻结流程**；④ 若同时放开客户侧手环派生可见（本项不涉及，但须防"顺手一起放开"），另走 **R15** 同等流程。

**同一泛化条款会覆盖本项本身**：路线图 **L1589** 已就条款 B 的泛化写明 ——「**条款 B 恰好也覆盖了 C1-1′ 本身**……**这才让条款 B 真正成为 R13c（乃至整个 R4 家族）的牙齿**」。因此本项一旦开工，**若再被要求调整角色范围或登记内容，同样按 +2~4 计**。

### 5.2 「强制佩戴」这一条，**任何技术方案都化解不了**

必须让业务方看清这一点：**变更裁定只能解锁"调理师端可见"，解锁不了"强制佩戴"。**

| 冲突对象 | 原文 | 行 | 为何技术无解 |
|---|---|---|---|
| **Non-goals #3** | 「**不强制手环佩戴** —— 源文档明确"手环佩戴完全自愿"，且 Hermsen 2017 证明**强制依赖必然因衰减失效** —— 任何硬性依赖手环数据的判定都会误判」 | **L967** | 这不只是合规立场，**含一条工程判断**：强制依赖会**因依从衰减而失效**。即使合规上被放行，**数据层面也走不通** —— 强制并不能提高长期佩戴率 |
| **P0-02** | 「**拒绝佩戴手环不得成为拒绝服务理由，不得降低服务等级**」；数据源标记 `self-report` | **L790** | 这是**服务等级的非歧视性要求**，属产品定位级约束，**不是可配置项** |
| **§⑥ 护栏②** | 「"**必须打开小程序**"不得升级为获得服务的任何前置条件」 | **L570** | 该护栏堵的正是**"必须做 X 才能获得服务"这一形式**——把 X 换成"佩戴手环"，**同型，同样被堵** |
| **P0-25 / ARC-07·08·11** | 「**任何"手环缺项反转为阻断"的写法一律违规**」；手环类缺项**不得反转为阻断** | **L307** / **L1474** | 强制佩戴在系统语义上**必然**表现为"手环缺项 → 阻断"，**与这条正面冲突** |

**结论（须原样转达业务方）**：
> **「强制佩戴」与 Non-goals #3（L967）+ P0-02（L790）+ 护栏②（L570）+ P0-25（L307）的正面冲突，无法通过任何技术方案化解。** 它需要业务方**以书面形式推翻自己在 2026-09-16 的裁定**（L161 原话 + config #40 冻结定值），且**仍需单独解决合规问题** —— 变更流程只解决"流程合法性"，不解决"实体合规性"。
