## TL;DR（3-5 行）

1. **基数判定 = 不触发增项、基数不动。** P0-10（L）与 P0-16（M）**均不需调整** —— 依据不是"看起来没影响"，而是：**这两项的估算是按"交付形态"（Schema + 降级）而不是"按厂商"定的**，且路线上早已写明"手环已在 P0-10"；换厂商只改**数据来源**，不改**有没有 Schema、有没有降级路径**。
2. **R2 不关闭，且不是简单"换形态"—— 必须按【对象】一分为二。** 原 R2 的对象是**调理设备（店内仪器）+ 参数下行（P0-16）**；GTL1 是**手环（客户穿戴）+ 数据上行（P0-10）**。**GTL1 提供 SDK 对原 R2 的缓解为零**（用一个手环的 SDK，去关闭一条关于仪器的风险 = 口径串了）。正确处置：**R2-甲（调理设备 · 保留改名 · 不关闭）＋ R2a（手环 SDK 可获得性）＋ R2b（手环 SDK 字段完备性）**，三者**并列**（不同对象/不同维度）。
3. **有新的外部依赖等待，必须进"不能用人日衡量"清单。** 换厂商引入了 **SDK 交付 / 商务与保密 / 技术支持响应 / 最低订货量门槛 / SDK 版本迭代 / 依赖厂商 App 配对** 等**日历约束**。建议把附录 A.2 从「三类」**扩为「四类」**（口径补充，**非人日、不进任何账**）。**关键路径判定不变 —— 手环接入仍不上关键路径**（PRD 硬约束：手环自愿、缺失不阻断、只进依从性）。
4. **P0-16 台账裁定：两个台账，必须分开。** P0-16 = **门店级「调理设备」台账**（店内仪器，型号 = 杠2 / 现有，**下行**参数）；GTL1 = **客户级「穿戴设备」数据源**（手环，**上行**数据），归 **P0-10**。二者**基数不同（1 店:N 仪器 vs 1 客户:1 手环）、方向相反、异常语义相反**，合并会造成数据模型层面的错误。
5. **文档修改点**：路线图侧 **10 处**（正文 7 · 附录 3，正文须授权）；PRD 侧 **7 处**（归析客）= **17 处，全部为文本/口径维护，0 工程人日。**

## 一、基数判定结论（不动 / 增项 二分 + 理由 + 规则④自查）

### 1.1 结论：**不触发增项、基数不动**（逐项）

| 项 | 现封版估算 | 换设备后 | 判定 | 理由（"为什么不影响"，而非"没事"） |
|---|---|---|---|---|
| **P0-10 手环数据接入与缺失降级** | **L** | **L** | 🟢 **不动** | ① **估算锚在"交付形态"，不在"厂商"**：其验收要点 = 字段 Schema + 同步失败标空缺（**不得自动补 0**）+ 未佩戴按中性 + 评估页显式暴露"缺失 N 天 / 覆盖率"。这四件事**与字段来自哪家 SDK 无关** —— 换厂商只替换**适配器**（通常是最小的一块），不改变 Schema、降级逻辑与暴露口径的**存在性**。② **换厂商不构成"更差"**：封版时的基线假设甚至**更悲观**（PRD §10 假设"设备厂商可提供**或可被适配层桥接**"，即原假设允许厂商**不开放**）；现厂商**已明示提供 SDK** → 该方向是**净改善**，**不存在上调的依据**。③ **账本早已认领**：端形态增项账 A1 行原文已写"原生能力接入…**不含**手环（**已在 P0-10**）" —— 手环的载体/接入账**已在 P0-10 内部**，**换厂商不等于开新账**。 |
| **P0-16 门店级设备台账与参数下发** | **M** | **M** | 🟢 **不动** | ① **对象未变**：P0-16 管的是**店内调理设备**（杠2 / 现有）的**参数下行**；GTL1 是**手环**（**客户穿戴、数据上行**）—— **换手环厂商，不改门店调理设备的型号枚举，也不改下行链路**。② P0-16 的估算是"台账注册 + 意图参数映射 + 审核事件触发 + 失败转待办/`device_push_failed`"这套**结构性工作**，与手环厂商**无交集**。③ 若研发评审最终认定二者**同一台账**（本文**不同意**，见第四节）→ 才需重评 M，**且仍走「待评审增项」、不得回改基数**。 |

> **一句话**：**换设备改的是"数据从哪来"，不是"有没有 Schema / 有没有降级 / 有没有台账"。** 估算锚在后者，所以不动。

## 二、R2 拆解定性（按【对象】一分为二，不是简单换形态）

### 2.1 先纠一个口径：原 R2 说的**不是**手环

对原文逐字核验（roadmap §5 风险表 R2 / PRD §10）：

| 原文要素 | 原文内容 | 指向的对象与方向 |
|---|---|---|
| R2 名称 | 「**设备厂商接口不开放，参数下发无法落地**」 | **参数下行** |
| R2 影响 | 「中——**P0-16** 技术可行性受质疑」 | **P0-16 = 调理设备** |
| R2 触发信号 | 「适配层联调连续失败；**厂商拒提供协议文档**」 | **协议下行** |
| R2 缓解 | 「先做适配层 + **人工降级**（下发失败转待办 + `device_push_failed` 留痕）」 | **下行失败**语义 |

→ **原 R2 的对象 = 门店调理设备（店内仪器）；方向 = 下行。**
→ **GTL1 事实的对象 = 手环（客户穿戴）；方向 = 上行**（"提供 SDK/API 接入你现有 App" = 让**我们读手环数据**）。

> 🔴 **本轮最容易被误判为"关闭"的一条**：**用一个手环的 SDK，去关闭一条关于店内仪器的风险 —— 属于把两个不同口径的数据当成同一件事（本团队规则③「口径 ≠ 数据」的反向）。** 因此 **R2 不得判"关闭"。**

### 2.2 正确拆法：R2 按对象一分为二 + 一维新增

| 编号 | 风险（改名后） | 对象 / 方向 | 概率 | 影响 | 缓解 | 预警信号 | 负责 |
|---|---|---|---|---|---|---|---|
| **R2-甲**（原 R2 · **改名保留 · 不关闭**） | **调理设备厂商参数下行接口不开放** | **调理设备 / 下行（P0-16）** | **中高**（维持原值） | 中 —— P0-16 技术可行性 | **不变**：先做适配层 + 人工降级（下发失败转待办 + `device_push_failed` 留痕），协议缺失不阻塞 v1；并行攻关 | 适配层联调连续失败；厂商拒提供协议文档 | 研发 + 硬件 |
| **R2a**（手环 · **新**） | **星迈 SDK 接口「可获得性」**（愿不愿给、商务条款、技术支持响应） | 手环 / 上行（P0-10） | **低**（↓，因官网已明示提供 SDK） | **中** —— 若不给，手环数据源断供，退回"人工/自报"路径；**不阻断主链路** | ① 立项即索取 **SDK 文档 + Sample + 字段清单**；② 商务与技术支持 SLA 写入对接计划；③ **零依赖兜底**：手环缺失即走既有降级（标空缺、中性、覆盖率暴露） | 索取文档/Sample **>2 周无响应**；要求**最低订货量**超试点需求；要求签保密协议却**拒给字段清单** | 硬件 + 研发 |
| **R2b**（手环 · **新**） | **星迈 SDK 「字段完备性」**（是否覆盖 PRD 要求的 7 类字段） | 手环 / 上行（P0-10） | **中高** | **中高** —— 若缺字段 → P0-10 的 Schema 需裁剪、"覆盖率"口径与"中性处理"范围扩大；**不阻断主链路** | ① **数据侧"待厂商确认清单"先行**，把"7 类字段逐个确认"设为**接口验收前置**；② P0-10 建模时**按"可缺字段"设计**（字段可空 + 覆盖率显式暴露 —— **这本就是 P0-10 的既有验收项，零新增**）；③ **若确认缺字段：收窄到可用字段 + 如实暴露缺口，不以新增开发量去"补齐数据"**（口径透明 > 数据补齐） | 厂商回复"需定制开发"；仅提供**聚合值**无原始值；**无佩戴检测**接口 | 数析 + 研发 |

### 2.3 R2b 的**可观测线索**（本文只做"规格页 vs PRD 字段"对照，**不假设 SDK 能力**）

**PRD 要求的 7 类字段**：睡眠 / 步数 / 心率 / **静息心率** / **压力** / 血氧 / 运动类型。

**厂商规格页宣称能力**：心率 / 血氧 / 血压 / 体温 / 睡眠（含分期）/ 步数 / 距离 / 卡路里 / 16 种运动模式。

> ⚠️ **对照结论（仅据已公开事实，不推断 SDK）**：规格页**未明写「静息心率」与「压力」**，而这两项是 **PRD 必需字段**。→ 这正是 **R2b 的实体**，也是 R2b 概率判"中高"的**唯一定量线索**。
> 📌 **纪律**：**规格页宣称 ≠ SDK 能力**（前者是整机卖点，后者是本项目实际可读的接口面）。**SDK 到底能读到哪些字段 / 采样频率 / 原始值还是聚合值 / 有无佩戴检测 —— 一律不假设**，交数据侧"待厂商确认清单"。

### 2.4 关系定性（**并列**，不是替代）

- **R2a 与 R2-甲：并列** —— **对象不同**（手环 vs 调理设备），互不替代、互不缓解。
- **R2b 与 R2-甲：并列** —— **维度不同**（原 R2 只问"给不给接口"；R2b 问"给了够不够用"），**R2b 是全新维度**。
- **R2a 与 R2b：并列且递进** —— 先"给不给"（R2a），再"够不够"（R2b）；**R2a 未决时 R2b 无法评估**。
- **替代关系**：**仅 R2a 一条**可视为原 R2 中"厂商愿不愿给"这半句在**手环侧**的**接续**（不是替代整条 R2）。**其余均为并列。**

## 三、关键路径与外部依赖更新

### 3.1 关键路径判定：**不变 —— 手环接入仍不上关键路径**

**结论：换厂商不改变"A 手环接入属可并行支线、不上关键路径"的判定。**

理由（技术性，非口号）：
1. **PRD 硬约束使手环不构成阻断**：手环**自愿佩戴**、**只进依从性、绝不进效果主判据**；**结构性缺失不扣分**；ARC-07/08/11 明定"**手环类缺项一律警告、不得反转为阻断**"。→ 即便 SDK 迟迟不到位，**机关门与判定链路照常交付**，只是"覆盖率 = 0 / 数据全缺"。
2. **交付形态可独立验收**：P0-10 的交付是"Schema + 降级 + 覆盖率暴露"，**Schema 可先按目标字段冻结**，SDK 到位后填值（恰是 A.2 所述"适配层可先上线"的同型做法）。
3. **降级路径已存在且被复述**：M2 演示项②"**设备参数下发或人工降级留痕**"即为此设计。
→ 故 **仍与"小程序端 / 设备适配层"并列，作为可压缩总工期的并行支线**。

### 3.2 **新增外部依赖等待**（要点 —— 人日无法衡量）

| # | 新增外部依赖 | 为什么是"等待"而非"工时" | 谁控制 |
|---|---|---|---|
| D-1 | **SDK 交付与商务前置**（保密协议 / 是否收费 / **最低订货量门槛** / 技术支持 SLA） | 官网明示"部分定制服务需达**最低订货量**" → **对方的商务节奏**决定开工日 | 商务 + 硬件（对方节奏） |

## 四、P0-16 台账范围裁定：**两个台账，必须分开**

### 4.1 明确立场（不两边都说）

> 🔴 **P0-16 管的是「调理设备」（店内仪器，如"杠2"）—— 与 GTL1「手环」是两回事、是两个台账，必须分开。**

| 维度 | P0-16「**调理设备**」台账 | GTL1「**穿戴设备**」（P0-10 数据源） |
|---|---|---|
| 对象 | 店内仪器（杠2 / 现有） | 客户腕上智能手环 |
| 归属层级 | **门店级属性**（PRD：`device.store_id`，"型号是门店级属性，**门店无权改**"） | **客户级属性**（随客户跨店移动） |
| 基数 | **1 门店 : N 台仪器** | **1 客户 : 1 手环** |
| 数据方向 | **下行**（方案意图参数 → 设备） | **上行**（设备 → 系统） |
| 异常语义 | 下发失败 → 转待办 + `device_push_failed`（**可追责**） | 未佩戴 / 同步失败 → 标空缺 + 中性 + **不得作不利依据**（**合规约束**） |
| 责任项 | P0-16 | P0-10 |

### 4.2 为什么"合并"是错的（不是命名问题，是数据模型问题）

1. **基数冲突**：同一枚举 `device.model`（杠2 / 现有）承载"门店唯一"的设备 **＋** "客户可多台"的手环 → **把两种基数混进一张表**，跨店 / 换店 / 换设备时必然出错。
2. **方向相反**：一张表管"下行"与"上行"两个方向 → **把"下发失败"与"同步失败/未佩戴"两种本质不同的异常混为一谈**。
3. **合规风险（最重）**：手环类缺项受 **ARC-07/08/11「不得反转为阻断」** 的合规约束；**混表后，这条约束可能被误用到"下发失败"上（该追责的没追责），或反之（该留痕的变成阻断）** —— 这正是本团队反复防的"口径串了"。

### 4.3 建议的区分表述与文档修改点

- **术语表新增一行**：
  > **「穿戴设备」≠「调理设备」**：**穿戴设备** = 客户佩戴的数据源（**上行**、客户级、归 **P0-10**）；**调理设备** = 门店资产（**下行**、门店级、归 **P0-16**）。**二者不共表、不共用型号枚举。**
- **P0-16 名称加限定**：`门店级设备台账与参数下发` → **`门店级「调理设备」台账与参数下发`**（正文 §1 交付物名 + §3 支线描述 + PRD P0-16 验收同批）。
- **数据模型**：`device` 表**保持门店级不动**；**若**确需登记手环型号 / SDK 版本（客户级），**作为 P0-10 的数据源登记**，**不并入 `device` 表** —— 且**此为 P0-10 内部实现，不新增编号、不新增账**（是否需要的判定，见第七节问项 #3）。

### 5.2 新增：手环维度的**软性偏好（非硬标准）**

> **软性偏好（非硬条件）**：在 2~3 家试点中，**优先选至少 1 家"安卓用户占比高 + 客户年龄结构偏高"的门店** —— **作为「取数优先」而非「验证优先」**，用以**主动暴露手环配对链路难题**（必须经厂商 App 连接、安卓防后台被杀、中老年客户操作能力）。

**为什么是"软性偏好"而非"硬标准"（三条理由，缺一不可）**：
1. **选店已被三重约束占满**（直营 / 加盟 / 老设备），**再硬加一维可能选不到店**；
2. **该偏好服务于"暴露问题 / 取数"，不是"验证结论"** → **不达标不构成退出条件**；
3. **与 v1.1 F 节先例一致** —— "同源元数据留存"曾经是**硬标准**、后被**撤回为软性偏好**；**同一纪律不重复犯错**：能用软性偏好达成的目的，不升级为硬门槛。

**📌 用户侧（瑞思）追加 —— 把"用途"写明（本文采纳）**：本偏好**不服务"验证结论"，而服务"取数"**。试点店在**准入时顺带记录三项**：**客户年龄段 / 手机系统（安卓 or iOS）/ 是否家属代操作**。
- 这三个数即本件 **Q-G6（有智能机+微信占比 / 家属代持占比）** 的答案，**决定"门店代配对"要承担多少量**；
- **年龄段**：建档已有（PRD `customer.age` int 必填 + `age_group_locked` 8 组分龄）→ **0 新增**；
- **手机系统 / 是否家属代操作**：🟢 **不进产品字段表、也不是待评审增项** —— 用户侧第二轮已裁定（三条理由）：① P0-03 建档必填项是**业务必需**的（基本信息 + 健康史 + 主诉），插"您用什么手机"**没有业务理由**，客户会问"治病为什么要问我手机型号"，**与 PIPL 最小必要相冲**；② 这两项**只在手环场景下才有意义**（不戴手环者采集纯冗余）；③ **本质是"取数的实验字段"，不是"产品字段"**。
- → **处置**：挂在**实验 A（试点实验）记录表**作为**一次性观察项**（实验 A 本就要求记录每客户卡点 / 是否家属代做 / 断连原因，**这两项是其天然列**）→ **产品侧 0 新增、实验侧 0 研发人日、Q-G6 照样拿到答案**。
- ⚠️ **唯一例外**：若业务方要把"手机系统"做成**长期分层的运营口径**（如"按安卓 / iOS 分组看佩戴率"），才必须成为产品字段 —— **那是业务方的运营需求，应由业务方发起，路线图侧不替其预设**。

> **可直接落的写法（用户侧提供、本文采纳）**：`取数口径（年龄段 = 建档已有 0 新增 / 手机系统 + 家属代操作 = 试点实验一次性观察项，不进产品字段表；若业务方要长期分层则须业务方另行发起）`

**为什么把用途写明**：避免后面被要求"**用这个偏好去证明佩戴率**" —— **取数 ≠ 验证**，两者不可互相顶替（规则③「口径 ≠ 数据」）。

**配套（不改验收标准）**：M2 演示时**如实呈现**一项观测数据 —— 手环**实际配对成功率 / 有效佩戴率**（属"如实呈现"，**不是新增验收阈值**）。

> ⚠️ **两点纪律**：① 此为**选店软性偏好，不得升级为硬标准**（理由同上）；② **不产生新增人日**（选店与观测口径属规划/运营动作，非工程工时）。
