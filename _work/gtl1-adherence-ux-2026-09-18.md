**关联**：PRD P0-02 / P0-09 / P0-10 / P0-17、§5.3 AS v2、§7.3 判定规则、§11.4 R4b、roadmap R13b、`design-brief-tiaoyun-2026-09-17.md` §六-3

## TL;DR（5 行）

1. **GTL1 是一条"手机中转"链路，不是"手环独立"链路** —— 手环不自己联网，数据必须经**客户自己手机上的第二个 App（即米运动健康）**常驻后台才能上来。这决定了后面所有问题。
2. **放弃率最高的一步 = 蓝牙配对（尤其是"手机系统蓝牙已连过 → 厂商 App 阻断搜索 → 必须先『忽略此设备』+ 重启手环"这个陷阱）** —— 它是**硬失败**（卡住 = 零数据），不是衰减；且操作反直觉，中老年客户不具备该知识，手册明写会发生，属**设计性高频失败**，不是偶发。
3. **最危险的不是"戴不上"，而是"戴了但系统以为没戴"** —— 本件列出 **8 个会被误判为「行为性缺失」的场景**（§四），其中**住院/洗浴/桑拿摘除**与**安卓后台被杀**是最硬的两条：前者是**厂商说明书要求的合规使用**，后者客户毫无过错。
4. **PRD 现有的「结构性 / 行为性」二分法在 GTL1 链路下不够用** —— 建议至少新增**「技术性缺失」**与**「合规摘除」**两类；若业务方不同意增类，**最低限度必须把技术性缺失并入「结构性」处理（不扣分）**，绝不能默认计 0。
5. **准入向导里现在就问"愿不愿意戴手环"问得太早**，而且**这个"太早"会直接制造误判**：客户随口答"愿意" → 系统写 `applicable=True` → 两周后因设备原因没数据 → **被我们自己的规则判成"行为性缺失扣分"**。建议**保留表单原位、改意愿语义、并在第 1~2 次调理后加一次体验式重申**。
6. **★ 以上 1~5 的成立范围受"接入形态"约束** —— 本件 §一/§二 只在**形态②（厂商云 API）/③（健康平台中转）** 下成立；若走**形态①（SDK 直连我方 App）**，客户不装厂商 App，但**要装我方原生 App，与「客户 = 小程序」这条业务硬约束正面冲突 → 需业务方重新裁定**。**三种形态的对照与差异见 §一附 —— 接入形态是本件最高优先级的阻塞项。**

## 一、客户侧逐步链路与放弃点

> **⚠️ 本节成立条件 = 形态②或③（客户使用厂商 App「即米运动健康」）。** 形态①（SDK 直连我方 App）下客户根本不装厂商 App，本节 S3~S10 大部分不适用 —— **三种接入形态的差异见 §一附**。本节不该被当成唯一事实。

### ⚠️ 先说一个必须交给业务方确认的分叉点（阻塞项）

**这份 GTL1 是「门店发」还是「客户自购」？两种情形链路完全不同，本件无法替业务方裁定。**

| | **情形 A：门店发（发放/租借/含在疗程内）** | **情形 B：客户自购** |
|---|---|---|
| 设备成本 | 门店/品牌承担 | 客户承担 |
| 谁拆封/激活/充电 | **门店可在客户不在场时先做**（拆封、充电激活、开机、验机） | 客户自己 |
| 谁装 App / 谁配对 | **必须用客户本人手机** → 门店只能在**客户在场时**做 | 客户自己（或家人） |
| 出问题谁兜 | 门店（客户会拿回来问） | 客户自己找厂商客服 |
| 与 R4b 的关系 | **直接加重门店执行负担**（新触发源） | 门店负担轻，但**放弃率显著上升**，A3 覆盖率崩塌 |
| 与「不强制佩戴」的关系 | 要小心：**"门店发的"容易被客户理解为"店里要求戴"**，实质弱化了"完全自愿" | 自愿性更纯粹，但**选择不买 = 客户自己承担不便** |

**关键判断（本件最需要业务方拍的一条）**：
> **即便是「门店发」，门店也无法替客户完成手机侧配对** —— 配对必须在客户本人手机的厂商 App 内完成（手册明确）。所以"门店发"**只省掉了设备钱与拆封激活**，**省不掉**"装第二个 App + 注册 + 授权 + 蓝牙配对 + 保持后台"这一整段。**这一段才是放弃率的所在。**
> **→ 因此无论 A 还是 B，用户侧的核心困难都是一样的；差别只在"谁在场承担"。**

〔推断〕两种情形在真实门店中可能**并存**（早期自购自用、后期门店配套），建议业务方**明确单一形态**，否则培训包与话术无法收敛。

### 1.1 逐步链路拆解（60~75 岁客户 · 以情形 B 自购为主，A 的差异另注）

| # | 步骤 | 具体动作 | 放弃风险 | 失败性质 | 门店发的差异 |
|---|---|---|---|---|---|
| S0 | 拿到设备 | 拆封、清点（手环 + 磁吸充电线） | 低 | — | 门店可代做 |
| S1 | **充电激活** | 磁吸线接触电源 → 即激活（充满约 2h） | **中** | 磁吸线**接口无方向但易滑脱/易丢**；客户可能不知道"必须先充" | 门店可代做（可预充满） |
| S2 | **开机** | 长按触摸键 3 秒 | 低 | 0.96" 单点触控屏，无多点触控；中老年对"触摸键在哪"常有困惑 | 门店可代做 |
| S3 | **下载 App** | 应用商店搜「即米运动健康」 | **中高** | ① 会搜到同名/近名 App；② **国内版「即米运动健康」/ 海外版「Runmefit」两个名字**，易错装；③ 部分安卓机应用商店无此 App → 需浏览器下 APK（**中老年几乎不可能独立完成，且 APK 有安全风险**） | 门店可在客户手机上代下载（**必须是客户手机**） |
| S4 | **注册 / 登录** | 手机号 + 短信验证码（推断） | **中高** | 验证码收不到 / 被拦截 / 不知如何查看；老人手机常为家人代持号码 | 门店可现场代做 |
| S5 | **授予权限** | 蓝牙权限、**定位服务**、通知、**后台运行**、**电池优化白名单/自启动** | **高（安卓）** | 安卓需**多层系统设置**，且各品牌 ROM 路径不同；漏一项 = 后台被杀（回到 S8 的静默失败） | 门店可现场代做，**但不同机型路径不同 → 培训包必须含机型清单** |
| S6 | **App 内搜索设备并配对** | App 内搜索 → 选中 `GTL1-xxxx` → 连接 | **★ 最高** | **手册明写的陷阱**：若手环已被**手机系统蓝牙**连过，**厂商 App 会主动阻断搜索** → 需先到**系统蓝牙设置「忽略此设备」**、**重启手环**、再回 App 重连。**这是反直觉操作，中老年不会自我诊断，一定卡死。** iOS 同理（苹果系统蓝牙默认连回该设备 → App 检测不到 → 同样要"忽略此设备"） | 门店可现场代做（**门店可能是唯一能过这一步的地方**） |
| **S6b** | **（另一条接入方式特有）"准后台"窗口保活** | 若走**微信蓝牙后台能力**的准后台方式（客户配对后，**一定时间窗口内**退到后台仍能同步；**超窗后仍需重开小程序**） | **★ 高（新增失败层）** | **继承 S6 全部摩擦，并新增一层本件 §一 原链路没有的失败**：⚠️ **窗口何时失效客户无从感知** —— 表现为"**有时能同步、有时不能**"。**这不是"没戴"，是"同步时点没踩上窗口"** → 极易被误读为依从问题。**→ 见 §四 M9。** | 同 S6 |
| S7 | 日常保持近距离 | 手环与手机需在蓝牙范围内 | 中 | 手机不在身边（做家务/午睡/出门忘带）= 无数据 | 同 |
| S8 | **保持 App 后台存活** | 安卓：App 需常驻后台，**即使后台也不能被系统杀掉** | **★ 高（隐形）** | **国产 ROM 的"省电/清理"仍可能杀进程**。这是**静默失败**：客户以为戴了，系统显示没数据 | 同上，**门店无法远程解决** |
| S9 | **定期充电** | **续航 5~7 天**（待机 45 天≠可用 45 天） | **高（重复发生）** | 客户按"待机 45 天"理解 → 实际 5~7 天就没电；**磁吸线易丢**；不充电 → 手环彻底静默 | 门店可提供"到店免费充"/提醒 |
| S10 | 数据上行 | 手环 → 客户手机 App → **厂商云** → 调元云 | **未知（结构性前提）** | ⚠️ **依赖厂商是否提供 API/SDK/开放平台**。若不提供，**前面 9 步全做完也拿不到数据**（见 §六 · 结构性不可观测） | 同 |

### 1.2 「放弃率最高的一步」判断与依据

**★ 最高放弃点 = S6 蓝牙配对（含 iOS/安卓同一陷阱）**

依据（三条，均为推演但指向一致）：
1. **硬失败**：S6 卡住 = 全链路零数据，与 S9 的"衰减"、S3 的"装错版本"不同，它**没有部分成功**。
2. **反直觉**：正确解法是「去系统蓝牙里**删掉**一个已连上的设备」，这与"连不上就多连一次"的本能相反。**客户不会自我诊断，只会反复重试或放弃。**
3. **设计性高频**：手册是**主动写出来**的注意事项，说明厂商自己知道这是常规发生的问题 —— 不是边角故障。

**★ 次高、且对误判更危险 = S8「App 被系统杀掉」**
它不表现为"放弃"，表现为**"客户以为戴着、系统以为没戴"** —— 这正是 §四 要解决的冤判源头。

〔推演〕若不做任何干预，**"走到 S10 且连续 7 天有数据"的客户占比，本件估计明显低于"愿意佩戴"的客户占比** —— 但**具体数字本件拒绝给出**，因为无实测数据；请以 §七 实验 A 的实测结果为准。

### 1.3 与既有依据的一致性

- Hermsen et al., JMIR mHealth 2017（PMID 29084709）已入 PRD：**停用主因中"设备故障 / 没电 / 丢失"占停用者 56.7%**。GTL1 是**手机中转型**，其"故障面"比 Fitbit 那种"手环直连手机"更大（多了 App 常驻、权限、双蓝牙冲突三层）→ **衰减依据在本链路只会更适用，不会更宽松。**
- 移动健康 App 30 日留存 3%~8%（AppsFlyer/Adjust 2023）→ **即米运动健康对客户而言是"零使用动机的通用运动 App"**（客户要的是调理，不是看步数），留存预期应取下限。

## 一附、三种接入形态下的链路分叉

> **背景（数析 §2.0 发现）**：厂商官网原文「二次开发：由我们提供 SDK/API 接口，**接入您现有的 App**」→ 数析判定 **SDK 宿主 = 原生 App**（`.aar` / `.framework`），而**客户侧载体 = 微信小程序** → **原生 SDK 无法嵌入小程序**。故接入形态有三种并列可能，**本件三种并列评估，不预设①为定案**。
> **纪律**：用户原话「这是星迈 GTL1 智能手环的 SDK」**暗示**①，但**"SDK"这个词不携带能力信息**（有 SDK ≠ SDK 能嵌小程序 ≠ 能拿到佩戴数据）—— **不能把暗示当事实**。

### A.1 三列对照

| | **形态① SDK 直连** | **形态② 厂商云 API** | **形态③ 健康平台中转** |
|---|---|---|---|
| **数据通路** | 手环 →（蓝牙）→ **我方原生 App**（内嵌厂商 SDK）→ 我方云 | 手环 → 厂商 App → **厂商云** →（API）→ 我方云 | 手环 → 厂商 App → 厂商云 → **HealthKit / Health Connect** → 我方 |
| **客户要装什么** | **我方原生 App**（**不装厂商 App**） | 我方（小程序）+ **厂商 App** | 我方（小程序）+ **厂商 App** |
| **厂商是否已具备** | 宣称有 SDK，**能力未知** | **大概率不存在** | ✅ 已具备 |
| **小程序内可用** | ❌ | ✅（服务端对接） | ❌ |
| **佩戴检测（on-body）** | **取决于 SDK 是否暴露**（未知） | **取决于厂商**（未知） | ❌ **不可能** |
| **本件 §一 链路（S3~S10）** | **大部分不适用** | ✅ 成立 | ✅ 成立 |
| **A3 数据可得可能性** | **取决于 SDK 能力**（未验证前按"不可得"记账） | **取决于厂商开放度**（未验证前按"不可得"记账） | 中（渠道成熟，但**仍依赖厂商是否写入健康平台**） |
| **放弃点排序是否要改** | **要改**（见 A.2） | 本件 §一.2 有效 | 本件 §一.2 有效 |

### A.2 ★ 形态① 下 S6「蓝牙配对陷阱」是否仍是最高放弃点？

**答案：仍然成立（是）。但依据分两级，且有一处必须标"需实测"。**

**先看手册原文的两句（本件引用的原始事实）：**
1. 配对流程：「下载即米运动健康 App → 开启手机蓝牙 → **App 内搜索设备** → 选中手环名称连接」
2. 阻断说明：「App 在搜索附近的设备时，**会自动阻断已通过手机系统蓝牙连接的设备**」（需先到系统蓝牙「忽略此设备」、重启手环，再回 App 重连）

**关键推理（区分"机制来自哪一层"）：**

- **可确证的部分（来自设备/系统层，与宿主无关）**：手册这句写的是 **"App 在搜索……时会阻断"**，但在**手册语境下，那个 App 就是厂商唯一的 App** —— 手册没有、也不可能描述"换成第三方 App 会怎样"。**因此这句原文只能证明"厂商 App 会阻断"，不能证明"任何 App 都搜不到"。** ⚠️ **这一点必须明确标注：手册未说明阻断发生在哪一层。**
- **但有一条独立于原文的结构性依据，指向"设备/系统层"，且与宿主无关**：
  > **BLE 连接的**物理独占性** —— 一个 BLE 从设备在同一时刻通常只能维持一条连接（或极有限的连接）。若手环已被**手机系统蓝牙**占住连接，我方 App 即便发起扫描，**扫到的广播可能受限、或连接建立被拒**。
  > **且 iOS 侧的机制更明确**：手册写"苹果手机连接一次后，**系统蓝牙会默认连上该设备**，需忽略 App 才能检测到" —— **iOS 的系统级自动回连是操作系统行为，不是我方 App 能绕过的**（这是 iOS 对已配对 BLE 外设的既有行为）。
  > → **结论：iOS 侧 S6 陷阱与宿主无关，形态① 下依然成立，几乎可以确定。**
- **安卓侧存在真正的未知**：安卓对 BLE 的连接管理更宽松，**理论上存在"我方 App 直接扫到并接管连接"的可能** → **此处不得推测，必须实测**。

**→ 因此对 team-lead 问题的回答：**

| 子情形 | S6 是否仍为最高放弃点 | 依据 |
|---|---|---|
| **iOS** | **是** | 系统级自动回连是 OS 行为，任何 App 都绕不过（手册明写"需忽略 App 才能检测到"） |
| **安卓** | **大概率是，但需实测** | BLE 物理独占性指向"设备/系统层"；但手册未说明层归属，**存在我方 App 绕开的理论空间** |
| **整体判断** | **是**（若维持"安卓也成立"，则 S6 结论无需改） | 即使安卓可绕开，**"双方都在抢同一条 BLE 连接"这个冲突源仍在** —— 它只是从"搜不到"变成"连不稳"，**放弃点可能从 S6 前移到 S5（权限）或后移到 S8（保活）**，但**不消失** |

**⚠️ 一处诚实标注**：**手册未说明阻断发生在手环/US 系统蓝牙层、还是厂商 App 的实现层。** 本件倾向"设备/系统层（尤其 iOS 已确定）"，但**安卓侧须实测**。
→ **这条正好挂到实验 B**：我已在 §七 实验 B 补一行——**若形态① 成立，实验 B 须增加"用第三方 BLE 工具（不装厂商 App）尝试连接已系统蓝牙占用的手环"这一组**，用来判定阻断层归属。

### A.3 形态① 的客户侧代价（★ 这是本件要工具级提示的第二处）

**（1）对 60~75 岁客户的可得性：装"门店的业务 App"比装"通用运动 App"更难还是更易？**

**答案：'更易'与'更难'同时成立，净效应为"更难"，且难点性质变了。**

| 维度 | 装「即米运动健康」（通用运动 App） | 装「调元云 App」（门店业务 App） |
|---|---|---|
| **安装动机** | **弱** —— 客户要的是调理，不是看步数；"我为什么要在手机上装个跑步软件？" | **更强** —— 与自己的调理直接相关，门店**可以给出理由**（"这是您的健康档案，方便看自己的变化"） |
| **对 App 的信任** | 中立（不知名但无害感） | ⚠️ **更敏感** —— "门店让我装个 App"会触发"是不是要卖我东西/是不是监控我"的疑虑（**与 §五 的"被监测"不适同源**） |
| **安装渠道** | 应用商店通用 | 同上，但**门店自研 App 更可能不在部分应用商店**，需扫码/浏览器装 APK → **中老年几乎不可能独立完成** |
| **安装后是否还要注册** | 是（手机号+验证码） | **可以用微信登录 / 或由门店预置**（我方自研，可控） → **这一项形态① 反而更易** |
| **权限清单** | 蓝牙+定位+通知+后台+电池白名单（**五层**） | 同样需要（蓝牙+后台保活），**但定位服务可省**（形态① 不需要厂商 App 那套定位要求） → **略优** |
| **失败后的可求助对象** | 客户自己找厂商客服（**帮不上**） | **门店**（这是门店的系统）→ **这一项形态① 明显更易** |
| **净判断** | — | **"更难"**：安装动机虽增强，但**触发隐私疑虑 + 安装渠道不可控**；不过**失败可求助门店**这一点显著改善了兜底 |

**→ 一句结论**：形态① **把"装一个莫名奇妙的运动 App"换成"装一个门店让我装的 App"** —— **动机更强、兜底更好，但隐私敏感度更高、安装渠道更不可控**。**净效应仍是负向**，因为**"零安装的小程序"这一条不可逆的体验优势被放弃了**。

**（2）是否与「客户 = 小程序」这条业务硬约束冲突？→ 明确回答：冲突。**

> **「客户 = 微信小程序」是业务方已裁定的硬约束（端形态裁定）。形态① 要求客户安装我方原生 App。**
> **这不是我能消化的技术细节，这是一次业务裁定的变更。**
> 本件**不自行消化**，明确写成：
> **⚠️ 形态① = 需要变更业务裁定（客户侧从"小程序"扩为"小程序 + 原生 App"），必须由业务方重新裁定，否则不可采纳。**

**（3）与 §五（引导时机）的连带影响**
若走形态①，客户要在**准入向导阶段就装我方 App** → 这会把"装 App"塞进**本已过重**的准入三步（禁忌筛查→建档→签同意书）里 → **§五 的"太早"问题会进一步恶化**（客户还没体验服务就要装门店 App）。→ **形态① 必须配"装 App 延后到第 1 次调理后"的体验式引导**，否则准入转化率会掉。

### A.4 三种形态下的结论覆盖范围（防误用）

> **★ 形态选择同时决定两件相反的事（务必并列读，勿只引一半）：**
> - **形态③ 对「数据可得性」是利空** —— 健康平台中转必然丢实时性、断连期最长 → **不可观测占比最高**；
> - **形态① 对「字段可得性」是利好** —— 我方自建 App，`device_unbind` / `pause_period` 判据在自己手里 → 判据可执行性上升（**但前提是不与「客户=小程序」冲突，载体未定前不得当作已成立**）。
> → **因此「不可观测占比」必须按形态单列，不得三形态平均**（否则形态③ 的"根本不可用"会被形态①/② 拉平掩盖）。此点已与数析 §1.8 建议 #11 对齐。

| 本件章节 | 形态① | 形态② | 形态③ |
|---|---|---|---|
| §一（S0~S10 链路与放弃点） | **大部分不适用**（S3~S10 替换为我方 App 链路） | ✅ 适用 | ✅ 适用 |
| §一.2（S6 为最高放弃点） | **iOS 适用 / 安卓待实测**（见 A.2） | ✅ 适用 | ✅ 适用 |
| §二（两个 App 的负担） | **不适用**（只装我方 App，是"一个 App"）—— 但 §二.2 方案 C/E 与"成本转移"框架**仍可复用** | ✅ 适用 | ✅ 适用 |
| §三（门店代配对负担） | ✅ 适用（代配对动作仍在） | ✅ 适用 | ✅ 适用 |
| §四（8 个误判场景） | ✅ 适用（M1~M8 在形態① 下大多仍会发生，**但 M1/M8 的成因从"厂商 App 被杀"变为"我方 App 被杀"**） | ✅ 适用 | **M2/M5 更严重**（健康平台中转**必然丢实时性**，断连期更长） |
| §五（引导时机） | ✅ 适用，**但恶化**（还要装 App，见 A.3(3)） | ✅ 适用 | ✅ 适用 |
| §六（残余风险） | U3 由"厂商是否开放"变为"**SDK 是否真能拿到佩戴数据**" | ✅ 适用 | ✅ 适用 |

> **一句总结**：**本件 §一/§二 只在形态②/③ 下成立；§三/§四/§五 在三种形态下都成立；形态① 的核心代价不只在技术，而在于它要求变更「客户=小程序」这条业务硬约束。**

## 二、两个 App 的负担与化解方案

> **⚠️ 本节成立条件 = 形态②或③（客户需另装厂商 App）。** 形态① 下客户只装我方一个 App，本节"两个 App"的前提不成立 —— **差异见 §一附 A.3**；但 §2.2 的**"成本转移对象"分析框架**在三种形态下通用。

### 2.1 负担评估

客户侧实际上有**两套并行的数字负担**：

| | 调元云小程序（P0-09 每日填报） | 即米运动健康（GTL1 配套） |
|---|---|---|
| 安装 | **零安装**（微信内即用） | **需下载原生 App** |
| 注册 | 微信授权 | 手机号 + 验证码（推断） |
| 权限 | 订阅消息（有既有动作挂载点） | 蓝牙 + 定位 + 通知 + **后台常驻** + 电池白名单 |
| 使用动机 | 强（与自己的调理直接相关，有即时反馈） | **弱（通用运动健康 App，与门店无绑定）** |
| 失败后果 | 少填一天，有补填窗口 | **零数据，且客户不会知道** |

**结论（中老年客户）**：
> **小程序是"低门槛 + 强动机"，即米 App 是"高门槛 + 零动机"。把后者压在前者身上，是本次换型引入的**最大用户侧新增成本**。且它不是"慢慢衰减"的问题 —— **它是"第一步就装不上"的问题**。
> 更麻烦的是：**客户不会把"手环没数据"归因于 App**，他会归因于"店里发的这个东西不好用" → **信任损耗落在门店，而不是落在 App 上。**

### 2.2 化解方案清单（含**成本转移对象**）

| 方案 | 做法 | 效果 | **成本转移给了谁** | 与 R4b 的关系 |
|---|---|---|---|---|
| **A. 门店现场代配对** | 客户在场时，用**客户本人手机**一次性做完 S3~S6 | 直接跨过最高放弃点 | **门店（调理师/经络师）** | ⚠️ **直接叠加**：新增一项门店作业纪律，需进培训包，需计时付薪 |
| **B. 门店预装预注册** | 门店代装 App、代注册账号 | 同上，但**注册账号涉及客户手机号与短信**，需客户在场 | 门店 | 同 A；且**账号归属客户，后续换机/换号会脱钩** |
| **C. 不经厂商 App，走系统健康库中转** | 数据由手环 → **iOS HealthKit / Android Health Connect** → 调元云 | 客户**零额外安装**（若系统健康 App 已存在），动机问题消失 | 转移给**研发/厂商**（需确认 GTL1 是否支持写入系统健康库） | **低**（门店无新增动作）→ **若可行，这是最优解** |
| **D. 门店侧设备采集** | 客户到店时，由门店用一个 App/设备读走数据 | 只解决**到店当天**的数据 | 门店 | 中；**但解决不了居家 6 天的空白** → 作为兜底，不能作为主方案 |
| **E. 换设备** | 换成支持系统健康库同步 / 有开放 SDK 的手环（如华为 Health Service Kit 生态） | **根治**：把"第二个 App"换成"系统级健康库" | 转移给**业务方**（重新选型 + 已购 GTL1 沉没成本） | 低 |
| **F. 家人代操作** | 由子女帮装帮配 | 见效于有子女在身边的客户 | 转移给**家属**（不常在身边、不熟悉门店业务、换机后需重来） | 低（但不可控） |
| **G. 明确"不追求佩戴数据"** | 接受 A3 常态 `applicable=False` | **完全合规且设计上可接受**（A3 权重 0.20，结构性缺失不扣分） | 转移给**判定引擎的数据完整度** | **零** |
| **H. （"准后台"方式下的**新增**成本）厂商 App 注册节点前置** | 走**依赖厂商 App 的接入方式**时，客户侧**必然新增一次**：「装即米 App + 手机号注册 + 短信验证码」 | ⚠️ **不是"多装一个 App"，而是"多交一次手机号 + 过一次短信验证 + 多一次隐私授权"** | **转移给客户本人**（隐私疑虑 + 操作负担）；**门店无法代收验证码** → 门店兜底能力被削弱 | ⚠️ **比 A/B 更重**：A/B 至少是"门店可控的流程"；**这一处是"厂商 App 的注册流程"，我方既不能简化、也不能兜底**。**与§二.2 方案 B 同源，但它是必然而非可选** —— 只要走依赖厂商 App 的方式，这一处**不可规避** |

### 2.3 一条必须先纠正的读法

> **A3 权重只有 0.20，且"未同意佩戴"结构性缺失不扣分 —— 也就是说，从系统设计上，「客户不戴」本来就是可接受的。**
> **因此，化解方案的正确目标不是"让所有人都戴上"，而是：**
> **① 让真戴上的人「数据别掉链子」；② 让不戴的人「不被冤枉」。**
> 把目标错设为"提高佩戴率"，会推出"半强制"的运营动作 —— 那与「不强制佩戴 / 拒绝佩戴不得降低服务等级」的硬约束正面冲突。

### 2.4 规则⑤检查（若建议取消某个客户可见项）

若采纳**方案 C 或 E（客户不再自己装厂商 App）**，必须先回答"**客户原来靠它做到的是什么**"：

| 客户原来靠厂商 App 做到 | 同等效力替代物 |
|---|---|
| 知道"我的数据有没有在被采集"（掌控感） | **小程序内加一个只读的"我的佩戴状态"卡**（近 7 天是否有数据、上次同步时间），**文案中性、不出现"你没戴"的指责式表述** |
| 换手机 / 换号后能自主重配 | **门店"重配"服务入口**（客户到店即可，不用自己折腾） |
| 能看到自己的步数/睡眠（自我激励） | 若确有此需求，可由**小程序回显一条趋势**（复用 P0-09 填报的"即时反馈"位置），**不新增第二个 App** |

**没有替代物就不建议取消** —— 否则客户会失去"数据是否在被采集"的唯一可见入口，反而制造新的信任问题。

## 三、门店侧执行负担估算（推演）

> 全部为**结构化推演**，无实测。请以 §七 实验 A 的实测计时为准。

### 3.1 单客户耗时推演

| 动作 | 顺利 | 常见 | 最坏 | 说明 |
|---|---|---|---|---|
| 现场协助配对（S1~S6，一次） | 8~12 min | 15~25 min | 30~40 min | 常见情形 = 遇到系统蓝牙冲突要「忽略 + 重启手环」；最坏 = 客户手机老旧、需重启、验证码收不到、需指导多层权限 |
| 电量/断连排障（**每月 1 次**，推断） | — | 3~8 min | 15 min | 多为电话远程指导（"您把蓝牙打开看看"） |
| 充电提醒（每 5~7 天一次） | — | 1~2 min | — | 若走系统推送/门店群通知，可摊薄 |
| **单客户首次投入合计** | **≈10 min** | **≈20~30 min** | **≈50 min** | 含后续首个周期的排障 |

### 3.2 门店高峰期是否可行

**判断：不可行，若按"现场一次性完成"来设计。**

依据（均来自既有设计约束）：
- `design-brief-tiaoyun-2026-09-17.md` §四：门店现场 = **手可能潮湿、站立操作、常在走动中、点击目标 ≥44pt、避免精细操作** → **不适合连续 20~40 分钟的"手机设置类"精细操作**（这是与调理服务完全不同的动作类型）。
- 20~40 分钟**连续占用一名员工**，在高峰期等于**少接一位客户**。
- 承担者是**经络师 / 门店负责人**（= P0-19 的代录人集合），**他们同时也是最忙的两个角色**。

**可行做法（建议）**：
1. **放到低峰时段或专门的"设备服务台"**（不占调理师的服务间隙）；
2. 或**改为"客户到店前 10 分钟到店"**的预约式设置（把成本前移、不占服务时间）；
3. 若业务方要求"必配"，**必须显式计入人日/运营成本，不可免费挂靠门店培训包**。

### 3.3 与 R4b 及「门店培训包」的衔接

- 现有口径：**门店培训包 = R4b / R4c / R4d / "门店作业方式改变引发执行抵触" 四条风险的共同缓解，不可延后于 P0-19 上线**（roadmap v1.26 订正）。
- **本件给培训包新增第 5 条作业纪律：「手环代配与排障」。** 同时它给 **R4b 增加了一个新的触发源**（代录之外的第二种门店执行动作）。
- **一个有利于执行的性质差异（值得写进培训包）**：
  > **代录退款是"客户不在场、结果不可见、心理成本高"的动作（≡ user-memo B′-3）；代配手环是"客户在场、当场看得见成果、心理成本低"的动作。** 因此**代配的执行率应显著高于代录** —— 这不能减轻它的时间成本，但**可以减轻"门店不愿做"的动机阻力**。培训话术可以把这一条讲清楚，帮门店把代配定位成"专业服务的一部分"而不是"额外负担"。
- **⚠️ 但要防一个新的诱导**：若门店把"帮客户戴上"当成**自己的 KPI 或门店健康度加分**，会推出**半强制佩戴** → 直接违反"不强制佩戴 / 不降低服务等级"硬约束。**建议明确：手环相关指标一律不进门店健康度排名（HSI 现有八项已不含手环，应保持）。**

## 四、误判场景清单与判定建议（★ 本件最重要）

### 4.1 问题本质：GTL1 把「戴了」和「没戴」在数据上变成了同一个东西

> PRD 只有两类：**结构性缺失（未同意佩戴 → 不扣分）** ／ **行为性缺失（同意却漏戴 → 缺失天计 0）**。
> **但 GTL1 链路上，一个"同意佩戴且真的戴了"的客户，可以因为以下 8 种与他的意愿和努力毫无关系的原因，在系统里表现成"零数据" —— 然后被按「行为性缺失」计 0 分。**
> 这不是"数据缺失"，这是**系统性冤枉**。下表逐个列出，并给判定建议。

### 4.2 八个误判场景

| # | 场景 | 系统看到什么 | 真实性质 | **判定建议** |
|---|---|---|---|---|
| **M1** | **安卓系统杀掉了厂商 App**（即使做了权限配置，国产 ROM 仍可能杀） | 连续 N 天零数据，无任何卸载/解绑事件 | **技术性**（设备/系统原因，客户零过错） | **归「技术性缺失」，不扣分。** 识别特征：① 此前有稳定有效佩戴记录；② 断点**突变**（前一天有、后一天无）；③ **无 `app_uninstall` / `device_unbind` 事件**。→ **建议 PRD 必须新增事件字段 `app_uninstall` / `device_unbind` / `unbind_reason`**，否则系统无法区分 M1 与"客户主动放弃"。 |
| **M2** | **客户戴了，但没带手机 / 手机没电 / 蓝牙关了** | 同上，零数据 | **技术性 + 结构性不可观测（见下）** | 若厂商支持**断连后回补同步** → 归技术性，不扣分；**若本地缓存不可回补 → 归「结构性不可观测」（客观拿不到），不得计 0**。⚠️ 本项**必须由实验 C 定性**（见 §七）。 |
| **M3** | **客户不会充电 / 磁吸充电线丢了** | 数据在电量耗尽后中断直至下次充电 | **首次 = 设备性；重复 = 行为性** | **建议"先免责一次、再追责"**：**首次电量耗尽不扣分**（= 系统/门店未完成引导，责任不在客户）；**仅当系统已推送过充电提醒、且客户在提醒后仍连续 N 天不充电，才计入行为性。** → 需新增字段 `charge_reminder_sent_at`。 |
| **M4** | **住院 / 洗浴 / 桑拿期间按说明书摘下** | 数天至数周零数据 | **★ 合规摘除**（**厂商说明书要求**：IP68 但不可游泳/潜水/热水淋浴/桑拿，水蒸气会损坏） | **★ 明确归「合规摘除」，不扣分。** 且**系统应支持「暂停期（pause）」申报**（客户/门店申报住院、医疗期、长期外出），**暂停期从"应戴天"分母中剔除**。**依据强度最高的一条** —— 因为它是**厂商自己要求客户摘下**的，把合规使用判成不依从，逻辑上无法辩护。 |
| **M5** | **家人代操作，家人不在身边**（数据在家人手机上） | 客户名下长期零数据 | **结构性（caregiver-mediated）** | 若"绑定设备 = 家属手机"或"客户无微信" → 该客户 A3 应视为 **`applicable=False`（结构性）**，并标 `self-report / caregiver-mediated`。⚠️ **需与 P0-09 代核、P0-02 代签的口径保持一致**（家属代办是否算数，是同一个问题的三处）。 |
| **M6** | **45 天待机 vs 5~7 天续航的认知落差** | 客户以为能"45 天不用管" → 实际 5~7 天没电 | **厂商文案导致的系统性预期错位** | **首次电量耗尽不扣分**（同 M3）；且**引导环节必须显式纠正**："手环需**每 5~7 天充一次**，不是 45 天。" **这一句应写进知情同意/引导话术，不得省略。** |
| **M7** | **换手机 / 换微信 / 系统升级后需重配** | 重配期间零数据（且可能再次踩 S6 陷阱） | **结构性事件** | **应支持「设备迁移」态**，迁移期不计入缺失；迁移**由门店协助**（不指望客户自己重走一遍 S3~S6）。 |
| **M8** | **iOS 系统蓝牙默认自动连回该设备** | 手环在手上，但 App 长期检测不到 → 长期零数据 | **技术性** | 归技术性，不扣分；**识别特征同 M1**（无解绑事件 + 稳定记录后突变）。 |
| **M9** | **（"准后台"方式特有）客户错过了同步窗口** | 数据**断续**：有时有、有时无，**无规律** | **技术性（时机性）** | 归技术性，不扣分。**特征：不同于 M1~M8 的"突变后归零"，M9 是"锯齿状断续、且总量偏少但不为零"** —— ⚠️ **此形态下不能再用"连续性"作为依从性判据**（连续性会误伤客观正常的窗口机制）。<br>**→ 新增要求**：该方式下**评估页必须显示"同步窗口机制说明"**，否则经络师会把锯齿读成"客户不认真戴"。**本项为"另一条接入方式"特有，形态②/③ 不适用。** |

> **S6b / M9 的来源**：由 `user-researcher-2` 的「微信蓝牙后台能力（准后台）」评估衔接而来 —— **不是本件原链路（厂商 App 常驻后台）的失败模式，而是另一条接入方式特有的失败层**。**两者不可混引**：本条是"客户能感知到的窗口失效"（实际是机制），原 M1/M8 是"客户完全无感知的静默断连"。**处置一致（均不扣分），但识别特征不同。**

### 4.3 判定建议汇总（可直接进 PRD）

1. **最低限度（若业务方不同意新增类别）**：
   > **把「技术性缺失」与「合规摘除」并入「结构性缺失」处理（`applicable=False`，不扣分）。**
   > **绝不能默认按「行为性」计 0。** —— 宁可少扣分，不可错扣分：依从性门槛（AS ≥ 0.8）只是**门槛**，而错扣分会把"真戴了的客户"推向"依从不足"分支，进而影响判定与退款路径，**代价远大于少扣**。

2. **建议新增两类（更精确，也更可审计）**：
   - **`involuntary_technical`（技术性缺失）**：判据 = 有前置有效记录 + 无解绑事件 + 断点突变。
   - **`compliant_removal`（合规摘除）**：判据 = 有暂停期申报（住院/洗浴/桑拿/医疗期）。
   - **判据字段是新增需求**：`app_uninstall` / `device_unbind` / `unbind_reason` / `charge_reminder_sent_at` / `pause_period`。**这些字段现在是空的（P0-10 未包含），没有它们，上述判据全部无法执行。**
   - **⚠️ 自我订正（2026-09-18 补，重要）**：`app_uninstall` 与 `device_unbind` **不具同等可获取性** —— **App 无法上报自身被卸载**（同"崩溃上报无法上报自身缺失"）；**卸载事件只能靠厂商推送通道的"卸载回执"或重装检测**（待研发确认是否可用）。而 **`device_unbind`（客户在 App 内点"解绑设备"）是 App 内动作，可正常上报**。→ **结论：T2 中 `device_unbind` 是可靠能力，`app_uninstall` 降级为"待研发确认"，不得当作已成立能力记账。**
   - **不依赖技术的判别替代物（低成本，必须配）**：评估页在"缺失 N 天"旁标注"**缺失原因待门店确认**"，由调理师/经络师**在客户到店时问一句**并选结构化原因。**这把"不可观测"变成"可询问"，成本落在已存在的到店接触点上。**

3. **必须保留的一条兜底（不改 PRD 也能做）**：
   > **评估页在显示"手环缺失 N 天"时，必须同时显示「缺失原因推断」**（技术性 / 合规摘除 / 无解绑事件 / 有提醒记录 …），**让经络师在人工复核时有据可依，而不是只看到一个"缺失 12 天"的数字。**
   > 依据：P0-10 已要求"显式暴露缺失 N 天/覆盖率"，本件建议**在同一个字段位上加"原因"维度** —— 这是**成本最小、收益最直接**的一条改动。

4. **反博弈提醒**：新增"技术性缺失不扣分"后，**理论上存在"伪装成技术性缺失来规避扣分"的空间**（例如同意佩戴后主动卸载 App 谎称被杀）。**但本件不建议为此收紧** —— 因为 A3 只占 0.20 且不参与效果主判据，**为它增加博弈对抗的复杂度不划算**；正确做法是**让 `app_uninstall` 事件可留痕**（有卸载事件 → 不认定为技术性），**用留痕替代审批**。

## 五、佩戴引导时机建议

### 5.1 现状与问题

PRD P0-17：**禁忌筛查 → 建档 → 签署知情同意书**三步在同一"准入向导"内连续完成；**手环意愿在签同意书这一步填**（P0-02：愿意 / 暂不佩戴）。

**评估：这个时点问得太早。三条理由：**
1. **信任未建立**：这是第一次进店，客户对门店、对调理师都还没有体验。此刻问"要不要戴手环"，客户的第一反应是"**为什么要看着我？**"（尤其对中老年客户，"被监测"是不适的）。
2. **价值未被理解**：客户此时**不知道手环对自己有什么用**。粘性来自体验，不来自说明。
3. **★ 最关键的：这个"早"会直接制造 §四 的误判** ——
   > 客户在不理解的情况下，**多半会顺口答"愿意"**（不想驳面子 / 不想显得不配合）。
   > → 系统写入 `band_willingness = 自愿佩戴` → **A3 `applicable = True`**。
   > → 两周后因为 M1/M3/M6（App 被杀、不会充电、待机误解）没数据 → **按"行为性缺失"扣分**。
   > **即：我们把"客户礼貌性点头"记录成了一个他做不到的承诺，然后用这个承诺去扣他的分。这是本件发现的、最应该被修掉的一条因果链。**

### 5.2 建议：**保留表单原位，但改"意愿"的语义，并加一次体验式重申**

**不建议**把意愿采集从准入向导挪走（改表单结构会牵动 P0-02 电子签一页承载、以及 P0-17 三步连续性的硬约束，代价大、收益不明）。

**建议改为三件事：**

1. **改问法（0 成本）**：
   准入向导里问的不是"愿不愿意长期佩戴"，而是"**是否愿意了解一下 / 先试试**"；**默认选项偏「暂不佩戴」**，避免诱导性默认值。
   > 理由：**"愿意了解"是客户此刻真能兑现的承诺；"愿意长期佩戴"不是。**

2. **加一次「体验式引导」（第 1~2 次调理之后）**：
   由**调理师在核销后顺带 1~2 分钟**：把已充好电的手环**当场给客户试戴**，说一句中性话术（例：「这个是自愿的，您先戴着感受一下，不舒服随时摘，不影响任何服务。」），**并允许客户在此刻把意愿从「暂不佩戴」改为「自愿佩戴」**。
   > 理由：到这一刻客户**体验过服务、建立了信任、也看到了手环的样子** → 意愿才是有意义的意愿。

3. **意愿必须可双向变更并留痕**：
   新增 `band_willingness_revision`（意愿版本 + 生效时间 + 变更人 + 渠道）。**这是本条建议里唯一真正的字段新增**（成本小）。
   > **重要**：变更**只能单向放宽扣分，不能收紧** —— 即"愿意 → 暂不佩戴"**应当立即把 A3 置为 `applicable=False` 且已产生的缺失不追扣**；反向（暂不佩戴 → 愿意）**从变更生效日起计算应戴天**，不回溯。

4. **A3 的 `applicable` 判定时点应后移到"首次有效数据出现"**：
   > 拿不到任何数据的"自愿佩戴"，在统计上应视同**结构性缺失**处理（因为系统从未真正观测过一次）。**只有当客户至少成功产生过一次有效佩戴记录后，后续缺失才开始按"行为性"讨论**（且仍受 §四 的 M1~M9 例外约束）。

### 5.3 改动代价（必须记账）

| 项 | 改动 | 代价 |
|---|---|---|
| **表单** | P0-02 增加 `band_willingness_revision` 字段 + 默认值改「暂不佩戴」 | **小**（字段级，0 额外人日量级，待研发确认） |
| **门禁** | **不动** —— 四道闸门（禁忌/同意书/协议/方案）与手环意愿无关，PRD 已定"手环缺失不阻断、不可反转为阻断" | **无** |
| **运营** | 多一次"体验式引导"动作（1~2 min/客户） | **加进门店培训包**（= 再次给 R4b 加负担，与 §三 同一批资源） |
| **判定引擎** | A3 的 `applicable` 判定时点后移 + 意愿变更语义 | **中**（属 P0-12 判定前置断言范围，需研发评估） |

### 5.4 规则⑤检查（若有人提议"干脆不在向导里问手环意愿"）

**客户原来靠这一步做到的是：在签约前就知道"有一个手环、可以自愿佩戴、不影响服务"。**
**替代物（必须同时给出，否则不能删）**：**保留《知情同意书》正文里的"手环说明"条款（文本，只读回显）** —— 即**知情保留、意愿采集延后**。这样客户仍被充分告知，只是不再被要求"提前承诺"。

## 六、残余风险分离结论

> 沿用本团队口径：**任何"不可缓解"的风险，不得写成本团队能解决。**

### 6.1 可缓解（含具体缓解手段）

| 风险 | 缓解手段 | 落在谁的账上 |
|---|---|---|
| 配对失败（S6 陷阱） | **门店现场代配对**（客户本人手机上做）+ 培训包含"忽略此设备 + 重启手环"的机型化 SOP | 门店时间 / 培训包 |
| 安卓后台被杀（S8） | 权限配置核对清单（按 ROM 分）+ **`device_unbind` 解绑留痕**（`app_uninstall` 待厂商确认）+ 判据规则 M1 | 研发字段 + 培训包 |
| 电量耗尽（S9/M3/M6） | 充电提醒 + **首次免责** + 引导话术显式纠正"5~7 天要充，不是 45 天" | 研发（提醒）+ 培训话术 |
| 合规摘除（M4） | **暂停期申报机制**（住院/医疗期/洗浴桑拿期）+ 归"合规摘除"不扣分 | 研发（字段 + 入口） |
| 早问意愿导致误判（§五） | 改问法 + 体验式重申 + 意愿可变更（单向放宽）+ `applicable` 时点后移 | 研发（字段）+ 培训包 |
| 缺失原因不可解释 | **评估页在"缺失 N 天"旁显示「缺失原因推断」** | 研发（复用 P0-10 既有字段位） |
| 家属代操作（M5） | 标 `caregiver-mediated`，A3 归结构性；与 P0-09 代核口径统一 | 研发 + 业务口径 |
| 客户失去"我的数据在被采集"的可见入口 | 小程序内只读"我的佩戴状态"卡 | 研发（小程序） |

### 6.2 结构性不可观测（设计上没有观测能力，不可缓解）

| # | 内容 | 为什么是"不可观测"而非"未缓解" |
|---|---|---|
| **U1** | **居家期间"戴了但手机不在身边"与"根本没戴"，在 GTL1 手机中转链路上数据表现完全等价。** | **不是"暂时看不到"，是"当前架构下这两件事在数据上就是同一个东西"** —— 手环不独立联网，只有经客户手机 App 上传才有数据。补检测无从补起：**要区分它们，恰恰需要它们缺失的那段数据本身。** → **只能在评估页做"不可区分"的诚实标注，交给人工问一句。** |
| | **⚠️ U1 的严重程度随接入形态而变，故「不可观测占比」必须按形态单列** | 形态②（厂商云 API）断连期较短；**形态③（健康平台中转）必然丢实时性、断连期最长 → 不可观测占比最高**。**若三形态平均，形态③ 的"根本不可用"会被形态①/② 拉平掩盖** —— 与既有护栏（HSI 覆盖率须门店级 + 全网级分别告警）同源原则：**高缺失的单元不得被聚合平均掉。**（已与数析 §1.8 建议 #11 对齐） |
| **U2** | **客户在非到店时段是否真的佩戴了（人体佩戴检测）** | 取决于 GTL1 是否具备 on-body detection 且**能否通过自有接口暴露**（待厂商确认）。若厂商不开放，**系统永远只知道"有没有数据"，不知道"有没有戴"** → 这一点必须在设计上认下来，不能写成"我们做了佩戴监测"。 |
| **U3** | **手环 →（厂商云 / 我方 App）→ 调元云 这一段的数据可获取性** | ⚠️ **若厂商不提供 API/SDK，或提供的 SDK 无法在客户侧载体（微信小程序）上使用，前 9 步全部做完也拿不到数据** —— 此时"佩戴链路"在设计上不成立。**注意：该风险随接入形态而变（见 §一附）**：形态② 取决于厂商开放度；形态③ 取决于厂商是否写入健康平台；形态① 取决于 SDK 是否真能拿到佩戴数据 —— **三种形态都必须先验证，不得假定任一形态成立**。**这是本件最需要被当作前置阻塞项的一条。** |

### 6.3 需业务方裁定才能缓解（本团队无权自行解决）

| # | 待裁定 | 为什么必须业务方定 | 影响 |
|---|---|---|---|
| **B1** | **设备是「门店发」还是「客户自购」** | 决定成本归属、决定谁在现场承担配对的 20~40 分钟，也决定"自愿性"是否被稀释 | §一 全节；R4b 是否加重 |
| **B2** | **是否接受"客户需装第二个 App"**；或是否愿意**换设备**（方案 E） | 换设备 = 重新选型 + GTL1 沉没成本，只有业务方能拍 | §二 全部 |
| **B3** | **是否同意新增「技术性缺失 / 合规摘除」两类** | PRD 硬约束目前只有两类（结构性/行为性）；改口径属业务方权限 | §四 全部 —— **若不同意，则退到"并入结构性不扣分"的最低限度** |
| **B4** | **门店「手环代配」是否计工时/付薪；是否强制** | 决定 R4b 是否被实质加重；决定门店会不会把它做成半强制佩戴 | §三；与"不强制佩戴"硬约束的边界 |
| **B5** | **是否允许门店代客户完成 App 注册**（涉及客户手机号与短信） | 涉及账号归属与个人信息处理，需业务方 + 法务 | §二 方案 B |
| **B6** | **厂商数据通道（U3）是否成立** | 商业/采购层面的谈判结果 | §六.2 U3 |

## 七、⚠️ 待确认项与最小验证实验

### 7.1 待确认项（不开工即可能返工）

| # | 待确认 | 谁答 | 为什么阻塞 |
|---|---|---|---|
| Q-G1 | 设备来源：门店发 / 客户自购 / 两者并存 | **业务方** | §一 全节链路与成本归属 |

### 7.2 最小验证实验（**无实测数据，以下为验证本件推演所需的最小方案**）

**实验 A · 10 位客户佩戴观察（验证 §一 的放弃点排序与 §三 的耗时）**
- **样本**：10 位，建议构成（推断画像）—— ≥60 岁 **6 位**、家人代操作 **2 位**、有慢病需长期管理 **2 位**；**分 2 组**：5 位**门店代配对** / 5 位**自助配对**（直接对照 §二 方案 A 的效果）
- **周期**：**14 天**（覆盖 ≥2 个充电周期，能观察到第一次电量耗尽）
- **记录项（每客户）**：
  1. 逐步耗时与卡点（**精确到 S0~S10 每一步**，记录是否放弃、放弃在哪一步）
  2. 有效佩戴天数 / 断连天数 / **断连原因自报**（区分 M1~M8）
  3. 是否发生过系统蓝牙冲突（验证 S6 陷阱发生率）
  4. 电量曲线（验证"5~7 天 vs 45 天"的误解比例）
  5. 客户主观反馈一句（"您觉得这东西麻烦吗？"）
- **产出**：**逐步放弃率曲线** + **断连原因分类占比** + **单客户真实耗时区间**（替换本件 §三 的推演值）

**实验 B · 配对陷阱复现（验证 §一 S6 为最高放弃点；并判定阻断层归属）**
- **做法（B-1，形态②/③）**：5 台 GTL1，**先**用手机系统蓝牙连上，**再**进厂商 App 搜索 → 记录是否被阻断、客户/店员能否在无手册指导下自行恢复
- **做法（B-2，★ 若形态① 成立则必做）**：用**第三方 BLE 工具（不装厂商 App）**尝试连接**已被手机系统蓝牙占用**的 GTL1 →
  - **能连上** → 阻断来自**厂商 App 的实现层** → 形态① 下我方自研配对 UI **可能绕开陷阱** → **§一.2 的排序须改（S6 可能不再是最高放弃点）**
  - **连不上 / 扫不到** → 阻断来自**设备/系统层** → **§一.2 排序无需改，三种形态下 S6 结论一致**
  - **iOS 与 安卓各测一组**（iOS 侧预期必为"连不上"，已由系统级自动回连行为支持）
  - ⚠️ 这正是手册**未说明**的那一处，**不得用推测替代**
- **成本**：极低（半天可完成，B-2 加半天）
- **产出**：S6 陷阱的**发生率**与**平均恢复耗时**；**B-2 的阻断层归属判定**（直接决定 §一附 A.2 的结论）

**实验 C · 手机中转段盲区验证（决定 M2 / U1 的归类）**
- **做法**：3 位客户**戴手环但把手机留在家里 3 天**（手环正常佩戴、正常记录）→ 回家后重连 App，看**能否回补这 3 天的数据**
- **产出**：决定 M2 归「技术性缺失（可缓解）」还是「结构性不可观测（不可缓解）」—— **这是本件唯一一个"结论会因实验结果而反转"的判断，优先做。**

**实验 D · 合规摘除申报（验证 M4 的机制可行性）**
- **做法**：在实验 A 的 10 位客户中，请 2 位**按说明书在洗浴/桑拿时段摘下手环**并尝试申报 → 验证"暂停期申报"在真实门店里是否被客户理解、是否被门店愿意执行
- **产出**：暂停期机制的操作成本与话术

### 7.3 本件的自我失效条件（团队规则③）

> **本件结论的依据类型 = 设备手册原文 + 客户画像推断 + 角色动机推断（无任何观测数据）。**
> **复原（失效）条件**：
> - 若**实验 A** 显示"完成自助配对的客户占比"显著高于本件推演 → §一 的放弃点排序（S6 最高）需修订；
> - 若**实验 C** 显示断连数据可完整回补 → §四 M2 应从"结构性不可观测"退回"技术性缺失（可缓解）"；
> - 若**厂商确认无开放数据通道（Q-G2）** → **本件 §一/§二/§五 的用户侧引导建议全部作废**，问题性质从"用户可得性"变为"链路不成立"，须整体返工。
> **在以上实验完成前，本件所有推演结论一律按「未缓解」记账。**

## 附二：与数析侧的轴对齐（2026-09-18 与 data-analyst 已互认）

**结构映射（本件场景轴 M1~M8 ↔ 数析口径轴 G 系列）—— 两轴处置一致，一律"不扣分"，无冲突：**

|---|---|---|
| **M1 / M8**（安卓杀 App / iOS 系统蓝牙自动连回） | **G7 技术性缺失** | 不扣分；判据 = 有前置有效记录 ∧ **无 `device_unbind`** ∧ 断点突变（**不依赖 `app_uninstall`**） |
| **M4**（住院/医疗期/洗浴桑拿按说明书摘除） | **G8 合规摘除** | 不扣分；**暂停期从「应戴天」分母剔除** |
| **M3 / M6**（不会充电 / "45 天"误解） | 由 `charge_reminder_sent_at` 支撑 | **首次免责；提示后仍不充才追责** |
| **M2 / M5**（手机不在身边 / 家属代操作） | **结构性不可观测** | 不可缓解（= 本件 U1 / U2） |

**★ 一条必须并列引用的对偶（本件 U1 ↔ 数析的台账分母）：**
> 数析口径轴强调：**「应戴天」必须由设备台账（绑定日 → 解绑日）产生，不得由"数据存在性"产生** —— 否则 **A3 恒为 1.0、静默虚高**。
> 这与本件 **U1（"戴了但手机不在"与"没戴"在数据上不可区分）** 是**同一件事的两面**：**客户视角看不见 ↔ 分母不能用数据存在性来定义。**
> **引用时必须并列** —— 只讲 U1 会显得"问题无解"，只讲台账分母会显得"分母已解决而客户仍是黑箱"。**两面合起来才是完整解：分母用台账定义（谁绑了谁没绑，客观可查），分子里的缺失原因用 §4.3 的判据分流。**

**已互认的其他三条：**
- 「技术性缺失不扣分」「`applicable` 后移至首次有效数据」「缺类别时并入结构性不扣分」—— 数析全部确认一致；
- 「用留痕替代审批、不为 A3 增博弈复杂度」（证据不足时既不罚客户也不奖自己）—— 数析同意；
- 本件 §4.3 的「缺失原因待门店确认」兜底已被数析列为建议 #10，**0 新增字段、复用 P0-10 既有字段位**。
