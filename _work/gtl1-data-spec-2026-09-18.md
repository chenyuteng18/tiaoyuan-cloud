## TL;DR（5 行）

1. **规格页 ≠ SDK 能力**。GTL1 规格页能证明的是「设备**可能**采集到心率/血氧/睡眠/步数等生理数据」，**不能证明「星迈 SDK 会把这些数据交给我们的系统」**。P0-10 与 A3 的可交付性**完全取决于 SDK 契约，而该契约当前 100% 未知**。
2. **7 字段里有 5 类 GTL1 规格页有依据（睡眠/步数/心率/血氧/运动模式），2 类无依据（静息心率、压力）**，后者必须走「待厂商确认」，**不得预设"HRV 可推压力"为事实**（该措辞仅在宣传文案、不在参数表，可信度低）。
3. **接入形态存在一个未被讨论的结构性冲突**：厂商说的「SDK 接入**您现有的 App**」要求**原生 App 宿主**，而本产品客户端载体是**微信小程序**——**原生 SDK 无法嵌入微信小程序**。该冲突是形态①可行性的第一道门，必须先确认。
4. **A3 风险判定 = 高危且不可自动兜底**：若 SDK 只回传**聚合日数据**、无**佩戴检测字段**，则「未佩戴」与「佩戴但无有效读数」**不可区分** → A3 在正负两个方向都会系统性失真（算例见 §3.3，同一行为可使 AS_refund 在 0.75↔0.83 之间跨越 0.8 门槛）。
5. **「不补 0」会静默失效**（§4）：缺数据那天不产生记录 → 系统看不到"缺失"→ 该天**不进分母** → 字面遵守了"没补 0"，语义上却**把分母扔掉了**（即「**缺失不得被平均或清洗**」原则，*既有原则、第三处复现*，见 §四附）。**在拿到佩戴检测字段前，建议 A3 默认 `applicable=False`、权重重归一、不扣分。**

## 一、字段映射矩阵（GTL1 能力 → P0-10 要求）

### 1.1 总表

> **读法（重要）**：本表「GTL1 规格页依据」一列只说明**设备规格是否宣称具备该采集能力**；「SDK 可获取性」一列说明**我们能否拿到**——**后者一律为「待厂商确认」**，因为 SDK 契约未获取。**规格页有 ≠ SDK 能拿到。**

| # | P0-10 要求字段 | GTL1 规格页依据 | 规格侧判定 | **SDK 可获取性** | 备注 |
|---|---|---|---|---|---|
| 1 | **睡眠** | ✅ 明确：入睡时间 / 浅睡 / 深睡 / REM | ✅ 规格有能力 | ⚠️ **待厂商确认** | GTL1 粒度**细于** PRD（PRD 只要"睡眠"，GTL1 给分期）→ 存在**粒度对齐成本**，非缺失 |
| 2 | **步数** | ✅ 明确：步数 / 距离 / 卡路里 | ✅ 规格有能力 | ⚠️ **待厂商确认** | 距离/卡路里为 GTL1 额外项（见 §1.3 不需要项） |
| 3 | **心率（HR）** | ✅ 明确：HX3918 心率传感器 + "心率监测" | ✅ 规格有能力 | ⚠️ **待厂商确认** | 需确认回传是**原始时序 / 整点采样 / 日汇总**（决定 §4 能否成立） |
| 4 | **静息心率（resting_hr）** | ❌ **参数表未列此项** | ❌ 规格页**无依据** | ⚠️ **待厂商确认** | **三选一判定见 §1.2** |
| 5 | **压力（stress）** | ❌ **参数表未列**；仅**宣传文案**提"心率变异性分析、情绪检测" | ❌ 规格页**无依据**（文案级旁证，可信度低） | ⚠️ **待厂商确认** | **三选一判定见 §1.2**；且**压力不属 A3 所需** |
| 6 | **血氧（SpO2）** | ✅ 明确：HX3918 血氧传感器 + "血氧监测" | ✅ 规格有能力 | ⚠️ **待厂商确认** | 消费级 SpO2 精度存疑，见 §5 合规 |
| 7 | **运动类型（workout type）** | ✅ 明确："16 种运动模式" | ⚠️ **部分**：**枚举值未公开** | ⚠️ **待厂商确认** | 规格只说"16 种"，**未给出 16 个枚举**；与 PRD 所需运动类型可能**非一一对应** → 需映射表 |

**映射结论汇总（自证伪检查）**：7 个字段中，**规格页有明确依据 = 5 个**（睡眠/步数/心率/血氧/运动模式，其中运动模式仅"部分"因枚举未公开）；**规格页无依据 = 2 个**（静息心率、压力）。**5 + 2 = 7 ✓ 与 P0-10 字段数吻合。** 但**"规格有依据"的 5 个中，SDK 可获取性 0 个已确认**——故**本矩阵不构成任何"可交付"结论**，只构成"提问方向"。

### 1.2 「静息心率」与「压力」的判定（三选一，逐项）

**PRD 明确要求在参数表里没有的两项，必须显式判定，不得默认"可推导"。**

| 字段 | ①真缺失？ | ②可由已有数据推导？ | ③需向厂商确认？ | **数析判定** |
|---|---|---|---|---|
| **静息心率** | 规格页未列 → 可能真缺失 | **技术上可推导**：业内标准做法是从心率时序 + 静息期识别（睡眠/静止段）计算静息心率。**但前提是 SDK 回传"可分辨静息期的心率时序"**；若只回传"日心率汇总（均值/最高/最低）"，最多用"日最低心率"**近似**，**非真静息心率** | ✅ **是** | **③ 为主 + ② 有条件保留**：先问厂商"是否原生提供 resting HR"；若无，再问"是否提供可分辨静息期的心率时序"。**不得预设可推导为事实** |
| **压力** | 规格页未列 → 可能真缺失 | **技术上依赖 HRV**（时域 RMSSD/SDNN 或频域 LF/HF）。**关键警示**：规格页的"心率变异性分析、情绪检测"**出现在宣传文案（marketing copy）里，不在参数表（spec table）里** → **可信度显著低于参数项**，**不得据此推断"可推压力"** | ✅ **是** | **③ 需向厂商确认，且标注"文案级旁证、低可信"**。另注：**压力字段不进 A3**，其缺失对依从性判定**无直接影响**，仅影响 P0-10 的 schema 完整性与指标卡 |

> ⚠️ **纪律声明（团队规则④同类要求）**：本节**没有**写"由 HRV 可推压力"，因为规格页并未证实 SDK 暴露 HRV/RR 间期；**规格页的宣传文案不能作为 SDK 能力的旁证**。能力必须由厂商在 SDK 文档中自证，**不能靠规格页反推**。

### 1.3 GTL1 有、但 P0-10 不需要的能力项（同样要处理）

| GTL1 能力项 | 是否在 P0-10 7 字段内 | 处置建议 |
|---|---|---|
| **血压监测（BP）** | ❌ 不在 P0-10 7 字段内 | ⚠️ **但 05 表数据模型列了 `bp`**（见下「口径不一致」）→ 需业务裁定是否要；且**消费级血压精度争议大 + 厂商已声明非医疗器械**，见 §5 |
| 体温检测 | ❌ 不在 | 若需要需另立需求；消费级体温多为接触式/趋势值 |
| 距离 / 卡路里 | ❌ 不在 | 可由步数派生，**不建议入库**（避免冗余口径） |
| 抬腕唤醒 / 久坐提醒 | ❌ 非数据字段 | 设备功能，与数据接入无关 |
| 16 种运动模式 | ✅ 部分对应"运动类型" | 枚举未公开，见 §1.1 |
| HRV 分析 / 情绪检测 | ❌ 不在 | 仅宣传文案，**标低可信、待确认**（见 §1.2） |
| 支持 Google Health / Apple Health | ❌ 非设备能力，是**厂商 App 的对接能力** | 是形态③的既有基础（见 §2.3） |

### 1.4 ⚠️ 发现的文档内部口径不一致（须业务裁定）

**PRD 自身两处字段清单不一致**（自证伪检查发现）：

| 来源 | 字段清单 | 与 GTL1 能力对照 |
|---|---|---|
| **P0-10 验收标准** | 睡眠 / 步数 / 心率 / **静息心率** / **压力** / **血氧** / **运动类型** | 静息心率、压力**无规格依据** |
| **附录 C.1.6（05 表 → `band_telemetry`）** | `{sleep, steps, resting_hr, bp, glucose, uric_acid}` | **`bp / glucose / uric_acid` GTL1 规格页均无**；且此清单**无 stress / spo2 / workout** |

**问题**：
- 两处清单**交集仅 3 项**（sleep / steps / resting_hr）；P0-10 有**压力/血氧/运动类型**但数据模型没有；数据模型有 **bp/glucose/uric_acid** 但 P0-10 没有。
- **GTL1 规格页完全没有 `glucose`（血糖）、`uric_acid`（尿酸）、`bp`（血压）中的任何一项的明确参数依据**（`bp` 仅有"血压监测"宣称，`glucose/uric_acid` 无任何依据）。
- **后果**：若按附录 C 的数据模型实施，会要求接入 GTL1 **根本不具备**的血糖/尿酸字段 → **必然落空**；若按 P0-10 实施，则 `band_telemetry` 的 DDL 与验收标准**不闭合**。
- **建议**：请 team-lead 转业务/析客——**以 P0-10 的 7 字段为验收口径**，`band_telemetry` 的 `glucose/uric_acid` **标记为「非 GTL1 能力、需移除或另定数据源」**；`bp` 单列为待裁定项。

## 二、三种接入形态对比

> 前提澄清：用户原话是「**这是星迈 GTL1 智能手环的 SDK**」，**暗示形态①**；但**"SDK"这个词本身不携带任何能力信息**——能读到什么字段、什么频率、原始值还是聚合值、是否含佩戴检测，**全部未知**（§7 待确认项汇总）。以下三形态**并列评估，不预设①为定案**。

### 2.0 ⚠️ 前置阻塞项：客户端载体是什么？（决定形态①生死）

厂商官网原文：**「二次开发：由我们提供 SDK/API 接口，接入**您现有的 App**」**——这把 SDK 的宿主**限定为原生 App**（Android `.aar` / iOS `.framework`，通常含 native `.so`）。

**而本产品客户端载体是「微信小程序」**（PRD：客户侧每日填报走小程序；US-4 等均以小程序为触点）。

| 载体 | 能否集成厂商 native SDK | 结论 |
|---|---|---|
| **微信小程序** | ❌ **不能**。小程序只能通过 `wx.*Bluetooth*` API 做**通用 BLE** 通信，**无法加载/运行厂商 native SDK** | 形态①**在小程序内不可行** |
| 原生 App（Android/iOS） | ✅ 可以 | 形态①可行，但**需新增原生 App 载体**（成本/工期/合规均变） |
| uni-app / Flutter 等混合 | ⚠️ 需**原生插件**桥接，可行性取决于 SDK 是否有对应插件封装 | **待确认** |

> **这是本节最重要的发现**：形态①的可行性**不取决于手环，取决于我方客户端是不是原生 App**。若客户侧坚持小程序，则「厂商 SDK 直连」这条路**在架构上就不成立**，必须转向形态②或③。**请 team-lead 优先向业务确认客户端载体。**

### 2.1 形态①：厂商 SDK 在我方 APP 内蓝牙直连手环

| 维度 | 内容 |
|---|---|
| **需厂商提供** | ① Android/iOS 双端 SDK 包；② **完整协议/SDK 文档**（字段、单位、频率、原始 vs 聚合）；③ 设备发现/绑定/鉴权流程（配对密钥由谁签发）；④ 蓝牙 GATT 服务/特征值定义；⑤ 固件 OTA 接口（可选）；⑥ **SDK 版本维护承诺与生命周期**；⑦ 测试机 / Sandbox |
| **我方 APP 承担** | **配对流程**（自研配对 UI，因手册明确"不能通过手机系统蓝牙直接连接"）；**权限申请**（Android 12+ `BLUETOOTH_SCAN/CONNECT`、定位权限；iOS 蓝牙权限 + `UIBackgroundModes=bluetooth-central`）；**后台保活**（Android 前台服务 + 电池优化白名单，**国产 ROM 杀后台是已知高发问题**）；**断连重连状态机**；**数据落库/去重/补传**；**SDK 体积与包大小影响**（原生 SDK 常含多架构 `.so`，可达数 MB~十几 MB，影响包体与 64 位合规） |
| **可行性风险** | 🔴 **① 客户端载体冲突（见 §2.0）——最高风险**；🟡 ② 双端 SDK 成熟度未知（厂商是否真有 iOS SDK 未证实）；🟡 ③ 后台保活失败 → 数据缺口 → **直接污染 A3**；🟡 ④ SDK 体积与合规（隐私清单/权限说明）增加上架成本；🟡 ⑤ 客户需**安装我方 App**（而现在客户只用小程序）→ **获客/依从性成本** |

### 2.2 形态②：走厂商云 API（若存在）拉取客户在 Runmefit/即米 的数据

| 维度 | 内容 |
|---|---|
| **需厂商提供** | ① **是否存在服务端开放 API**（⚠️官网只写"SDK/API 接口"，**"API"是否有云端点未证实**）；② 鉴权方式（OAuth / 账号绑定 / 数据导出）；③ 字段与频率；④ **数据中心位置与数据主权条款**；⑤ SLA |
| **我方 APP 承担** | 客户在 **Runmefit / 即米运动健康** 内授权第三方读取；账号**绑定关系管理**；服务端**定时拉取**；多源**去重与合并**；令牌刷新 |
| **可行性风险** | 🔴 **① 云 API 是否存在未证实**——大概率**不存在面向第三方的云 API**（消费级白牌手环厂商通常只提供**本地 BLE SDK**，云端是封闭的自有 App）；🟡 ② 即便有，**客户需装两个 App**（我们的 + 厂商的）→ 依从性负担；🟡 ③ 数据经厂商服务器 → **合规面变化**（见 §5）；🟡 ④ **无法做实时/近实时**，只有厂商 App 同步后才有 |

### 2.3 形态③：混合（客户用厂商 App，我方经 Apple Health / Google Health 中转）

| 维度 | 内容 |
|---|---|
| **需厂商提供** | ✅ **这条是厂商 App 的既有能力**：规格页明确 Runmefit/即米**支持 Google Health / Apple Health** → **无需厂商新增开发**（这是三形态中**唯一不依赖厂商配合**的） |
| **我方 APP 承担** | 引导客户在手机健康平台**授权我方读取**；**平台适配层**（HealthKit 类型映射 → 我方 schema）；去重；**同样受 §2.0 载体限制**（HealthKit / Health Connect **只能在原生 App 读取，小程序读不到**） |
| **可行性风险** | 🔴 **① 载体限制同上**（小程序读不到 HealthKit）；🔴 **② 平台侧只有"聚合值"**（日步数/日睡眠/心率区间），**无原始 PPG、无佩戴检测** → **A3 与"不补 0"更难成立**；🔴 **③ 数据来源不可辨（同源性问题）**：HealthKit 里同类型数据可能来自**任何 App/设备**，**无法证明该条数据来自 GTL1** → 与项目「**同源测量**」原则（《集成指标规范》§1.3、PRD §5.3 硬约束）**直接冲突**；🟡 ④ 出境传输风险（Apple/Google 服务器，见 §5） |

### 2.4 三形态对比速览

| 对比项 | ① SDK 直连 | ② 厂商云 API | ③ 健康平台中转 |
|---|---|---|---|
| 厂商是否已具备 | ⚠️ 宣称有 SDK（**能力未知**） | ❌ **大概率不存在** | ✅ **已具备**（规格页明示） |
| 我方可否小程序内用 | ❌ 不能 | ✅ 可以（服务端） | ❌ 不能 |
| 能否拿原始/高频数据 | ⚠️ 若 SDK 支持则**最优** | ❌ 通常只有厂商聚合值 | ❌ **只有聚合值** |
| 能否做佩戴检测 | ⚠️ **取决于 SDK** | ⚠️ 取决于厂商是否回传 | ❌ **不可能** |
| 同源可验证 | ✅ 可（我方自己采） | ✅ 可 | ❌ **不可**（多源混杂） |
| 数据落点 | 我方服务器 | 厂商服务器 → 我方 | Apple/Google → 我方 |
| 客户负担 | 装我方 App | 装我方+厂商 App | 装我方+厂商 App |
| **综合建议** | **若载体是原生 App 且 SDK 文档可证 → 唯一可能承载 A3 的形态**；否则不可行 | **先证实存在性，再评估** | **仅作"降级兜底"，不可承载 A3** |

> **形态对 A3 的额外口径要求（2026-09-18 与瑞思对表，详见任务 #3 §1.8）**：
> - **形态③下"结构性不可观测"占比更高**（健康平台中转必然丢实时性、依赖客户主动打开厂商 App 触发写入）→ **A3 的"结构性不可观测占比"须按形态单列，不得三形态平均**（否则形态③的高占比被拉平，掩盖"A3 在该形态根本不可用"）。**归属「缺失不得被平均或清洗」原则（*既有原则、第三处复现*，见 §四附）。**
> - **形态①（我方自带原生 App）下，`device_unbind` / `pause_period` 由我方自建 → 判据可得性上升**（前提是载体不与小程序硬约束冲突，故为**条件性利好**）。

## 三、A3「有效佩戴率」口径影响与降级口径

### 3.1 A3 定义回顾

`A3 = 有效佩戴天 / 应戴天`，权重 **0.20**（四维口径）/ 在 `AS_refund` 中重归一为 **0.286**（A1 0.571 / A3 0.286 / A4 0.143，**合计 1.000 ✓**）。**仅"同意佩戴者"适用**，未同意 → `applicable=False` 不扣分。

### 3.2 核心问题：仅凭聚合日数据，能否区分「未佩戴」与「佩戴但无有效读数」？

**答：不能可靠区分。** 机理：

| 缺失类型 | 系统看到的表象（若 SDK 只给日汇总） | 真实含义 |
|---|---|---|
| **未佩戴** | 该天**无记录** | 客户没戴（行为性缺失，应扣分） |
| **佩戴但无有效读数** | 该天**无记录** 或 **有记录但值为 0/异常** | 戴了，但传感器/贴合/电量导致没采到（**不应扣分**） |
| **充电中（未佩戴）** | 该天**无记录** | 170mAh / **续航仅 5–7 天** → 每周约 1 天在充电 → **规律性缺口** |
| **蓝牙未同步** | 该天**无记录**（数据还在设备里） | 佩戴了、也采到了，只是没传上来（**不应扣分**） |
| **App 后台被杀** | 某段**无记录** | 同上（**国产 ROM 高发**） |

**关键**：以上 **5 种情形在"日汇总"视角下高度同构**——多数都表现为"这一天没有记录"。**没有佩戴检测字段（wear/off-wrist）与有效测量时长，就无法拆分**。

> ⚠️ **口径 ≠ 数据（团队规则③）**：本节写的不是"佩戴率不重要"或"风险不存在"，而是**"我们目前没有能支撑 A3 的数据"**。二者不能互相替代。

### 3.3 A3 失真的量化演示（同一行为、结论反转）

设定：客户 B，`A1 = 0.9`（应到 10 次到 9 次）、`A4 = 0.8`、真实行为 = **7 天里戴了 5 天，其中 2 天"戴了但无有效读数"**。用 `AS_refund = 0.571×A1 + 0.286×A3 + 0.143×A4`（门槛 0.8）：

| 口径 | A3 取值 | AS_refund 计算 | 结果 |
|---|---|---|---|
| **口径甲**：「有效佩戴 = 有有效读数」 | 3/7 = **0.429** | 0.571×0.9 + 0.286×0.429 + 0.143×0.8 = 0.5139 + **0.1227** + 0.1144 = **0.751** | **< 0.8 → 依从不足** ❌ |
| **口径乙**：「佩戴即算（戴了就算）」 | 5/7 = **0.714** | 0.5139 + **0.2042** + 0.1144 = **0.833** | **≥ 0.8 → 达标** ✅ |
| **口径丙**：静默失效（缺 2 天不进分母） | 5/5 = **1.000** | 0.5139 + **0.2860** + 0.1144 = **0.914** | ≥ 0.8 → 达标（**虚高 0.081**）⚠️ |

**结论**：**同一客户的同一佩戴行为，仅因"有效"二字的口径不同，AS_refund 在 0.751 ↔ 0.833 之间摆动，跨越 0.8 门槛，判定结果反转。** 且口径丙的"静默虚高 +0.081"是**无报错、无告警**的。→ **A3 在缺乏佩戴检测字段时，正负两向都会系统性失真，且方向不可预知。**

### 3.4 降级口径（**明确标注：降级口径，需研发评审，非定案**）

**在拿到 SDK 佩戴检测字段前**，建议按以下**优先级**处置：

| 方案 | 口径 | 适用条件 | 代价 / 风险 |
|---|---|---|---|
| **D0（首选）** | **A3 `applicable=False`，权重重归一，不扣分** | SDK 无佩戴检测能力 | 等同"结构性缺失"处理；**最保守，最合规**（不误罚客户）；代价是 A3 维度暂时"空转" |
| **D1（次选）** | 改名 **「手环数据覆盖率」** = `有数据天 / 应戴天`，**仅进 `AS_ops`，不进 `AS_refund`** | SDK 无佩戴检测、但有数据存在性 | **不得称"有效佩戴率"**（名实不符会误导）；不进退款门禁 |
| **D2** | 以 **「有效测量时长 ≥ 阈值（如 ≥10h/天）」** 定义"有效佩戴天" | SDK **提供**逐日有效测量时长 | 需校准阈值；仍需研发评审 |
| **D3** | 用 **「我方同步尝试日志」** 反推分母（`应戴天` = 有同步尝试覆盖的天） | SDK 无佩戴检测 | **仅能证明"同步过"，不能证明"戴过"**；是**代理口径**，须显著标注 |
| **D4（兜底）** | 保留 **人工降级 + 留痕**：调理师到店代核手环佩戴情况，人工录入 | 全形态失败时 | PRD 已有此思路（"设备适配层可先人工降级上线"）；**人工口径不可作为退款门禁硬依据** |

> **护栏复用**：无论采用哪个降级口径，均应沿用既有护栏——**覆盖率不足自动降权**（PRD §5.3 手环定位收紧已有此条）+ **应戴天 < 7 标"样本不足"**（AS 既有护栏）。

## 四、「不补 0」静默失效风险评估

### 4.1 风险机理（本任务最关键的一节）

PRD P0-10 要求：**「同步失败或未佩戴 → 标记空缺，不得自动补 0」**。

**该要求的隐含前提是**：系统**知道**"这一天应该有数据但没有"。

**若 SDK 只给日汇总，且缺数据的那天不产生记录**，则：

```
客户实戴 5/7 天（缺 2 天：1 天充电、1 天蓝牙未同步）
产品 / SDK 返回：5 条日记录
系统解析结果：这 5 天 = 全部记录
A3 = 5 / 5 = 1.000            ← 分母从 7 变成 5
```

- **字面层**：系统**没有**补 0（没给缺失天写 0）→ **P0-10 的字面要求被"遵守"了**。
- **语义层**：那 2 天**根本没进分母** → **等价于把分母扔掉了** → **A3 虚高**（演示见 §3.3 口径丙，虚高 +0.081）。
- **静默性**：**没有报错、没有告警、没有"缺失 N 天"标记**（因为系统"看不见"缺失）→ PRD 要求的「评估页显式暴露手环缺失 N 天」**也一并失效**（无数据可暴露）。

> ⚠️ **这与「缺失不得被平均或清洗」原则（*既有原则、第三处复现*，见 §四附）同源**：原文口径为「**分母不能被稀释或清洗来讨好指标**」（《集成指标规格》§11.1 / §11.2）。手环覆盖率与 ECC 指标是**同一条原则的两次出现**——**只要分母由"数据存在性"决定，指标就必然可被粉饰。**

### 4.2 风险等级与性质判定

| 维度 | 判定 |
|---|---|
| **发生概率** | **高**（若 SDK 为"聚合日汇总"形态，则**必然**发生） |
| **影响面** | **直接作用于 A3**（权重 0.286 of AS_refund）+ **使 P0-10 的第 3、4 条验收无法达成** |
| **可见性** | **极低（静默）**——不报错、不进告警，指标"看起来正常" |
| **是否可事后发现** | ❌ 若只有日汇总，事后**无法复原**缺失天（**无数据即无证据**） |
| **性质** | **不是"漏报"，是"系统性虚高"**，且方向单一（只涨不跌）→ 最危险的一类失真 |

### 4.3 能真正区分「未佩戴」与「无数据」所需的最小字段清单（→ 厂商提问硬输入）

**以下 7 项是"最小充分集"**，缺任一项则 §4.1 的静默失效无法根除：

| # | 最小字段 | 作用 | 缺它的后果 |
|---|---|---|---|
| **M1** | **佩戴状态 / 离腕检测**（`wear` / `off_wrist` / `unknown`，逐日或逐时间片） | **区分"未佩戴"与"佩戴"** | 无法区分行为性缺失与结构性缺失（§3.2 全部失效） |
| **M2** | **有效测量时长**（分钟/天）或有效采样点数 | 定义"有效佩戴"的分子 | 无法判断"戴了但没采到" |
| **M3** | **数据覆盖区间**（每条记录的起止时间戳） | 判断"部分覆盖"的天 | 只能得到"有/无"，无法得到"覆盖多少" |
| **M4** | **记录存在性语义**：无数据时是**返回"无记录"标记**，还是**静默不返回** | **这是"不补 0"能否成立的关键** | 静默不返回 → §4.1 必然发生 |
| **M5** | **同步/采集失败原因码**（未佩戴 / 未同步 / 蓝牙断 / 电量低 / 传感器失败） | 归因缺口 | 缺口无法归因，只能记"原因未知" |
| **M6** | **设备绑定状态 + 设备唯一 ID** + **`device_unbind`（解绑事件）/ `unbind_reason`**（含绑定/解绑时间戳） | 确定"应戴天"的起止（绑定日 → 解绑日）+ 区分"主动放弃"与"技术性缺失" | 分母无法由台账产生（见 §4.4）；无法区分主动放弃 |
| **M7** | **电量 / 充电状态** + **`charge_reminder_sent_at`**（充电提醒发送时间） | 识别"充电期缺口"（**5–7 天续航 → 每周约 1 天充电**）+ 支持"首次免责、提示后仍不充才追责" | 把充电误判为"未佩戴"（误罚客户） |

> **⚠️ 两档字段处理（2026-09-18 与用户研究员瑞思对齐后的订正）**：
> - ✅ **可靠、建议硬需求**：`device_unbind` / `unbind_reason` / `charge_reminder_sent_at`（**这些是 App 内动作或我方推送记录，可正常上报**）
> - ⚠️ **降级为"待厂商确认，不得当作已成立能力"**：**`app_uninstall`**（**App 无法上报自身被卸载** —— 同"崩溃上报无法上报自身缺失"；卸载事件只能靠厂商推送通道的**卸载回执 / 重装检测**，**能否拿到取决于厂商，属未确认**）
> - **关键**：**"客户主动放弃"的唯一可靠信号 = 有没有一次主动解绑动作（`device_unbind`）**，**这条不依赖厂商开放即可成立**，故 §4.4 台账分母方案与"区分主动放弃"的判据**均不因 `app_uninstall` 缺失而失效**。

### 4.4 若拿不到上述字段：检测手段与替代方案

| 方案 | 做法 | 局限（必须标注） |
|---|---|---|
| **A. 同步日志反推（客户端侧）** | 我方 APP/小程序记录**每次同步尝试**（时间 + 成功/失败 + 覆盖区间） | ✅ 能证明"**我方尝试过同步**"；❌ **不能证明客户"戴过"** → 只能得到"**同步覆盖率**"，非"佩戴率" |
| **B. 分母台账化（服务端侧，推荐）** | **`应戴天` 由设备台账决定**（`绑定日 → 解绑日` 的日历天数），**不依赖数据存在性** | ✅ **能让分母不可被清洗**（回应 §4.1 本质）；❌ 仍需 M1/M2 才能算"有效佩戴天" |
| **C. 代理推断（数据侧）** | 用"该天有步数>0 或睡眠记录"推断佩戴 | ❌ 静坐日/未戴日可能都有步数；**是代理口径，非"有效佩戴"** |
| **D. 缺项显式标记** | 无记录天一律标 `missing_reason = unknown`，在评估页显式暴露"**原因未知缺口 N 天**" | ✅ 至少**不静默**（满足 P0-10 第 4 条"显式暴露"的精神）；❌ 仍不能区分原因 |
| **E. 到店询问转结构化（0 新增字段，推荐配套）** | 评估页在"缺失 N 天"旁标注「**缺失原因待门店确认**」，由调理师在**既有到店接触点**问一句并选结构化原因 | ✅ **把"不可观测"转成"可询问"**；在缺 `app_uninstall` 时，这是把"杀进程类（技术性）"与"主动放弃"分开的现实手段；❌ 依赖门店执行 |

> **方案 B 是唯一能直接修复"分母被扔掉"的手段**，且**不依赖厂商**（可用我方台账实现）→ **建议作为研发可立即落地的口径修正**：**`应戴天` 必须来自设备绑定的日历天数，而非"有数据的天数"。**
> **方案 B（分母） + 方案 E（原因归类）是配套的**：B 修分母、E 补归因；两者都**不依赖厂商开放新能力**，可在 SDK 契约未定前先落地。

## 四附、同源护栏原则『缺失不得被平均或清洗』（**既有 · 三处复现**）

> **命名（主理人裁决 2026-09-18，受限采纳）**：**「缺失不得被平均或清洗」原则（*既有原则；本次系在第三处复现，非新创*）**。
> 🛑 **禁写「本次提出的原则」** —— 该原则在《集成指标规格》§11 已存在、HSI 处已应用；以"本次提出"口吻命名会让人误以为指标规格原先没有、**凭空多出一个待评审增项**，或让人回查后发现"原文没有这个名字"而**质疑文档可信度**。→ **凡引用处一律写「既有原则，复现于 X 处」。**

### 三处出处（同一原则的独立复现）

| 处 | 出处 | 该处形态 | 口径 |
|---|---|---|---|
| ① | 《集成指标规格》**§11.1 / §11.2** | **原始出处** | 分母不能被稀释或清洗来讨好指标；`migratable=false` → 计入分母、不计入分子 |
| ② | 《集成指标规格》**§11.2 / §11.2.1**（可判定覆盖率） | 第二次应用 | 门店级 <20 标"样本不足"，但**全网/租户级仍须告警** |
| ③ | **本文 §2.4 / §4.1 + 任务 #3 §1.8③** | **第三次复现** | **本文 §4.1「不补 0」静默失效**（缺数据天不进分母 = 把分母扔掉）+ **A3 不可观测占比须按形态单列** |

**一句话定性**：**这条原则是"防止指标被粉饰"的护栏，不是"数据不得清洗"的禁令。**

### 两条限定（本裁决的实质内容）

**限定 1 · 命名须写明"既有原则的复现"，不得写成"本次新创"** —— 见上方命名与 🛑 警示。

**限定 2 · 适用范围必须收窄，只约束两件事，不得泛化为"任何分母都不得清洗"**：

✅ **只约束**：① **因缺失而剔出分母**（悄悄扔掉没数据的单元 → 分母虚小）；② **跨单元聚合平均**（高缺失单元与低缺失单元平均 → 缺口被掩盖）。

🚫 **不约束、也不得被援引来反对**：① **重复记录去重**（同 `device_id` + 同时间戳的重复上报）；② **测试 / 联调数据剔除**（`is_test` 标记行）；③ **异常值技术性修正**（越界时间戳、明显错误单位）。

> ⚠️ **为何必须写这条边界**：若被泛化为"分母一律不得动"，研发做数据清洗时会**无据可依** —— **去重与剔测试数据是正当且必要的**，被误挡会直接导致指标数值错误（**重复计数**）。**"缺数据不能说"与"假数据要清掉"是两回事。**

## 五、合规风险点（**只指风险点，不下法律结论**）

### 5.1 数据落点与出境

| 形态 | 数据落点 | 是否经厂商服务器 | 出境风险 |
|---|---|---|---|
| ① SDK 直连 | **我方服务器**（境内可控） | ❓ **待确认**（部分 SDK 要求设备先经厂商服务器激活/鉴权） | **取决于是否经厂商服务器 + 服务器位置**（未知） |
| ② 厂商云 API | **厂商服务器 → 我方** | ✅ 是 | 🔴 **若厂商服务器在境外 → 触发数据出境** |
| ③ 健康平台中转 | **Apple / Google 服务器 → 我方** | ✅ 是（经平台方） | 🔴 **高**（Apple Health 经 iCloud、Google Health Connect 经 Google 服务） |

### 5.2 与 PIPL 的关系（风险点罗列，不作结论）

- 心率、血氧、睡眠、血压等属 **PIPL 第 28 条「敏感个人信息」** → 需**单独同意**、**告知必要性与影响**、**最小必要**（PRD P0-02 已有"个人信息授权分项勾选、可单独拒绝"的设计，方向正确）。
- **数据出境**（PIPL 第 38/39 条）：若触发，需**单独同意** + 安全评估 / 标准合同 / 认证 之一。**形态③ 的出境风险最高**，需法务确认。
- **需法务确认项**：① 云 API 数据主权条款；② 健康平台中转的合法路径；③ 隐私政策与授权文案中对手环数据的表述粒度；④ SDK 内置第三方 SDK 的隐私清单（原生 SDK 常含统计/崩溃组件）。

### 5.3 ⚠️ 厂商免责声明对本设计的影响（**"印证"与"新增约束"双重**）

厂商使用手册/保修免责原文：**「本产品并非医疗设备。所有数据和测量结果仅供参考，不用于医疗诊断」**。

| 角度 | 判定 | 说明 |
|---|---|---|
| **是"印证"** | ✅ **是** | 厂商**自己**声明数据不用于医疗诊断 → 我们"**手环数据绝不进效果主判据**"的设计，**与数据源的能力声明方向一致**，**不是过度保守，而是与数据源对齐的必然选择**。同时印证"核心指标必须靠**同源自评量表**（02 题组 0–4），而非手环生理数据"这一硬约束 |
| **是"新增约束"** | ⚠️ **是** | ① **对外材料一律不得把手环数据表述为"医疗/诊断/疗效判定依据"**（协议、小程序、评估页文案均须核查），否则与数据源免责声明冲突，可能构成误导；② **血氧 / 血压**这类消费级精度存疑字段，**必须降级为"参考"**，且**不得进"效果"**；③ 若对外宣称手环"监测血压/血氧"用于健康管理，须**同时保留"非医疗设备、不用于诊断"的免责表述** |
| **反向印证 A3 设计** | ✅ **有利** | **A3 是"行为度量"（有没有戴），不是"生理度量"（戴了测得准不准）** → 恰好**规避**了"非医疗器械"的免责风险。**这是"手环只进依从性"这一设计原则的又一条独立支撑** |

> **数析口径**：厂商免责声明**不构成**削弱 A3 的理由（因为 A3 不算生理值）；但它**强化**了"手环绝不进效果主判据"与"生理字段仅作参考"的约束。

## 七、结论与建议

### 7.1 结论（三条）

1. **GTL1 规格页只能支撑"设备可能采集到部分生理数据"，不能支撑"SDK 会把这些数据交给我们"。** P0-10 与 A3 的**可交付性完全取决于 SDK 契约，而该契约当前 100% 未知**。**所有形态相关的结论均为"条件性结论"，不构成可行性背书。**
2. **存在一个比"字段缺失"更前置的阻塞项**：厂商 SDK 要求**原生 App 宿主**，而本产品客户端是**微信小程序** → **形态①在小程序内不可行**（§2.0）。**这不是设备问题，是载体问题，且必须先确认。**
3. **A3 是本次评估的最高风险点，且风险是"静默"的**：无佩戴检测字段 → 无法区分"未佩戴"与"佩戴但无有效读数"（§3.2）→ 与"不补 0"静默失效叠加 → **分母被扔掉、A3 系统性虚高、方向单一、无告警**（§4.1）。**这即「缺失不得被平均或清洗」原则（*既有原则、复现于 §11 与本处*，见 §四附）。**
