## TL;DR（结论先行 · 5 条）

1. **方案能做出来，但"保证打开即成功"做不到 —— 能保证的是"打开即自动触发"。** 触发是**客户端可控逻辑**（`onShow` 冷/热启动均触发）；**成功**依赖蓝牙/授权/电量/占用/距离/停留时长等**客户侧与平台侧不可控变量** → **"触发 ≠ 成功"不可被工程消除**。
2. **组织先说：`onShow` 是唯一正确主触发点**（覆盖冷启动 + **热启动从后台返回**这一"客户再次打开"的主要形态），`onLaunch` 只做一次性初始化。**补拉模式（13 条逐日历史接口按日期回捞）是本方案的实质改进** —— 它把"数据产生时刻"与"同步时刻"**解耦**：客户只要**在设备留存窗口内打开过一次**，窗口内的缺失日可**补回**。
3. **但补拉抬起了一个从未解的小项：A6「无数据语义」升为关键项。** 补拉必然大量遇到"某些天设备不返回数据"；**若无法区分"超出留存窗口"与"客户确实没戴"，就会把"窗口外丢失"误记为"客户没戴"** → 这是本方案**最大的、静默的冤枉客户风险**（M2/U1 同根）。
4. **「保证可解释」的机制存在，且比"保证成功"更有价值**：**把失败分成三类 —— ①未触发（客户没打开，不记账）②触发但同步失败（技术性，不怪客户）③同步成功但确实没戴（行为性，唯一可扣分）**；并**强制"同步状态"对客户四态可见**（对照既有 **R4c**「客户以为已提出、系统里查不到」的同构失效）。
5. **人日**：复核既有 **17~38** → **在补拉模式下量级基本够，但构成需重排、下沿两处偏乐观**；建议按 **≈18~37** 复审（**下沿 +1 / 上沿 −1，量级持平**）。**账目裁定：P0-10 内吸收 5.5~10（采集链路 + 上报）＋ P0-26 内吸收 0.5~1.5（同步状态 UI 增量）＋ 待评审增项 12~25.5（SDK 编译打通 / 补拉引擎 / 授权引导 / 测试与真机）**；**封版基数与端形态三口径全部不动**。

## A. 「打开即自动同步」技术方案设计

### A.1 触发点：`onShow` 为主，`onLaunch` 只做初始化

| 触发点 | 何时执行 | 判定 |
|---|---|---|
| **`onLaunch`** | **冷启动**（进程不存在 → 创建）时**一次** | ⚠️ **不承担同步触发** —— 只做一次性初始化（读同步位点、加载授权态缓存、注册 `onBLECharacteristicValueChange` 全局回调） |
| **`onShow`** | **冷启动（onLaunch → onShow）+ 热启动（从后台返回）均触发** | ✅ **主触发点** —— **热启动从后台返回是"客户再次打开"的主要形态**，只有 `onShow` 覆盖它 |

**三条工程约束（缺一即出事故）**：① **节流** —— `onShow` 在"切到客服会话再切回""扫个码再回来"时**也会触发** → 必须 **App 级 `onShow` + 时间窗节流（建议 5 分钟内不重复发起）**；② **不阻塞渲染** —— 扫描/连接/订阅是秒级异步链路，须与首屏渲染解耦（后台 Promise），否则客户感觉"小程序卡住"；③ **可续断** —— 微信**退后台 5 秒挂起 JS 线程**（P-1），客户很可能在同步完成前离开 → 必须**逐日持久化位点**，下次 `onShow` 接着补（见 A.3④）。

### A.2 前置链路（伪代码级）

```

  runSync().catch(recordSyncFailure)                       // ② 不阻塞渲染；失败必留痕

async runSync():
 1  await wx.openBluetoothAdapter()                          // 未开 → 降级(A.5#1)；iOS 首次弹系统框(B.4)
 2  await ensureAuthorized()                                 // 授权态检查；拒绝 → A.5#2
 3  await wx.startBluetoothDevicesDiscovery({ allowDuplicatesKey:false })

 5  await wx.stopBluetoothDevicesDiscovery()

    chars    = await wx.getBLEDeviceCharacteristics(...)    // 定位 notify + write 特征
 8  wx.onBLECharacteristicValueChange(cb)                   // 全局订阅（= uni.onBLECharacteristicValueChange 的小程序映射）
 9  await wx.notifyBLECharacteristicValueChange({ state:true })
```

> ⚠️ **第 11~12 步是"能力自证"而非"业务取数"**：`getVersion()` 的 `supportSugar` 等**布尔能力位须以设备上报为准**（文档有 ≠ 设备有，brief §8.4）；`pair()` 是否必需取决于 **A13（是否强制厂商账号激活，未解）**。

### A.3 补拉时序（**本轮重点**）

> **为什么补拉是本轮的实质改进**：13 条逐日历史接口入参为 `{year, month, day}` → **数据可事后按日期回捞，不必实时采**。这把 A3（有效佩戴率）从"**必须实时连续采**"改为"**按日期回捞**" → **同步窗口内掉的数据有机会补回**。

**① 起始日期如何确定（三重取交，取最大下界）**

| 输入 | 含义 | 取法 |
|---|---|---|
| `cursor = last_synced_date` | **上次同步位点**（服务端权威 + 本地缓存） | 位点缺失（首绑）→ 忽略此项 |
| `floor = today − N_retain` | **设备留存窗口下界**；`N_retain` 由 `getVersion().bufferSize` + `getX04HealthIntervals()` **实测推定**（C③） | **未实测前按保守假设（建议 ≤7 天，取续航下沿），且 UI 明示"最多可回捞 N 天"** |
| `start = max(cursor + 1, floor)`；**上界 = `today`（含当日）** | | **不得回溯超过 `floor`** |

> 🔴 **"不得回溯超窗口"是硬约束**：超窗口的日期设备**不会返回**，回拉只会**制造假缺失** —— 若 A6 语义未解，这些"假缺失"会被读成"客户没戴"（见 C⑥）。

**② 分页 / 游标**：逐日 × 13 接口调用；单接口内以 **`sportLength > 1` 判定"还有数据"→ 继续调用直至 `sportLength ≤ 1`**（§5.44）；每日每接口设**最大翻页数上限**，防死循环 / 防设备异常时无限重试。

**③ 幂等与去重**：**业务唯一键 = `(device_id, metric, date, hour, minute)`**（某接口若为日聚合则退化为 `(device_id, metric, date)`）；上报前按唯一键 **upsert（服务端权威）** → **同一天重复拉取 = 覆盖、非追加**。"同一天重复拉取"**必然发生**（每次 `onShow` 都会重试失败日）→ **幂等是必需项而非优化项**。✅ **与「缺失不得被平均或清洗」原则不冲突** —— 该原则明确**不约束重复记录去重**（README「既有原则」适用范围已界定），去重属**正当清洗**。

**④ 失败重试与断点续传**：**每完成一天即持久化 `date_done`**（**不等全部完成才写**）；单日/单接口失败 → 入 `pending_dates` 队列 + **指数退避**，**不阻断其余日期**，下次 `onShow` 继续；**连续失败达阈值** → 标 `sync_failed` 并进入下沉提示（A.5#5/#6），**不静默**。

**⑤ 采率口径变化（跨专业交接项 —— 交数析）**：补拉模式下 A3 的"缺失日"**必须重新分解**为 **{未触发 / 触发但同步失败 / 超出留存窗口 / 确实没戴}**，**仅最后一类进行为性**。既有 0.80~0.90 采率是"**只采当时**"假设下的值 → **补拉会抬高采率**，但**新上界 = `P(客户在 N_retain 窗口内至少打开一次) × P(打开时同步成功)`** —— **绑定变量从"实时在线率"变为"打开频率 × 留存窗口"**。（属数析口径，本文不代定数字。）

### A.4 上报我方服务端

- **通道**：`wx.request` POST 批量上报 → 我方服务端同步接口。
- **鉴权**：**沿用既有 X-1 服务端判定**；派生结论（A3 / `AS` / `effect_verdict` / 退款资格）**一律不下发客户端**（W-1）。
- **必须遵守既有「汇聚式数据流」**（brief §2.1.2 / PRD §2.7.1）：**上行链路 = 小程序 → 我方服务端（单向）**；小程序**只在采集时刻作为传输通道，采完即释放**；**本地只缓存同步位点与失败队列，不缓存业务数据副本**；**不得持有权威副本、不得转发给其他端**。三端仍各自从**服务端**拉取。
- ⚠️ **对既有架构的一处口径更新（须登记，非改架构）**：原架构为「手环 → 厂商 App → 厂商云 → 我方服务端」；**本方案新增一条上行支路「手环 → 小程序（BLE） → 我方服务端」**。**这不违反汇聚式**（小程序把数据交给服务端，**不是转发给其他端**），但它**改变了"谁采集"** → **正是 config #44 的 `M-WX-FG`**。**"权威副本唯一在我方服务端"不变。**

### A.5 失败与降级矩阵

| # | 失败环节 | 客户看到（**须合规 W-2：正向 + 中性**） | 我方如何记账 |
|---|---|---|---|
| 1 | **蓝牙未开** | "请打开手机蓝牙以同步手环数据" + 图文引导（**小程序无 API 直接跳系统蓝牙设置**，见 B.4） | 技术性 / **不扣分**；记 `sync_blocked:bt_off` |
| 2 | **未授权**（含 iOS 首次拒绝） | 一次性引导弹窗 + 拒绝后"去设置"图文（B.4） | 技术性 / **不扣分**；记 `sync_blocked:no_auth` |
| 3 | **配对 / 鉴权失败** | "同步失败，可稍后重试；到店可请调理师协助" | 技术性 / **不扣分**；记 `sync_failed:pair` |
| 4 | **连接超时 / 未搜到手环** | "未搜索到手环，请确认手环在附近且已充电" | 技术性 / **不扣分**；记 `sync_failed:connect` |
| 5 | **SDK 解包失败**（错误码 1~5） | "同步失败"（**不对客户暴露错误码**；错误码只上报服务端） | 技术性 / **不扣分**；记 `sync_failed:decode:<code>` |
| 6 | **上报失败**（网络 / 服务端 5xx） | **"已同步到本机，稍后将重试上传"**（**禁止写"同步成功"**） | 技术性；本地队列保留重试；**不得因上报失败下沉客户** |
| 7 | **当日无数据** | "该日暂无数据"（**正向计数，非"缺失 N 天"**） | ⚠️ **依赖 A6**：窗口**内**无数据 → 倾向行为性；**超窗口**无数据 → **必须判技术性**（C⑥） |
| 8 | **设备被厂商 App 占用连接**（M10 双 App 抢 BLE） | "未搜索到手环"（同 #4） | 技术性 / **不扣分** |

> 🛑 **两条硬底线**：**① 手环类缺项一律警告、不得反转为阻断**（ARC-07/08/11）；**② 同步失败不得转为对客户不利**（见 B.3③）。

## B. 「必须保证打开即成功」的可实现边界（**本轮最重要的判断**）

### B.1 「打开即自动触发」能保证吗？ → **能保证**

`onShow` 在**冷启动与热启动均触发**，是**纯客户端逻辑**，**技术上可控、可保证**。
> ⚠️ **但"触发"是客户端事件，不是"数据到达"事件。** 本节的核心就在于**触发 ≠ 成功**。

### B.2 「打开即采集成功」能保证吗？ → **不能**（逐项列不可保证变量）

| # | 不可保证环节 | 发生率来源 / 性质 |
|---|---|---|
| 1 | **客户没开蓝牙** | 手机省电习惯 ／ **客户侧** |
| 2 | **拒绝授权且 iOS 不再弹窗**（不可逆） | iOS 系统行为，**任何 App 都绕不过** ／ 平台侧 |
| 3 | **手环没电 / 未充电** | 实际续航 5~7 天 ≠ 文案"待机 45 天"（M6）／ 客户侧 + 厂商文案 |
| 4 | **手环被厂商 App 占着连接**（M10）＋ **信号干扰** ＋ **远离手机**（BLE ~10m） | BLE 单 central 独占 / 2.4G 拥挤 / 距离 ／ 技术性与环境 |
| 5 | **客户停留 < 同步所需时长** | 退后台 **5 秒挂起 JS 线程**（P-1）／ 平台侧 |
| 6 | **超出设备留存窗口** ＋ **微信 BLE 接口偶发失败** | `bufferSize` 有限 / 平台级 ／ 设备侧与平台侧 |

> 🔴 **发生率数据全部为"未实测推定"** —— 须由**实验 A（10 位客户 14 天）/ 实验 C（断连能否回补）**测；**在实测前一律按"未缓解"记账，不按"已缓解"记账**（双向执行）。

### B.3 👉 关键设计建议：**"保证成功"不可得，"保证可解释"可得且更值钱**

**① 区分三种失败（本方案的核心机制）**

| 类别 | 定义 | 是否可扣分 | 归属 |
|---|---|---|---|
| **① 未触发** | 客户**根本没打开小程序** | **否** —— 这不是"失败"，是"客户没来" | 仅作覆盖率分母说明 |
| **② 触发了但同步失败** | 技术性（蓝牙/授权/电量/占用/干扰/平台） | **否** —— **不怪客户** | 并入既有 **G7 技术性缺失** |
| **③ 同步成功但确实没戴** | 行为性 | **是 —— 唯一可扣分情形** | 进 A3 行为性 |

> **一句话**：**把"扣分"收敛到客户唯一真正可控的那一维。** 这正是"不强制佩戴"硬约束的**正确落地方式**。

**② 「同步状态」必须对客户可见（否则会复制 R4c 的同构失效）**

- 客户端**四态**：`同步中` / `同步成功（含最后同步时间，精确到日）` / `同步失败（原因类别 + 补救指引）` / `该日暂无数据`。
- 🔴 **同构失效（须并列引用）**：既有 **R4c =「客户认为他已提出过，而系统里什么都查不到」**；本方案下的对应物 = **「客户以为已同步，而系统里没有他今天的数据」** —— **同一条传递性失效链**。→ **同步状态 = R4c 的"回执状态位"在手环场景的复现**（瑞思已提出："没有回执状态位 = 永远显示成功的开关"）。
- ✅ **W-3②（同屏显示同步时间，精确到日）在本方案下从"必做"升为"不可省"** —— 它把"数据不一致 / 看起来没同步"**改写成"时点不同"的可见事实**。
- ⚠️ **文案纪律**：**"同步失败"是可说的**（技术性、非客户过错）；**禁止**写成"您未佩戴 / 您缺失 N 天"（W-2：负向措辞入扫描词表，命中阻断）。

**③ 失败不得转为对客户不利（对照 B-4 与"不强制佩戴"硬约束）**

- **B-4「同步义务转嫁给客户 → 依从性负担净增加」在本方案下仍然成立、且更需对冲**：打开即同步 = **同步义务形式上仍在客户侧**（客户得打开小程序）。
- **三条护栏（须同时落地）**：
  1. **同步失败 / 未触发一律不计入 A3 行为性** ——「不强制佩戴」落地边界：**拒绝佩戴不得降低服务等级**。
  2. **"必须打开小程序"不得升级为获得服务的任何前置条件**（承 `native-app-feasibility` §6.2 **B-1/B-2** 同型）。
  3. **评估页对技术性缺失标注"缺失原因待门店确认"**（既有 0 新增交互兜底，落在既有到店接触点）。
- 🛑 **本方案最大误判风险**：**把"客户没打开"读成"客户没戴"** —— 与 **M2 / U1 同根**，必须用 B.3① 三分类挡住。

**④ 措辞纪律（对业务方：可承诺 / 不可承诺）**

| 措辞 | 可否承诺 | 理由 |
|---|---|---|
| ❌ "**保证打开即成功同步**" | **不可** | 成功依赖客户侧 + 平台侧不可控变量 → **过度承诺** |
| ❌ "**自动采集（无需客户操作）**" | **不可** | "打开小程序"这一动作**本身即操作**；后台自动在微信平台**技术上不可能**（P-1/P-2） |
| ✅ "**打开小程序即自动发起同步，无需额外点击**" | **可** | 准确的**"触发"层**承诺；**不含"必定成功"** |
| ✅ "**尽最大努力自动同步；同步结果对客户可见**" | **可** | **承诺可解释性，而非承诺成功率** |
| ✅ "**同步失败不会对客户产生不利影响**" | **可（且应作硬承诺）** | 已落地的合规约束（ARC-07/08/11 + 不强制佩戴） |
| ⚠️ "**可回捞最近 N 天**" | **待实测后方可承诺具体天数** | 依赖 `bufferSize`；**未实测前不得对外给数字** |

### B.4 iOS 授权不可逆 —— 一次性引导设计

- **何时弹**：**不在准入/首页冷不丁弹**（会误拒且难补救）→ **在客户首次表达佩戴意愿后、且有上下文说明时弹**（"为同步您的手环数据，需允许蓝牙权限"）。
- **拒绝后补救**：iOS 拒绝后**不再弹系统框** → ① 捕获 `wx.openBluetoothAdapter` 的授权失败码；② **就地图文引导**："设置 → 微信 → 蓝牙 打开权限"；③ **每次 `onShow` 静默检测一次**，仍拒绝则**只保留一行轻提示**（**不反复弹窗骚扰**）。
- **小程序能否跳转系统设置？** → **不能**。微信小程序**无打开系统设置页的 API**；`wx.openSetting` **只能打开小程序自身的授权设置页，且仅覆盖小程序 scope 类权限，不含系统级蓝牙开关**。
- **替代方案（按优先级）**：① **`wx.openSetting`** 先试（可管理小程序内已授权 scope）；② **图文引导 + 门店兜底** —— 在**既有到店接触点**由调理师/经络师当面协助开启（**复用 T1 文案层，0 人日**）；③ **服务端兜底采集** —— 若 iOS 授权始终不可得 → **退回路径 B/C**（服务端拉取 / 装厂商 App）。
- **"一次性"纪律**：完整引导**只在首次触发且授权未通过时执行一次**；后续**只做静默检查 + 一行轻提示**。
