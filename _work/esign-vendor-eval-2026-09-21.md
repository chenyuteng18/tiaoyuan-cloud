## 〇、决策卡（业务方 5 分钟可拍板，用大白话）

> **一句话现状**：客户签协议这件事，我们**不自己造**（自建 CA 有法律风险、成本更高），而是**租一家有国家牌照的电子签平台**。现在要在 5 家里挑一家。**这件事不定，06 屏「协议书签署」就写不完，整个「先签后做」的门禁就收不了口。**

### 选项 A（主选）：e签宝（含医疗线「医签宝」）

| | 内容 |
|---|---|
| **是什么** | 国内成立最早、**唯一自主持有 CA 牌照**的电子签厂商之一；「医签宝」是它的**医疗行业版**，医院里签知情同意书用的就是这套。 |
| **选它，你会得到** | ① 资质最硬（国家密码局 / 公安部 / 等保三级 / 国密全套）；② **医院知情同意书 + 客户手写签 + 公司盖章**的真实落地案例最多（浙大四院、浙江省妇保、丽水卫健委）；③ **多租户架构已被卫健委/医共体验证过**——和我们「品牌 / 区域 / 门店」三级分层几乎同构；④ 微信小程序有三种官方接法（最省事的一种**零域名配置**）。 |
| **选它，你要接受** | ① 带 API / 回调的档位**公开价不透明**，得找商务报价（按份计费的门槛约 **¥650 / 100 份** 起）；② 品牌知名度高、报价弹性可能不如小厂。 |
| **不选的风险** | 无。这是主选，选了就能往下走。 |

### 选项 B（备选）：腾讯电子签

| | 内容 |
|---|---|
| **是什么** | 腾讯云旗下电子签，**长在微信生态里**，客户体验最顺、入门价最低。 |
| **选它，你会得到** | ① 客户在微信小程序里签字**最顺手**（面容 / 指纹都支持）；② **签署完成回调有官方文档**（`FlowStatusChange`），自动放行门禁有官方支撑；③ 入门门槛低（个人版免费，中小企业档约 **¥1,500 ~ ¥6,000 / 年**）。 |
| **选它，你要接受** | ① **医疗行业沉淀不如医签宝**（知情同意书案例少）；② **要 API 集成可能要上到约 ¥4 万 / 年 的专业档**——对我们是笔硬钱；③ **国密 / 信创适配较弱**（竞品口径，需核实），而《个人信息授权》是敏感信息，国密支持对我们有加分。 |
| **不选的风险** | 无。备选，是「主选谈不成时」的替代。 |

### 选项 C（什么都不选 / 继续拖）

| 代价 | 说明 |
|---|---|
| **06 屏写不完** | 「协议书签署与确认」的实现方案**依赖选型**（谁来发起签署、签完怎么通知我们）。不定选型，这块只能出「伪代码级」设计，开发照着做不了。 |
| **门禁收不了口** | 「未签协议 → 不产生执行记录」这条**后端拦截**，卡在「签完怎么知道」这一环。**没有回调，就得轮询，06 屏自动化程度直接降级**（见 §五）。 |
| **签署链路整体后退 4~6 周** | 与法务协议文本是**同一根链条**（`roadmap` 口径：法务侧 4~6 周日历）。选型是这条链上**我们自己能推**的一环，拖它就是白白占用法务的日历。 |

> **建议动作（今天就能做）**：把 §六 的「发给服务商的问题清单」分别发 e签宝 与 腾讯电子签，拿到**带 API + 回调 + 多租户的正式报价**，一周内二选一。**技术上两家都能做，差别在「医疗合规沉淀」与「报价」。**

## 一、候选池（5 家，均以 2026-09-21 现网核实）

**入围标准**（逐条对项目硬约束）：

1. 端形态：客户 = 微信小程序；调理师 = APP；管理 = Web，签署在**门店现场**发生 → **必须有好用的微信小程序签署路径**。
2. 签章形态：**客户手写轨迹** + **门店授权人企业签章/法人章**。
3. 合规：敏感个人信息、授权可追溯、**租户间物理隔离**（三级）。
4. 存证：可取证、**文本版本与留痕绑定**。
5. 多租户：按品牌 / 区域 / 门店隔离 + 可导出。
6. 预算敏感：**不要只为大企业设计的重方案**。

| # | 候选 | 一句话定位 | 是否入围 |
|---|---|---|---|
| 1 | **e签宝（含医疗线「医签宝」）** | 成立最早、自持 CA 牌照、医疗行业沉淀最深 | ✅ **主选** |
| 2 | **腾讯电子签** | 腾讯云出品，微信生态最原生，入门价最低 | ✅ **备选** |
| 3 | **法大大** | 商事合规/司法存证强，开放平台成熟 | ✅ 保留（第 3 备） |
| 4 | **上上签** | 合同全生命周期管理强，价格透明 | ⚠️ 保留但弱（医疗案例少、API 档贵） |
| 5 | **契约锁** | 面向中大型组织的印控 + 私有化标杆 | ❌ **排除**（重方案，¥20 万起，与「预算敏感 + 中小企业启动」不符） |

> **说明**：项目 `_source/上游结论汇编-给析客.md`（竞品能力表 · 医签宝行）与 **PRD 第 4 章「8 个真实竞品全景」的医签宝行** 把「**医签宝**」写作竞品能力；**核实后确认：「医签宝」不是独立第三方，而是 e签宝面向医疗行业的平台**（`esign.cn` 官方文章《e签宝携新一代医疗电子签名平台亮相 CHINC 大会》）。故候选池按「**e签宝 / 腾讯电子签 / 法大大 / 上上签 / 契约锁**」共 5 家收口，医签宝归入 e签宝一列。

## 三、推荐结论

### 3.1 主选：**e签宝（医疗线「医签宝」）**

**推荐理由（按硬约束逐条对照）**：

| 硬约束 | e签宝 匹配情况 | 依据 |
|---|---|---|
| ① 小程序端签署 | ✅ 官方文档给出**三种**小程序对接方式，其中「跳转 e签宝公证签小程序」**无需配置业务域名**、对接成本最低 | e签宝开放平台《微信小程序对接签署说明(推荐)》`[官]` |
| ② 手写轨迹 + 企业印章 | ✅ 手写签名接口 + 企业章/法人章；医疗场景已有**患者手写签知情同意书**落地 | 浙大四院案例（中国日报）、浙江省妇保案例 `[官]` |
| ③ 敏感信息可追溯 + 租户物理隔离 | ✅ **多租户架构**在卫健委场景已验证（丽水：22 医院 + 246 医共体共用一个平台的独立租户），与「品牌/区域/门店」三级**同构度最高** | e签宝官方《CHINC 大会》文章 `[官]` |
| ④ 可取证 + 文本版本绑定 | ✅ 模板版本 + 全流程存证 + 证据报告 / 公证书 / 司法鉴定意见书 | e签宝产品页 `[官]` |
| ⑤ 多租户隔离 + 按租户导出 | ✅ 有集约化管理实践，**导出细节需确认** | `[官]` + 🔍 |
| ⑥ 预算敏感（非大企业重方案） | ✅ 按份计费门槛约 **¥650 / 100 份**，属中小规模可承受；**带 API 的档位报价待商务** | `[三方·2025 价格盘点]` |

**主选唯一的不确定点**：带 API + 回调 + 多租户的**正式报价**（见 §六 待确认项）。若报价超出预算，直接切备选。

### 3.2 备选：**腾讯电子签**

**推荐理由**：微信生态最原生、客户现场签字体验最顺；**回调有官方文档**（`FlowStatusChange`）——这对 06 屏门禁自动放行是**决定性支撑**；入门价最低，谈崩主选时**切换成本最小**（同属小程序生态）。

**备选的两个减分项**：医疗行业沉淀弱于医签宝；**要 API 可能上到约 ¥4 万/年专业档**，是我们预算里的硬钱；国密支持口径存疑。

### 3.3 若主选谈不成时的切换成本

| 切换路径 | 成本（人日） | 说明 |
|---|---|---|
| **e签宝 → 腾讯电子签** | **≈3~5 人日** | 前提是**服务端做一层 `ESignAdapter` 防腐层**（发起签署 / 查询 / 回调接收 / 存证哈希 四个方法）。切换 = 换一个适配器实现 + 重跑实名/意愿流程，**业务代码零改动**。 |
| 若**不做**适配层、把 e签宝 SDK 直接散落进业务层 | **≈8~12 人日** | 回调字段、签署控件、状态枚举都要改，且要回归测试。 |
| **切到法大大（第 3 备）** | ≈4~6 人日 | 同为开放平台形态，但小程序内嵌需配业务域名，比 e签宝多一步。 |

> **工程结论（强建议）**：**无论选谁，都必须在服务端建 `ESignAdapter` 防腐层**。它把「选型决策」从「不可逆的一次性决定」变成「可替换的实现细节」——这是把本件的风险压到最低的关键动作。已与 **T-6 契约 §2.2 域 B · B1 入参**的 `customer_sign` / `operator_sign`（`_work/contract-t6-api-freeze-2026-09-19.md`）天然对齐。

### 4.5 ⚠️ 一个必须提请注意的合规细节

PRD **P0-02** 要求《知情同意书》一页承载包含「**禁忌结论回显（只读）**」+「个人信息授权（分项勾选）」。其中「**禁忌结论回显**」含**健康类信息**（属敏感个人信息）——若它会**进入送签的协议 PDF**，则该 PDF 含敏感个人信息，一旦上送第三方电子签平台即为**数据出域**，与 PRD Q6 默认口径「**健康数据不出租户边界**」（**PRD §10「待确认问题」· Q6**）存在张力。

> **⚠️ 2026-09-21 裁定后修订（team-lead 裁 (ii)，详见 §4.5.1）**：必须**分清两个对象**——裁定排除的是「**协议正文作为客户端包资产下发**」；**没有**排除「**禁忌结论在客户端页面上回显**」。

| 对象 | 裁定后的状态 | 是否触发出域 |
|---|---|---|
| **禁忌结论回显（P0-02，只读）** | **仍留在客户端**的知情同意书页面上 | ❓ **取决于它是否被渲染进送签 PDF**（见下） |
| **协议正文 8 章全文** | 移出客户端包 → 服务端 `doc_template.content` → 由服务端 / 厂商侧页面呈现 | 否（正文本身不含逐人健康数据） |

**⇒ 决定性问题因此收敛为一个二选一（**须法务裁定**）：**

> 🔖 **本问题 = 已登记的 `Q-E1`，不是本件新立的问题。** 定义见 **T-6 契约 §待裁定 · Q-E1**（🆕 2026-09-21 登记，注明源自本选型件 §4.5）；同源问题 **`Q-E2`**（协议书正文是否必须出现「退款」字样）见 **PRD 附录 C.6**。
> **本件处置（team-lead 2026-09-21 裁定）**：**不另立编号**，正文一律写 **`Q-E1`**；本表内保留的行内引用编号为 **`Q-E1（本件 EV-7）`**，且§七 只保留**一行**。理由：同一决策挂两个编号 = 口径漂移的起点。

> **「禁忌结论回显」是否会被写进送签的 PDF 正文？**
> - **不写进 PDF**（页面回显归页面、PDF 正文只承载**中性结论性表述**）→ 送签文本不含逐人健康信息，**出域问题按方案 a 关闭**。
> - **写进 PDF**（为满足下述 QC-6「签署前全文可读 + 可回看」，把回显内容一并渲染进签署稿）→ 该 PDF **含健康相关敏感个人信息，仍是出域** → **必须走方案 b**（授权范围 + 存储地域 / 不出境确认 + DPA）。

**（方案 a / 方案 b 定义不变）**：
- **方案 a（推荐）**：送签文本**不含**逐人健康细节，禁忌结论以「已告知、客户已确认」的**结论性表述**承载；原始禁忌数据**只在本地存**。
- **方案 b**：若必须含，则须把「电子签数据出域」写入《个人信息授权》范围，并确认厂商**数据存储地域 / 不出境**，并签 DPA。

> **🔴 一处不得被"服务端生成"四个字消解的边界（A6 提出，我方采纳）**：team-lead 裁定中「送签 PDF 由服务端生成 → 可控制不含逐人禁忌结论 → 同时解掉健康数据出域」这一断言，**依赖上面那个尚未裁定的问题，不能提前当作已关闭**。理由：**「服务端生成」只决定「谁渲染」，不决定「渲染什么进 PDF」。** 上方二选一未定前，§4.5 的出域敞口**保持开放**。

**→ 列入待确认项（§五 VQ-7）。**

#### 4.5.1 与 A6 合规门禁的交叉核实（**2026-09-21 与 a6-compliance-engineer 实测往来**）

> **本节为对上文的一处修正 + 一处加固。** 我先前向 A6 建议「把版本号 + 哈希纳入构建期扫描的管控字段」，**经 A6 指出并经我方复核，该建议属类别错误，现予撤回**——理由与替代结论如下，均已实测。

**(1) 撤回理由（三条，接受）**：

1. **类型不同**：A6 门禁是**负向字符串存在性检测器**（只扫 `client-package/**`，输出模型 = 「命中即构建失败」）；版本+哈希是**正向存在性 + 完整性**控制。二者失败语义对不上（前者的输出是 `term=` + `file:line`，「哈希缺失」既无 term 也无 line）。
2. **扫描面是 ADR-12 固定的三面**（`scan1_refund` / `scan2_negative` / `scan3_derived`），**不可增删改**：`skeleton/compliance/scan-manifest.json` 的 `scan_faces` 一旦漂移，门禁 **exit 4 拒跑**，自检 T3 另有独立手写副本再断言一次。加面 = ADR 修正，不是词表编辑。
3. **该控制已有归属**：`dy-audit` 的 canonical v1 审计哈希链（`AuditChainHash` / `ChainVerification`，配黄金向量 + 单射性 + 表契约测试）。**签署留痕的证据绑定属于那条链 + 厂商模板版本管理，不属于词表。**

**(2) 但真正的缝比我命名的更硬——A6 用真实门禁实测出两条**：

| # | 实测 | 结果 |
|---|---|---|
| A | 把 **PRD 自己的字段名** `agreement.refund_clause_snapshot` 喂进 scan1 | **BUILD FAILURE**（蛇形 / api 路径 / 常量名 同炸；同表中性兄弟字段 `agreement.clause_service_nature`、`agreement.privacy_scope_json`、`agreement.band_clause_text` 全部 quiet / exit=0） |
| B | 章节标题「**退款/终止/归档**」（**PRD 附录 C.1.5 · 04.§六**） | 命中——`退款` 是 scan1 词条且 **CJK 走子串匹配** |

> **已验证就位（2026-09-21 复核）**：`agreement.refund_clause_snapshot` 现于 **PRD §8 数据模型 · `agreement` 实体** 与 **PRD 附录 C.1.5 · 04.§六 退款/终止/归档**（04 表字段映射，原文「04.§六 退款/终止/归档（4 条）… 必须快照存储 … 未签阻断」）。**⚠️ A6 原引用的 PRD 旧行号（L1355）系 requirement-analyst 并行回写 PRD v1.31 后行号移位所致——内容一致；本条已一律改为语义指针。**
>
> **含义**：**按 PRD 正确实现内容，反而会让门禁构建失败**——因为 PRD 自己给 04 表 §六 起的字段名，按构造（ASCII 单段匹配 `refund` 打头）就是 scan1 命中项。今天未炸的唯一原因是 `client-package/` 实测仅 8 个文件、**里面还没有任何同意书/协议模板**；而 P0-02 的知情同意书页**是客户小程序端页面**（**PRD §2.3 端形态矩阵 · 客户 = 小程序**）。一旦 §六 章节名或该字段名进入小程序文案 / i18n 键表 / api 路径 / 常量，构建即失败。

**(3) 缝的准确形状（采纳 A6 的改述）**：

> **不是「词表少一个字段」，而是「协议文本及其字段名是一个没有归属的制品类别」。**

**但经我方复核：这个归属其实已经存在**——**PRD 附录 C.1.8 · `doc_template` 实体** 与 **PRD 附录 C.4 · P0-27**（v1.28 增项）已立该实体：`doc_type(enum{知情同意书, 调理协议书, …}) | tenant_id | content | version | is_active`，唯一键 `(tenant_id, doc_type, version)`，**version 递增、不可覆盖**，签署时快照、已签不回溯，并带**高风险词非阻断高亮**（含「无效退款」）。**⇒ 协议文本作为一个制品类别，其版本入口与归属人（超级管理员，tenant 级）已经裁定**；缺的不是机制。

**⇒ 因此真正的开口收敛为一个「客户端命名 / 下发」决策**：

| 选项 | 内容 | 解掉什么 |
|---|---|---|
| **(i)** | 客户小程序端对 refund 域字段名与 §六 章节名改用**中性词别名** | 仅解门禁撞词 |
| **(ii)** | **协议正文不下发为客户端包资产** | 解门禁撞词；**出域问题另需 §4.5 二选一裁定** |

> **✅ 裁定结果（team-lead，2026-09-21）：走 (ii)。** 要点：
> - 协议正文（含 04 表 §六「退款/终止/归档」章节名）**唯一落点 = 服务端 `doc_template.content`**（**PRD 附录 C.1.8 · `doc_template`**，`content(text)` + `version(int)` 递增不可覆盖；编辑入口 **P0-27 / config #46**）→ 签署时经**服务端 / 厂商侧页面**呈现。
> - **客户端侧标识符一律不得出现服务端 refund 域词汇**。
> - **门禁不得放宽**：不加 path 例外、不加白名单、不放宽词表。
> - **A6 已落地并实测**：`scan1_refund.words` 追加裁决在案区（词条 6 条零改动）、`compliance/README.md` 新增覆盖边界段；在真实 `client-package/constants/` 注入 `agreement.refund_clause_snapshot` → **仍 BUILD FAILURE**；门禁 PASS，自检 11/0。
> - **PRD 侧已登记为附录 C【QC-6】**，附不可省的验收项：**签署前全文可读 + 可回看**（协议书是客户签署的法律文书）。

> **⚠️ 措辞防误读（A6 提出，我方已采纳并改写本件全文）**：**「不下发」≠「客户看不到」。** 上文选项 (ii) 我原先写作「客户端只回显**中性摘要**」，**该措辞易被误读为降级方案，已废弃**。正确表述为：
> **「协议正文不下发为客户端包资产，但签署前经服务端 / 厂商侧页面完整可读、可回看」**（QC-6 明确不许退化为「客户只看中性摘要就签」）。

**(3·补) 我前述「(ii) 一并解掉健康数据出域」的说法须收窄**：
「协议正文不下发」**只决定正文的落点**，**不决定送签 PDF 里渲染什么**。出域敞口是否关闭，取决于 §4.5 那个二选一（禁忌结论回显**是否写进 PDF 正文**）。**」服务端生成」只决定「谁渲染」，不决定「渲染什么」。** 本节不作提前结案。

**(4) A6 可提供、我无法覆盖的那部分（如实标注边界）**：

构建期静态扫描**无法**为「健康数据出域」提供任何控制——它只读一个目录里的文本，不看数据流向、不看运行时、不看 PDF 内容、不看出境。A6 给出的定位判断（**已采纳进本件**）：

> **送签 PDF 的模板若落在 `client-package/` 内，它才在扫描面里；若模板在服务端或厂商侧，它完全在覆盖面之外。**

**⇒ 对本项目的含义**：我们的送签 PDF 由服务端 `doc_template.content` 生成 → **不在 `client-package/` → 不在扫描面**。**所以「协议文本本身」是被 scan1 覆盖不到的**；被覆盖到的是**客户端上任何出现该字段名 / 章节名 / 相关文案的地方**。这正是 P0-02「一页承载回显」页的风险点。

**→ 出域敞口列入待确认项（§五 VQ-7a / VQ-7b）；并升级至法务裁定 —— 即已登记的 `Q-E1`（本件行内编号 EV-7，见 §七）。**
